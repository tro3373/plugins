# pstack をセットアップする

このページではプラグインをインストールし、pstack が使うモデルを選び、最初のタスクを走らせる。セットアップはコマンド 1 つと短い会話だけである。

## プラグインをインストールする

Cursor のチャットで次を実行する:

```text
/add-plugin pstack
```

Cursor がプラグインのインストールを確認する。

## モデルを選ぶ

次を実行する:

```text
/setup-pstack
```

[`/setup-pstack`](../../skills/setup-pstack/SKILL.md) はアクセスできるモデルを検出し、reasoning budget を尋ね、各ロール (コードの委譲先、判断、レビューのパネル) を提示し、何を使いたいかを尋ねる。質問に答えると `~/.cursor/rules/pstack-models.mdc` が書かれる。これは pstack のすべての skill が読む小さなルールである。

上書きするのは自分が気にするところだけでよい。ルールに行のないロールは skill の既定値を保つ。既定値に戻すには、そのロールの行を消す。`/setup-pstack` を再実行すると、既定値と異なるモデルを持つロールはそのまま保たれる。0.15.3 より前に書かれたルールは古い既定モデルを固定しているので、そうしたロールの行を消すか、ファイル自体を消してから `/setup-pstack` をもう一度実行する。

Auto を使ったらどうなるか気になるだろう。ロールを `inherit-parent` か `auto` にすると pstack はサブエージェントの `model` フィールドを省略し、サブエージェントは親チャットのモデルを継承する。どちらの値も同じ意味であり、いずれもモデル slug ではない。パネルのロールでは値がリストになり、エントリ 1 つにつきサブエージェント 1 体が走るので、リストの長さがパネルのサイズを決める。セットアップは `swarm workers` も設定する。これは race が各アームにモデルを指定しない限り、すべての `/swarm` ワーカーが使う既定のモデルである。

## 検証の提案を受けるか、受けないか

セットアップの最後に、`/setup-pstack` はプロジェクト内でアプリの挙動を証明する手段 (`verify-*` skill か既存のハーネス) を探す。どちらも見つからなければ、[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md) で 1 つ生成することを一度だけ提案する。

yes と答えると `.cursor/skills/verify-<app>/` が書かれる。これはユーザと同じやり方でアプリを操作する方法をエージェントに教える、プロジェクトローカルな skill である。引き渡す前に、その skill が動くことを一度証明する。no と答えればセットアップは先へ進む。`/create-verification-skill` は後からいつでも自分で実行できる。[検証して出す](./06-verify-and-ship.ja.md#プロジェクトの検証-skill-を作る) が、これが割に合う場面を扱う。

セットアップ後は新しいチャットを始める。モデルのルールは新しいセッションに適用される。

## 最初のタスクを走らせる

現実的だが小さいものを選び、同僚に説明するのと同じやり方で書く:

```text
/poteto-mode add a --json flag to this command. text output stays byte-identical. verify both.
```

todo リストを見る。最初の項目群はマッチしたプレイブックのステップがコピーされたもので、このプロンプトなら Feature プレイブックである。`/poteto-mode` がステップを飛ばした場合、そのステップは `skip: <reason>` 付きでリストに残るので、何をやらないと判断したのかが見える。

ここから先は普通にフォローアップを打てばよい。`/poteto-mode` は sticky である。明示的に抜けると言うまで、その会話の間ずっと有効なままになる。
