# Experience First

実装の都合とユーザの喜びが衝突したら、喜びを選ぶ。

- すべての機能・コントロール・オプションは正当化されなければならない
- より少なく、よりよく出す (3 機能の磨かれた体験は、10 機能の粗い体験に勝る)
- コミットする前にプロトタイプを作る (設計判断は本番コードよりも使い捨ての HTML の方が安く済む)
- ディテールを正しく仕上げる (トランジション、アライメント、余白、フィードバック、エラー状態)
- コアループを締める (すべての機能は中心のワークフローに奉仕するか、さもなくば道を空けるべきだ)

ユーザとは、その成果を消費する者すべてである。UI ならエンドユーザだ。ライブラリや内部 API なら、それを import する同僚だ。次にそのコードを保守するエンジニアもユーザである。彼らの体験も同じ重みで評価し、彼らの視点から見た影響として説明する。

基盤は体験に奉仕すべきだ。Foundational Thinking は仕事の*順序*を統べる。この原則は*目標*を統べる。
