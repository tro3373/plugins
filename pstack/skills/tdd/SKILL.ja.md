# TDD によるバグ修正

明確で安価なテスト経路があるバグを直すときは、プロダクションコードを変える前に、壊れた挙動を実行可能にする。ゴールは、修正前に失敗し修正後に通る、焦点の絞られた回帰テストである。

現実的でないのにテストを無理やり作ってはならない。取りうるテストが、広範な harness のセットアップ、壊れやすいモック、遅いエンドツーエンドの基盤、プロダクション限定の状態、曖昧な再現手順、無関係な fixture の大量変更を要求するなら、新しいテストの追加はやめて、代わりに最も近い有用な検証を使う。

## ワークフロー

1. **バグを理解する。** 意図された挙動、現在の挙動、影響を受ける経路、観測可能な最小の再現を特定する。
2. **最も狭い実行可能なチェックを選ぶ。** そのコードパスに既に使われている、最も近い unit、component、integration、regression のテストを優先する。実用的なテスト経路が自明でないなら、ワークフローを満たすためだけにゼロから作らない。
3. **まず失敗するテストを書く。** そのバグを捕まえられたはずの、最小で焦点の絞られたテストを足す。テストは意図された挙動を符号化すべきであり、現在の実装を写し取るものであってはならない。
4. **修正前に新しいテストを走らせる。** 意図した理由で失敗することを確認する。通ってしまうか、無関係な理由で失敗するなら、実装を編集する前にテストか再現を直す。
5. **バグを直す。** 近傍の契約を保ちながら、意図された挙動を満たす最小のプロダクション変更を行う。
6. **回帰テストを再実行する。** 今度は通ることを確認する。

## 失敗するテストが現実的でない場合

代わりに最も近い実行可能な回帰チェックを使う。狙いを絞ったスクリプト、手動の再現コマンド、ブラウザ自動化、スナップショット比較、ログのアサーション、焦点を絞った integration チェックなど。

悪いテストを書くくらいなら、新しいテストを書かない方がよい。悪いテストとは、ほとんどモックをテストしている、現在の実装の詳細を符号化している、タイミングや無関係なグローバル状態に依存している、小さな修正のために高価な基盤を必要とする、あるいは修正を証明した直後に消されるようなテストである。

## ガードレール

- 誤った実装に合わせるためだけにテストを変えてはならない。
- 期待される挙動が本当に変わり、その理由が明確な場合を除き、既存のアサーションを弱めてはならない。
- 回帰テストはそのバグに焦点を絞って保つ。広範な fixture の変更や、無関係なカバレッジ拡大は避ける。
- バグが flaky なら、可能な範囲でテストを決定的にし、固定しようとしているシグナルを文書化する。
- バグがより広い失敗のクラスを露呈しているなら、まず焦点を絞った回帰の経路を着地させ、そのうえで追加の兄弟カバレッジを検討する。

## 最終応答

結果だけでなく証拠を報告する:

- 修正前に失敗したテストまたは実行可能なチェックと、それが出した失敗を名指しする。
- 修正後に通ったテスト実行と、実施した近傍の検証を名指しする。
- 修正前に失敗する証拠を示せなかった場合は、その理由を述べ、代わりに使った最も近い回帰チェックを説明する。
