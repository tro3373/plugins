# Automate me

ユーザの作業上の規約を、エージェントが従う skill へ変換するためのガイド付きフロー。出力は、そのユーザ向けに仕立てた 1 本の `-mode` skill である (例: `jay-mode`、`priya-mode`)。

この skill は 3 つの skill を統率する。インラインの mining パス (ステップ 1 を見よ)、Cursor 組み込みの `create-skill` (オーサリング)、そして **unslop** skill (散文の規律) である。順序付けるだけである。置き換えはしない。

## フロー

### 0. 既存の skill を確認する

ユーザのハンドルに一致する `.cursor/skills/**/*-mode/SKILL.md` と `~/.cursor/skills/*-mode/SKILL.md` を再帰的に探す。mode skill はトップレベルだけでなく、個人カテゴリのディレクトリ (`.cursor/skills/<handle>/`) にも置かれうる。既に存在するなら、`AskQuestion` で意図を確認する (ユーザが既に「update my skill」などと言っている場合を除く):

- 既存の skill を更新する (繰り返し実行時の既定)
- 一から作り直す (稀。実行前に理由を聞く)

更新モードは以降のフローを変える:
- ステップ 1 は、skill が最後に編集された時点 (`git log -1 --format=%cI <path>`) 以降の履歴だけを mining する。
- ステップ 2 は、ゼロから何を捕まえるかではなく、何が変わったか・何が欠けているかを聞く。
- ステップ 4 は既存ファイルをその場で編集する。ユーザが否定していないセクションは保持する。新しい証拠があるセクションは改訂する。新しいセクションを足すのは、本当に新規のルールのときだけにする。

### 1. 履歴を mining する

ファンアウトする前に、アクティブなワークスペースの transcript の在り処を特定する。システムプロンプトがそのワークスペースの `agent-transcripts/` ディレクトリを名指ししている。そのパスだけを使う。`~/.cursor/projects/*/` を横断して glob しない。それはワークスペース境界を越え、無関係なプロジェクトの私的なチャットを読むことになる。

そのスコープ内で、直近のエージェント会話を調査し、繰り返し現れるパターンを探す。履歴のスライスにまたがる複数のサブエージェントを並列で走らせる (例: 直近 2-4 週間を 3 スライスに割り、各スライスに十分な材料が載るようにする)。各スライスの mining サブエージェントは、親が渡すワークスペース限定のパスから transcript を読み、下の signal を探し、見つけたパターンの短い構造化リストを証拠へのポインタ付きで返す。既定で狙う signal:

- 応答の好み (長さ、トーン、フォーマット、「もっと噛み砕け」といった訂正)
- 委譲の癖 (サブエージェント、モデル、専用ワークフロー、並列度)
- 検証の姿勢 (「done」の意味。ユニットテストか live な再現か。レビュワー)
- コードと散文の規律 (スタイル、引用される原則、lint / format ツール)
- プロセスの規約 (worktree、コミット、PR、レビュー / マージのツール)
- メタな好み (タスクの途中で skill を直す、新しい skill を提案する)

signal を格上げする前に、スライス間で相互チェックする。2 つ以上のスライスで見えたパターンは高信頼。単発の signal は弱く、たいてい落とす。

### 2. ユーザに直接聞く

mining では、まだ表に出ていない意図を取りこぼす。ユーザにゼロから打ち込ませるのではなく、`AskQuestion` ツール (構造化された多肢選択) を使う。

形: 1 つか 2 つの質問、各 4-6 個の選択肢、カテゴリ質問には `allow_multiple: true`。広いところ (「どの領域が最も重要か?」) から始め、選ばれた領域について具体的な選択肢で追う。構造化ラウンドの後、選択肢が拾いきれなかったものを、自由記述のチャット質問 1 つで捕まえる。

20 個の質問をぶちまけない。

### 3. 発見をクラスタリングする

集まった signal をセクションへまとめる。よくあるもの (当てはまるものだけ使う):

- **Response style**: 長さ、トーン、フォーマット。
- **Autonomy**: 聞かずにどこまでやるか。MCP ツールの使用。
- **Understand first**: 変更のスコープを切るとき・調査するときにどの skill へ手を伸ばすか。
- **Subagents**: 既定、並列度、モデルとタスクの対応、専用ワークフロー。
- **Prose / code discipline**: 原則、lint ツール、スタイルガイド。
- **Review and verify**: 再現の姿勢、検証用 skill、live テストのツール。
- **Process**: git worktree、コミット、PR、レビュー / マージのツール。
- **Skills**: skill オーサリングの癖、fix-the-skill-first、新しい skill の提案。

**poteto-mode** skill が形を示している。粒度の参考に読む。中身をコピーしてはならない。ユーザのルールは poteto-mode のルールとは違う。

### 4. skill を起草する

Cursor 組み込みの `create-skill` skill を使って skill をオーサリングする。配置:

- パス: 既存の mode skill があるなら、そのカテゴリを保つ。新規の mode では、そのハンドル向けの個人カテゴリがリポジトリに確立しているなら `.cursor/skills/<handle>/<handle>-mode/SKILL.md` を使う。そうでなければプロジェクト内の `.cursor/skills/<handle>-mode/SKILL.md` を既定にする (ユーザが個人 skill を好むなら `~/.cursor/skills/<handle>-mode/`)。
- ハンドル: ユーザの下の名前か、本人が選んだ識別子。
- frontmatter の `description`: 「write code」「review PR」のような一般的なキーワードではなく、本人の名前 + `/<handle>-mode` + 「work in their style」で発火させる。
- frontmatter の書式: `create-skill` の YAML ルールに従う。`description` は 1 つの YAML スカラーに保つ。句読点や折り返しが必要なら、クォートするか `description: >-` とインデントした継続行を使う。
- frontmatter の `disable-model-invocation: true` を既定にする。ユーザが毎ターン自分の mode を効かせたいと明言した場合にだけ、これを外す。

### 5. 散文を磨く

**unslop** skill と `create-skill` の執筆ガイドラインを全行に適用する。

ドラフトをユーザに見せ、フィードバックを受ける。複数回のイテレーションを見込む。容赦なく削る。mode skill はマニュアルではない。

### 6. 着地させる

main から切った worktree で作業する。コミットして PR を開く。main へ直接 push しない。

## ガードレール

- **1 つの会話に過適合しない。** 一度述べられ、別の場面で否定された好みはノイズである。成文化する前に複数の事例を要求する。
- **賢ぶらない。** 他の skill の中身を言い直す、比喩を発明する、エージェント読者向けに「詩的な」散文を書く、これらはコストだけで便益がない。運用的に保つ。
- **参照せよ、インライン展開するな。** ユーザが頼りにしている他の skill は、貼り付けた抜粋ではなくパス参照として現れるべきである。よそで維持されている原則ドキュメントも同様。
- **セクションは最小限に保つ。** ユーザがそこに具体的で非既定のルールを持っているときだけセクションを足す。「明確に伝える」はセクションではない。「短い段落。選択肢を比較するときはテーブル。項目が本当に並列なときだけ箇条書き。」はセクションである。
- **規約の名前は一般名にする。** 命令文では著者の下の名前ではなく「the user」か「the human」を使う。
- **対称性を強いない。** ユーザに書き留める価値のあるプロセスのルールが無いなら、Process セクションは丸ごと省く。

## 評価

`-mode` skill は主観的な出力である。`create-skill` 流のテスト / イテレーションのベンチマークループはここでは役に立たない。ユーザと感触を確かめる。本人らしく読めるか。取りこぼしは無いか。そのうえで出す。

description 最適化のループを回すのは、その skill の発火精度が実際に問題になったときだけにする。

## 使わない場合

- ユーザが欲しいのがタスク固有の skill (作業上の規約ではない) のとき: `create-skill` だけでよく、mining は不要。
- ユーザが狭いワークフロー 1 つ (例: 「コミットメッセージの書き方」) を捕まえたいとき: それは通常の skill であって、mode skill ではない。
