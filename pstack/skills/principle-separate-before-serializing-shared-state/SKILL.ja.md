# Separate Before Serializing Shared State

並行するアクタが可変状態を共有しうるときは、まず同じ可変オブジェクトが必要なのかを問う。必要でないなら、共有を無くす。共有が本物なら、直列化を構造的に強制する。ロックファイル、逐次フェーズ、排他的な所有権。指示や規約は並行制御ではない。

**なぜか:** 共有状態への並行書き込みは、断続的で、再現が難しく、デバッグに高くつく競合状態を生む。

**パターン:**
1. **共有された可変状態を特定する** (両者が読み書きするファイル、両者が push するブランチ、両者が定義し消費する API)。
2. **既定: 共有された書き込み先を無くす。** こう問う。これらのアクタは 1 つの正典オブジェクトを必要としているのか、それとも独立した事実を publish しているだけなのか。各アクタに、自分が所有するファイル、キー、ブランチ、状態ディレクトリを与え、統合は読み取り / 報告の境界でだけ行う。2 人のワーカーがそれぞれの `lastX` フィールドを 1 つの `state.json` に書くのは、依然として共有された変更である。`indexer-state.json` + `metrics-state.json` はそうではない。
3. **共有された書き込み先が 1 つであることが本物の不変条件である場合にだけ、アクセスを構造的に直列化する** (ロックファイル、逐次フェーズ、単一書き手のアクタ、あるいはアトミックな compare-and-swap)。「ロックが要る」は既定の答えではなく、確認すべき設計の臭いとして扱う。
