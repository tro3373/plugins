# 教訓を構造に符号化する

繰り返される修正を、文章による指示ではなく仕組み (ツール、コード、メタデータ、自動化) に符号化する。あらゆるエラー、人間による訂正、予期しない結果は学習の信号だ。それを捕まえ、宛先へ振り分け、ループを閉じる。

**なぜ:** 文章による指示は見落としやすい。読み手が気付き、覚え、従うことを要求する。構造的な仕組み (lint ルール、メタデータフラグ、ランタイムチェック、自動化スクリプト) は、相手の協力なしにルールを強制する。

**パターン:**
同じ指示を 2 度目に書いている自分に気付いたとき:
1. 問う: これは lint ルール、メタデータフラグ、ランタイムチェック、スクリプトにできないか?
2. できるなら、符号化する。その指示は削除する
3. できないなら (判断を要するなら)、その指示をより目立たせ、失敗モードの例を添える

**最も強い仕組みを選ぶ。** 複数の仕組みが機能しうるときは、状況が許す中で最も強いものを選ぶ (コンパイルできない表現不可能な状態、次に CI を落とす lint や禁止 API、次に正式なヘルパー、次にランタイムチェック)。エージェントは周囲のコードが既にやっていることを何であれ真似るので、弱いガードは次のテンプレートになってしまうからだ。

**系:** 修正が構造的なものなら、構造的な修正のみを使う。その指示が症状だ。

**フィードバックループ:**
- **あらゆる訂正を捕まえる。** 人間が介入したりテストが落ちたりしたら、それが一度きりのものかパターンかを判断する。
- **正しい層へ振り分ける。** 一度きり -> brain note。繰り返される修正 -> skill か lint ルール。システム全体に及ぶ問題 -> 原則。
- **ループを閉じる。** 記録するだけで終わらせない。今適用するか、具体的な todo を作る。

**アンチパターン:**
- 記録せずに認めるだけ (「心に留めておく」は持続しない)
- 振り分けずに記録するだけ (あるべき lint ルールについての brain note は、その lint ルールが実装されない限り無駄になる)
- 一般化せずに直すだけ (1 箇所を直しつつ、繰り返されるパターンはそのまま残す)
