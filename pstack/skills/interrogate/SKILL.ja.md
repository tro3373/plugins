# Interrogate

設定された各モデルにつき 1 人のレビュワーを起動し、コード変更を敵対的にレビューさせる。敵対的なシグナルは割り当てたペルソナではなく、モデルの多様性から生まれる。成果物は統合された判定である。変更を自動適用しては**ならない**。

## ステップ 1、スコープ

文脈から何をレビューするかを特定する。

- ユーザが特定のファイルや差分を指しているなら、それを使う。
- フィーチャーブランチ上なら、変更セット全体を得るため `git diff main...HEAD` (または適切なベースブランチ) を実行する。
- ユーザのメッセージが最近の作業に言及しているなら、関連ファイルを集める。

差分またはファイル内容に、レビュワーがコードを理解するのに必要な周辺の文脈ファイルを添えてまとめる。

## ステップ 2、意図

レビュワーを起動する前に、ユーザのメッセージ、コミットメッセージ、PR の説明 (あれば)、コードから、意図を明確な 1 段落で述べる。意図が不確かなら、進める前にユーザに聞く。

## ステップ 3、レビュワーを起動する

Task ツールで 1 つのメッセージですべてのレビュワーを起動する。`~/.cursor/rules/pstack-models.mdc` の `interrogate reviewers` 行の 1 エントリにつき 1 レビュワーとし、エントリ数に合わせて Reviewer A、B、と続けてラベルを付ける。ルールまたはその行が無ければ表の既定値を使う。

| サブエージェント | 既定モデル |
|----------|---------------|
| Reviewer A | `claude-opus-5-5-xhigh` |
| Reviewer B | `grok-4.7-xhigh-fast` |

各レビュワーには `subagent_type: generalPurpose`、`readonly: true`、そして設定されたエントリ (設定行が無ければ表の既定値) を入れた `model` を与える。`auto` または `inherit-parent` のエントリでは `model` を省略し、そのレビュワーを親のモデルで動かす。

Task ツールが設定済みのエントリを拒否したら、そのファミリの表の既定値でそのレビュワーを動かし、その旨を述べる。ファミリは接頭辞で判定する: `claude-*`、および `cursor-grok-*` と `composer-*` を含む `grok-*`。拒否された `composer-*` のエントリは Reviewer B の既定値で動かす。ファミリが一致しなければ Reviewer A の既定値を使う。表の既定値も拒否されたら、そのエラーメッセージにある有効な slug から最も近い等価物 (同じファミリかつ同じ推論ティアを優先) を選んで起動し、既定表を更新する別の PR を開く。slug の問題でレビューを止めないこと。エイリアスのエントリを拒否された slug として扱ったり、どちらのフォールバックも適用したりしては決してならない。

`references/reviewer-prompt.md` を読み、全レビュワーに同じテンプレートを、述べた意図、差分またはファイル内容、`references/rubric.md` のルーブリック、`references/code-quality-review.md` のコード品質のレンズで埋めて渡す。各サブエージェントの reasoning level と fast / standard のスピードは、**poteto-mode** skill の Subagents セクションに従って仕事に合わせて選ぶ。

## ステップ 4、統合する

結果が返ってきたら、統一像を組み立てる。すべてのレビュワーの指摘をパースする。同じ問題を別の言い方で述べた指摘は統合し、どのモデルが挙げたかを記す。2 つ以上のモデルが独立に挙げた指摘は最高のシグナルだ。単一モデルのみの指摘も読むが、重みはそれ相応にする。不一致を記す。あるモデルが指摘し、別のモデルが明示的に反対しているなら、それは判定にとっての文脈だ。

## ステップ 5、リードの判断

あなたはリードレビュワーであり、実務的なシニアエンジニアであって、中立な集約器ではない。枠組みの全体は `references/lead-judgment.md` を読むこと。すべての指摘を 4 つのバケツのどれかに入れ、挙げたモデルと根拠の 1 行を添える。

- **Act on**。実際のゴールに照らして、正しさ、セキュリティ、保守性に影響する本物の問題。実際の PR ならブロックするもの。
- **Consider**。妥当だが、いま対処するコストに見合うか確信が持てないもの。ユーザの注意に値する。
- **Noted**。技術的には妥当だが、対処すべきものではない。文脈依存、時期尚早な最適化、または現段階では影響が小さいもの。
- **Dismissed**。間違い、些末、または文脈の欠落。理由を短く述べる。
