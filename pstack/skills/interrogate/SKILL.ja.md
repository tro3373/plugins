# Interrogate

設定された各モデルにつき 1 人のレビュワーを起動し、コード変更を敵対的にレビューさせる。各モデルは同じプロンプトとルーブリックを受け取る。敵対的なシグナルは割り当てたペルソナではなく、モデルの多様性から生まれる。

成果物は統合された判定である。変更を自動適用しては**ならない**。

## ステップ 1、スコープを決める

文脈から何をレビューするかを特定する。

- ユーザが特定のファイルや差分を指しているなら、それを使う
- フィーチャーブランチ上なら、変更セット全体を得るため `git diff main...HEAD` (または適切なベースブランチ) を実行する
- ユーザのメッセージが最近の作業に言及しているなら、関連ファイルを集める

差分 (またはファイル内容) に加えて、レビュワーがコードを理解するのに必要な周辺の文脈ファイルをまとめる。

## ステップ 2、意図を述べる

レビュワーを起動する前に、意図を明示的に述べる。次から導く。

- ユーザのメッセージ
- コミットメッセージ
- PR の説明 (あれば)
- コード自体

明確な 1 段落を書く。意図が不確かなら、進める前にユーザに聞く。

## ステップ 3、レビュワーを起動する

Task ツールを使い、1 つのメッセージですべてのレビュワーを起動する。`~/.cursor/rules/pstack-models.mdc` の `interrogate reviewers` 行を使い、1 エントリにつき 1 レビュワーとし、下の Reviewer A/B/C のラベルを設定されたエントリ数に合わせて増減させる。ルールまたはその行が無ければ表の既定値を使う。

| サブエージェント | 既定モデル |
|----------|---------------|
| Reviewer A | `claude-opus-5-5-max` |
| Reviewer B | `gpt-5.6-sol-max` |
| Reviewer C | `grok-4.7-xhigh-fast` |

各レビュワーについて:
- `subagent_type`: `generalPurpose`
- `model`: 設定された `interrogate reviewers` のエントリ、設定行が無ければ表の既定値。`auto` または `inherit-parent` のエントリでは `model` を省略し、そのレビュワーを親のモデルで動かす。
- `readonly`: `true`

Task ツールが設定済みのエントリを拒否したら、そのファミリの表の既定値でそのレビュワーを動かし、その旨を述べる。ファミリは接頭辞で判定する: `claude-*`、`gpt-*`、`grok-*`。ファミリが一致しなければ Reviewer A の既定値を使う。表の既定値も拒否されたら、Task ツールのエラーメッセージにある有効な slug を確認し、最も近い等価物を選び (同じファミリの最高推論ティアを優先)、それで起動し、既定表を更新する別の PR を開く。slug の問題でレビューを止めないこと。エイリアスのエントリを拒否された slug として扱ったり、どちらのフォールバックも適用したりしては決してならない。

`references/reviewer-prompt.md` を読み、テンプレートを次で埋める。
1. 述べた意図
2. 差分またはファイル内容
3. `references/rubric.md` のレビュールーブリック
4. `references/code-quality-review.md` のコード品質のレンズ

同じ埋め終えたテンプレートを全レビュワーに渡すので、すべてのモデルがコード品質のレンズを適用する。

## ステップ 4、統合する

結果が返ってきたら、統一像を組み立てる。

1. レビュワーからの**すべての指摘をパースする**
2. **合意を特定する**。2 つ以上のモデルが独立に挙げた指摘は最高のシグナルだ。
3. **単一モデルのみの指摘を特定する**。読む価値はあるが、重みはそれ相応にする。
4. **重複を除去する**。異なるモデルが同じ問題を別の言い方で述べることがある。それらを統合し、どのモデルが挙げたかを記す。
5. **不一致を記す**。あるモデルが指摘し、別のモデルが明示的に反対しているなら、それは判定にとって有用な文脈だ。

## ステップ 5、リードの判断

あなたはリードレビュワーであり、実務的なシニアエンジニアであって、中立な集約器ではない。

枠組みの全体は `references/lead-judgment.md` を読むこと。

すべての指摘を次のバケツで分類する。

- **Act on**。実際のゴールに照らして、正しさ、セキュリティ、保守性に影響する本物の問題。実際の PR ならブロックするもの。
- **Consider**。妥当な指摘だが、いま対処するコストに見合うか確信が持てないもの。ユーザの注意に値する。
- **Noted**。技術的には妥当だが、対処すべきものではない。文脈依存、時期尚早な最適化、または現段階では影響が小さいもの。
- **Dismissed**。間違い、些末、または文脈の欠落。理由を短く述べる。

各指摘について次を含める。
- どのモデルが挙げたか
- 分類 (act on / consider / noted / dismissed)
- その分類の根拠を 1 行で

## 出力形式

判定はこの構造で提示する。

### Intent
> [ステップ 2 で述べた意図の段落]

### Reviewers
- Reviewer [ラベル]: [モデル名]、[N 件の指摘] (レビュワーごとに 1 行)

### Act On
[対処すべき指摘。各項目について、説明、どのモデルが挙げたか、なぜ重要か。]

### Consider
[検討に値する指摘。各項目について、説明、どのモデルが挙げたか、関わるトレードオフ。]

### Noted
[妥当だが優先度が低いもの。短い一覧。]

### Dismissed
[却下した指摘と短い根拠。]

### Agreement Map
[モデルはどこで一致し、どこで分かれたか。そして一致/不一致のパターンは何を示すか。]
