# レビュールーブリック

関連するレンズを通してレビューする。すべてのレンズがすべての変更に当てはまるわけではない。判断して使う。

## 正しさ

コードは、意図が言っているとおりのことを実際にやっているか。

- エッジケース: 空入力、nil/undefined、境界値、並行アクセス
- エラー処理: エラーは捕捉され、伝播されているか、それとも黙って握り潰されているか
- off-by-one、型の暗黙変換、整数オーバーフロー、文字列エンコーディング
- 状態管理: 競合状態、古いクロージャ、ぶら下がった参照
- ハッピーパスは動くか。異常系は動くか
- 冪等性: この操作が 2 回走ったら、あるいは前回の実行が途中でクラッシュしていたらどうなるか。答えが「どんな状態が残っていたかによる」なら、突き合わせの手順が欠けている。
- 並行性: 複数のアクターが同じ可変状態 (ファイル、ブランチ、共有データ) に触れうるなら、そのアクセスは構造的に直列化されているか (ロック、逐次的なフェーズ、排他的な所有)、それとも守られない慣習によるものか。

バグの可能性を見つけたら、実行経路を辿る。「これは nil になりうる」とフラグを立てるだけにしない。nil になる呼び出し連鎖を示す。

## 根本原因か症状か

コードは実際の問題を直しているのか、それとも症状を糊塗しているのか。

これに答えるには、変更されたファイルの外を見る必要がしばしばある。周辺のコード (呼び出し元、呼び出し先、型定義、兄弟モジュール) を読み、その変更が置かれているアーキテクチャを理解する。使えるツール (Read、Grep、Glob) で探索する。呼び出し連鎖を辿る。型を読む。変更が適切な層に手を入れているかを判断する前に、そのコードがなぜ存在するかを理解する。

- より深い不変条件の違反を覆い隠すガード節
- 壊れた契約を隠すリトライ処理
- モデリングの誤りを黙らせる型キャスト
- 回避策を見つけたら問う: なぜその回避策が必要なのか。適切な修正はどのようなものか。
- モジュール A の修正が、本当はモジュール B の契約の修正であるべきもの
- 構造にできるところを指示で済ませているもの: 修正が「X をするな」というコメントや、誰かが覚えておかねばならない慣習であるなら、代わりに型の制約、lint ルール、または誤りを不可能にする実行時チェックにできないかを問う

## 構造的な健全性

コードは、それが属するシステムにうまく収まっているか。

- 境界の規律: バリデーションはシステム境界にあるか、それともビジネスロジック中に散らばっているか。データはシステムに入る場所で一度検証し、内部では信頼する。
- 抽象度: コードが高レベルのオーケストレーションと低レベルの詳細を混ぜていないか。
- 結合: この変更は、将来の変更を難しくする依存を持ち込んでいないか。
- データモデルの適合: データ構造は実際のアクセスパターンに合っているか。正しい構造は下流のコードを自明にする。誤った構造は至るところで抵抗する。
- 後付けか統合されているか: 変更は既存の設計に貼り付けられたのか、それとも設計が最初からそれを織り込んでいたかのように読めるか。新しい要件が最初から分かっていたら、コードはこの形になっていたか。
- レガシーな二重経路: 変更は古い API を生かしたまま新しい API を導入していないか。外部の利用者がいないなら、呼び出し元を移行し、同じ波で古い経路を削除する。恒久化する互換レイヤを残さないこと。

抽象化が無いことを理由に単純なコードを減点しない。時期尚早な抽象化は重複より悪い。

## 検証

このコードが動くと、読んで分かるか。

- テストはあるか。それは挙動をテストしているか、実装の詳細をテストしているか。
- リグレッションを捕まえるアサーション/不変条件はあるか。
- バグ修正なら、そのバグに対するテストはあるか。
- 統合の境界に触れるなら、経路全体がテストされているか。
- 代理ではなく本物を確認する。実際の値を読む代わりに、ファイルの mtime やキャッシュされた状態で生存確認をしているなら、それは検証のギャップだ。
- 委譲された作業や非同期の作業について: コードは実際の出力成果物を検証しているか、それとも自己申告と要約を信じているか。

## 複雑さの予算

その複雑さは、コードが達成することに見合っているか。

- 正しさや明快さを失わずにもっと単純にできるコード
- 呼び出し箇所が 1 つしかない抽象化
- まだ存在しないケースのための設定やパラメータ化
- デッドコード、未使用の import、痕跡だけのパラメータ
- 過剰設計: 現在の呼び出し元が無い「念のため」のコード経路
- もはや不要な移行期の安定性のために生かされている、古い互換経路。移行が済んだなら足場は削除する
- ユーザ体験はその複雑さに見合うか。すべての機能、コントロール、オプションはその存在を正当化しなければならない。中途半端な機能は、無い機能より悪い。

単純な方が良い。ただし単純だと間違いになる場合を除く。3 行の重複は時期尚早な抽象化に勝る。

## セキュリティ

セキュリティ上の指摘ごとに、入力経路をコードを通して辿り、それを示す。

- サニタイズ無しに危険なシンク (SQL、シェル、eval、innerHTML) へ流れるユーザ入力
- 新しいエンドポイントにおける認証/認可の抜け
- コード、ログ、エラーメッセージ中のシークレット
- セキュリティ上重要な経路での TOCTOU (time-of-check-time-of-use)
