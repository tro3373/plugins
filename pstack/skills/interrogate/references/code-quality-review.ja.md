# Code Quality Review

各レビュワーは、ルーブリックに加えてこのコード品質のレンズを適用する。実装品質、保守性、抽象の質、コードベースの健全性に焦点を当てた厳格な基準である。

何よりもまず、コード構造について野心的であること。局所的な片付けを指摘するだけで終わってはならない。「code judo」の一手、すなわち挙動を保ちながら実装を劇的にシンプルに、小さく、直接的に、エレガントにする再構成を積極的に探すこと。

## Core Prompt

このベースラインから始める:

> 現在のブランチの変更に対して、深いコード品質の監査を行う。
> 挙動に影響を与えずにコード品質を有意味に改善するため、変更の構造化 / 実装方法を考え直す。
> 抽象とモジュール性を改善し、スパゲッティコードを減らし、簡潔さと可読性を高めるよう取り組む。
> 野心的であること。コードベースの一部を再構成することで実装を改善する明確な道筋があるなら、それをやる。
> 極めて徹底的かつ厳密に。二度測って一度切る。

## 観点

各観点は 1 度だけ述べる。関連するものを適用すること。

0. **構造的な単純化について野心的であること。** 「もう少し綺麗にできる」で止まってはならない。分岐、ヘルパー、モード、条件式、レイヤーがまるごと消えるような再定義を探す。「code judo」の一手はしばしば存在すると想定する。それは既存のアーキテクチャをより効果的に使い、変更を劇的にシンプルにする。複雑さを並べ替えるのではなく削除できるなら、強くそれを推す。

1. **PR がファイルを 1k 行未満から 1k 行超へ押し上げることを、極めて強い理由なしに許してはならない。** これを強い臭いとして扱う。ヘルパー、サブコンポーネント、モジュールの抽出を選ぶ。diff がその閾値を跨ぐなら、先にコードを分解すべきかを問う。免除するのは、結果のファイルが明確に整理されたままである、説得力ある構造上の理由がある場合だけである。

2. **既存コードでのスパゲッティの成長を許してはならない。** 無関係なフローに差し込まれた、その場しのぎの新しい条件式、散らばった特殊ケース、単発の分岐を疑うこと。「あちこちの変な if 文」をスタイル上の些事ではなく設計の問題として扱う。既存の経路をもつれさせるのではなく、専用のヘルパー、ステートマシン、モジュールにロジックを押し込むことを選ぶ。

3. **動くコードをただ受け入れるのではなく、設計を綺麗にする方に寄せる。** 挙動を同じに保ったまま構造が有意味に綺麗になるなら、綺麗な方を推す。同じ複雑さをあちこちに撒き散らすリファクタよりも、可動部品を減らす単純化を選ぶ。

4. **ハックや魔法めいたコードよりも、直接的で退屈で保守しやすいコードを選ぶ。** 脆く、その場しのぎで、「魔法」的な挙動を問題として扱う。単純なデータ形状の前提を隠す汎用的な仕組みには懐疑的であること。明快さを買わずに間接性だけを足す薄い抽象、恒等ラッパー、パススルーのヘルパーを指摘する。

5. **型と境界の清潔さが保守性に影響するなら、そこを突く。** より明確な型境界があり得るのに使われている不要なオプショナル性、`unknown`、`any`、キャスト過多のコードを問う。緩い形のその場しのぎのオブジェクトより、明示的に型付けされたモデルを選ぶ。ある分岐が不明瞭な不変条件を覆い隠すために黙ったフォールバックに頼っているなら、境界を明示すべきかを問う。

6. **ロジックを正典のレイヤーに置き、既存のヘルパーを再利用する。** 機能固有のロジックが共有経路に漏れていること、実装詳細が API を通じて漏れていることを指摘する。独自の単発ものより既存の正典的ユーティリティを選ぶ。ドリフトを追認するのではなく、コードを正しいパッケージ・サービス・モジュールへ寄せる。

7. **より綺麗な構造が明らかなときは、不要な逐次オーケストレーションと非アトミックな更新を設計の臭いとして扱う。** 独立した作業が理由なく直列化されているなら、並列に走らせるべきかを問う。関連する更新が状態を中途半端に適用したまま終わり得るなら、よりアトミックな構造を推す。マイクロ最適化に偏り過ぎてはならないが、コードを脆くする回避可能なオーケストレーションの複雑さは指摘する。

## 出力の期待

まず構造的なコード品質のリグレッションと見逃された単純化を、次にスパゲッティと分岐の複雑さを、次に境界・型・ファイルサイズの懸念を、次に細かなモジュール性と可読性の問題を優先する。

## 承認のバー

挙動が正しそうだというだけで承認してはならない。作者が正当化できない限り、次を推定上のブロッカーとして扱う: code judo の一手で削除できる偶発的な複雑さを PR が大量に残している。ファイルを 1000 行未満から 1000 行超へ押し上げる。既存のフローをもつれさせるその場しのぎの分岐を足す。共有コード全体に機能のチェックを撒き散らす。不要な抽象、ラッパー、キャスト過多の契約を足す。既存のヘルパーを重複させる、または明確な正典的置き場があるのにロジックを誤ったレイヤーに置く。これらの条件が満たされていないなら、明示的で実行可能なフィードバックを残し、より綺麗な分解を推す。

## レビューのトーン

品質について直接的に、真剣に、要求水準高く臨む。無礼であってはならないが、重大な保守性の問題を穏やかな提案に薄めてもならない。コードがコードベースを散らかしているなら、そう言う。実装が明白で劇的な単純化を見逃しているなら、それも言う。本当の問題が構造的であるときに「これは名前を変えるといいかも」で満足してはならない。
