### Bug fix

**このタスクはお前の担当だ。プランし、レビューし、検証する。** 調査と修正はサブエージェントへ委譲し、自分はリードに留まる。

科学的にやれ。出荷される行はすべて実行時の証拠に遡れること。「効くかもしれない」念のための二重対策は仮説であって修正ではない。出荷しない。証拠が仮説を否定したら、それが動機だったものを差し戻す。証拠が正当化する最小の変更だけを出荷し、それ以上はやらない。

1. 制御 skill を通じて、該当するサーフェスで自分自身が再現する (Non-negotiables)。ユーザに再現を頼めと書かれたデバッグや計測のプロトコルがあっても関係ない。制御サーフェスが対象に届かない具体的な理由を述べたうえで、かつ限界まで動かした後にのみ、ユーザに聞く。直接再現しないなら、トリガーを合成し、条件を絞り、あるいは発火するまで計測を入れる。
2. 原因を二分探索する。候補となる仮説を立て、1 つが生き残るまで潰していく。仮説の種は、影響を受けるサブシステムに対する `how` と、リグレッションの履歴については **why** skill から得る。各パスで、残る問題空間を最も大きく削る分割を取り、実行時の証拠を得て、消去する。プログラムの状態が不明瞭なときは、計測やログを足し、コードが走るのに合わせて読む。推測してはならない。長引く、あるいは手強い探索は Cursor の `/loop` コマンドで駆動する。ステップ 3 の architect/interrogate のファンアウトの前に、生き残った*メカニズム*を実行時の証拠で確認する。
3. 修正をプランする。関数の境界をまたぐなら、先に `architect`。実装は、設定された bug-fix 用モデル (既定は `grok-4.7-xhigh-fast`) のサブエージェントへ、具体的なスコープを与えて委譲する。
4. 同じサーフェスで検証する。元の再現手順が通るようになっていること。「決定的でない」や別サーフェスは合格ではない。それはフラグを立てる。ユニットテストは分岐の挙動を示すのであって、バグの不在を示すのではない。
5. git 履歴上、失敗する再現が修正より前に入るようコミットを並べる。差分が物語を語る。バグに安価なローカルテストの経路があるときの、失敗するテストを先にするリズムは **tdd** skill を参照。テストが高価、統合寄り、または不明瞭なときは飛ばす。
   これは正典的な **sequence-verifiable-units** の principle skill であり、失敗するテストが先、修正がその上だ。
6. **Opening a PR** を実行する。

**返信:** 何が壊れていたか、根本原因、修正、どう検証したか。失敗してから通るまでの再現出力を逐語で貼る。
