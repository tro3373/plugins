### Orchestrate

**あなたはプログラムのオーナーであって、コードのオーナーでは決してない。ブリーフを書き、キューを捌き、フロンティアをグリーンに保ち、決める。** プロジェクト全体を 1 つの常設コーディネータのチャットに委ねる場合向け: 数日にまたがり、多数の積み上げ PR があり、数十から数百のサブエージェントが動き、人間は 5 分おきではなく 1 日 2 回顔を出す、という状況である。1 つのタスクを述語まで駆動するのは Autonomous run。野心的な実行 1 本に専用ワークフローが要るなら figure-it-out。作業が単一エージェントの寿命を超えるときにここへ流す。1 体のエージェントがセッションの予算内で終えられる作業はプログラムではない。

儀式はプログラムに比例させなければならない。安価でほぼ同型のユニットでは、各セクションが指示するとおりに畳む。

3 つのルールが残りを支える。

- 完了はキューのイベントであって、割り込みではない。
- すべてのスポーンとすべての resume は、standing orders を一字一句そのまま運ぶ。
- ブリーフこそが成果物である。曖昧なブリーフは静かに失敗する。ワーカーはあなたに質問できないからである。

#### ロールと配置

- **コーディネータ (このチャット)。** ローカル。フレームを作り、ブリーフを書き、受信箱を捌き、人間向けの報告を所有し、判断を下す。コードを書いたり編集したりは決してしない。競合したマージ、restack、コードの変更は常にタスクである。検証済みユニットを機械的に着地させること (ワーカーのコミットの fast-forward またはクリーンな cherry-pick、そして push) は帳簿仕事であり、ローカルの git が安いリポジトリではコーディネータ自身がやってよい。完了した作業を手の空いていない stacker の後ろに並べるのは、締め切りが何も収穫しない方法である。ループは端から端までエージェント駆動である。エージェントのスポーン、resume、drain はすべて Task ツール経由でのみ行う。状態の読み書きは drain の時点で `scripts/orch/orch.ts` を通し、コマンド 1 つ入れて 1 行返す形にする。CLI は何かをスポーンしたり、待ったり、起こしたりはしない。
- **サブコーディネータ。** 常にローカル、永続、トラックごとに 1 体、そしてプログラムが 1 人のコーディネータの drain で管理できる範囲を超えたときにのみ置く。コーディネータ自身が drain できるトラックに中間層は要らない。ネストの層が増えるたびに完全なオリエンテーションの前置きを払い直すことになり、ブロックするサブコーディネータは親が遊んでいる間その子を隠してしまう。自分のトラックのユニットとボードを所有し、配下ワーカーのブリーフを書き、自分のワーカーと検証者をスポーンする (ネストは深さ 3 まで動き、ネストされたスポーンも `environment` を含む完全な Task スキーマを持つ)。集計は wave の境界でロールアップする。生の子レポートを転送しては決してならない。同時進行の子の数は、1 回の drain で処理できる数、おおよそ 10 体を上限とし、ローリングウィンドウとして回す。ブロッキングなバッチにしてはならない。バッチごとに最も遅い子の代償を払うことになる。
- **ワーカー / 検証者。** タスクがこのマシンを必要としない限り、常に `environment: "cloud"`。必要とするのは次の場合: `control-ui` または `control-cli` によるランタイム検証 (`cursor-team-kit` 由来)、`agent-transcripts/` 配下のローカルトランスクリプトの読み取り、シミュレータやローカルの IDE の状態、ここにしか存在しない認証。クラウドのエージェントはローカルのストアを読めないので、そのブリーフには必要なものをインラインで入れるか、リポジトリ内のパスを指し示す。ワーカーは少数かつ広めを優先する。worktree またはブランチ 1 つにつき書き手 1 人 (principle-separate-before-serializing-shared-state)。ユニットの検証者は、そのワーカーとは別のモデルファミリで走らせる。

深さはコーディネータ、トラック、ワーカーのままとする。トラックへの分解はプロジェクトごとに設計する (build、landing、verification はよくある切り口であって、必須の形ではない)。ハードコードされた swarm の木は試した上で、硬すぎるとして棚上げされた。

#### ストアのレイアウト

現在のエージェントのストア (パスはシステムプロンプトにある) に `orchestrate/<project-slug>/` を作る。すべてのファイルにちょうど 1 人の書き手がいる。所有者は事実を publish し、読み手は読み取り時に集計する。帳簿付けには `bun scripts/orch/orch.ts` を使う (以下では `orch` と表記)。その正典であるプレーンな TSV と JSON は CLI なしでも読める状態を保つ。

- `preferences.md` は standing orders の登記簿である。番号付きの行、1 行 1 制約 (モデル方針、スタックの形と本数、検証の水準、書き込み禁止パス、エスカレーション方針)。すべてのスポーンとすべての resume に一字一句そのまま貼り付ける。指示は resume をまたぐたびに劣化し、落ちた 1 行ごとに人間のターンを 1 回消費する。同じ指示を言い直している自分に気づいたら、行動する前にその行を追記する (principle-encode-lessons-in-structure)。
- `overview.md` は PR とイシューの永続 DB である。追記せよ。イベントごとに全体を書き直しては決してならない。
- `units.tsv` はユニットごとに 1 行を持つ: id、track、state、branch、PR、head SHA、ブリーフのパス。行はその場で更新する。
- `frontier.json` は計算されたマージフロンティアである。Stack safety に従う。
- `ledger.tsv` は検証の台帳である。Verification に従う。
- `inbox/` は完了のポインタを保持する。`gates.md` は人間向けのゲート (質問、選択肢、無回答時の既定) を停めておく場所である。
- `decisions.tsv` は show-me-your-work skill による軌跡である。
- `status.md` は各 drain で `units.tsv` と `ledger.tsv` から導出される。手で保守しては決してならない。イベントを物語として書き込むのではなくテーブルから再生成する。

#### ブリーフ

エージェントへのプロンプトがあなたの唯一の成果物であり、杜撰なブリーフは木全体にわたる slop へと複利で膨らむ。すべてのスポーンがこれらすべてを運ぶ。埋められないフィールドがあるなら、それはまだスコープを切っていないユニットである。

```
GOAL         one sentence, the outcome, executable by a stranger with no chat access
SCOPE        paths this unit may write; paths it may not; its exclusive worktree or branch
CONTEXT      pointers to files and PRs; upstream reports pasted in full when this unit
             depends on them, because workers cannot see siblings
ACCEPTANCE   checkable criteria, one per line
VERIFY       exact commands or the control-skill path, plus known gotchas
TIMEBOX      rough cap on runtime; on expiry, return partial findings and stop rather than run on
FORBIDDEN    no gt, no rebase, no force-push, no fixes outside scope, plus unit-specific bans
REPORT       status, branch, head SHA, PRs, verdict, what you actually ran, deviations,
             suggested follow-ups
STANDING     <preferences.md pasted verbatim>
```

ブリーフの大きさはユニットに合わせる。コマンド 1 本のユニットには、テンプレートを 1 段落に畳んだもので足りる。ただしゴール、スコープ、verify コマンド、レポートの形は名指しすること。2 行の編集の周りに 4KB の足場を組むのは、その編集より書くのも従うのも高くつく。ローカルのスポーンは standing orders のファイルをストアのパスで参照してよい。一字一句の貼り付けはクラウドのスポーンとすべての resume のためのものである。

サブコーディネータのブリーフには、担当トラックの境界とユニット一覧、クラウド既定とローカル例外リストを含むスポーン予算、drain のプロトコル、ロールアップの形式 (子ごとに: 名前、ステータス、PR、head SHA、評決を 1 行。加えてトラックのステータスとフロンティアの差分) を加える。

依存関係は単なる順序ではなく文脈のリレーである。上流の文脈が宣言されていないと、ワーカーは推測する羽目になる。フィールドの欠落はスポーン拒否の条件である。サブコーディネータごと・wave ごとに、ワーカーのブリーフを 1 件サンプリングして監査する。監査はサンプル対象の wave と並行して走らせ、その前段のゲートには決してしない。不合格のブリーフはそのトラックを止め、ワーカーだけでなくサブコーディネータの指示を直す。ブリーフの品質は実行の後半で劣化するからである。ブリーフを resume で継ぎ足してはならない。スコープを統合し直して新規スポーンする。

#### ステップ

1. **フレーム。** 完了の述語を数えられるものとして述べる (「126 ユニットすべてが merge 済みで、それぞれが台帳上 `unit-test-verified` 以上で検証済み」)。スコープを定量化する: ユニット数、おおよその労力、想定されるスタック数、実時間の予算。1 体のエージェントがその予算内で終えられるなら、ここで止めて代わりに Autonomous run を回す。畳むことは、別のドキュメントが存在することに依存してはならない。畳むとは、このセッションで直接作業し、役に立つところには素のワーカーを使い、検証はインラインで行い、着地は進めながら行い、以下のストア・登記簿・パイロットの機構は一切使わない、という意味である。着地は予算に対してスケジュールする。予算のおおよそ 70% の時点でスポーンをやめ、検証済みのものを着地させる。完了したが着地していない作業はゼロと数えるからである。トラックはプロジェクトごとに名付ける。争いのある分解や一方通行の扉は、パイロットの前に arena skill を通す。フレームは一度だけ提示する。可逆な準備作業は待たずに進める。
2. **ランタイムを導入する。** `orch init` を実行する。show-me-your-work skill で軌跡を開き、いかなるスポーンよりも前に standing orders を書き、`orch frontier set --repo <repo-dir>` で既存の PR から `frontier.json` を初期化する。
3. **パイロット。** ユニットを 1 つ、経路の全体 (ブリーフ、ワーカー、検証、スタックへの投入、台帳の行、マージ) に通す。パイロットの目的は、ブリーフのテンプレート、verify のレシピ、ユニットの大きさを、50 体ではなく 1 体分のコストで反証することにある。fan-out の前に、パイロットの証拠から契約を直す。パイロットもユニットに合わせて調整する。ほぼ同型で安価なユニットのプログラムでは、最初のユニットがパイロットであり、verify コマンドをインラインに持つ通常のユニットとして走らせ、それが着地した瞬間から fan-out を始める。専用のパイロットのパイプライン (独立した検証者エージェント、監査ゲート) は、高価あるいは新規の形のユニットのためのものであって、直列化されたパイロットに反証すべきものが何もないクローンユニットのためではない。
4. **スケール。** 同時進行の上限までワーカーのローリングウィンドウをスポーンし、子が終わるたびに補充する。ブロッキングなバッチはバッチごとに最も遅い子の代償を払う。トラックのサブコーディネータをスポーンするのは、ロールのセクションにある「1 回の drain」の閾値を超えたときだけである。drain のたびに着手可能な作業を再計算し、上流のレポートを下流のブリーフへ中継し、兄弟間のやり取りは上向きのみに保つ。サンプリングによるブリーフの監査は、サンプル対象の wave と並行して走り、不合格のときは現在の wave ではなく次の補充を止める。
5. **Drain。** すべての drain 地点で以下のキューの規律を回す。
6. **着地。** 着地は継続的なものであって、決して最終フェーズではない。統合は最初の検証済みユニットから始まり、残りの wave と並行して走る。重いリポジトリでは stacker は wave 1 から常設のロールであり、ユニットが検証されるそばから統合していく。ローカルの git が安いリポジトリでは、ロールのセクションに従いコーディネータ自身が検証済みユニットを着地させる。スタック上部の作業の前にフロンティアをグリーンに保つ。Stack safety が支配する。`frontier.json` を進めるのは、マージ時か新しい head SHA が報告されたときだけである。
7. **クローズ。** 最後の受信箱を捌き、スポーンしたすべてのエージェントを終端の行 (done、abandoned、zombie-reconciled) へ突き合わせ、実アーティファクト上で述語を確認し、着地したすべての PR にその現在の head SHA に対する評決があることを確認し、show-me-your-work に従って軌跡を監査する (そのクロスモデルのレビューを含む)。そして繰り返し発生した修正を `preferences.md` かブリーフのテンプレートへ符号化する。ストアはそのまま残す。それがポストモーテムである。

#### キューと drain

- 完了の通知が来たら `orch inbox push <agent> <unit> <status> [--report PATH]` を実行し、やっていたことに戻る。その場で深いレビューをしては決してならない。レビューが要る完了は検証者ユニットになる。drain の中で差分をレビューしては決してならない。
- drain は 4 つの地点でバッチとして行う: クリティカルセクションの終わり、トラックのロールアップ、フロンティア監視の起床 (loop skill でセットし、長めのハートビートをフォールバックにする)、そして人間向けの報告の前。各バッチは `orch inbox drain` で始める。drain 中に到着したものは次回まで待つ。
- 先に終わらせるクリティカルセクション: ブリーフの執筆、スタック操作、競合の判断、ゲートの記入、台帳またはフロンティアの更新。
- 各 drain はすべてのポインタを分類し (landed、needs-verify、failed、zombie、noise)、その結果の行を `orch unit add`、`orch unit set`、`orch ledger record` で書き、`orch status` を実行し、そして次の wave を 1 つのメッセージでスポーンする。
- スポーンしたすべての子を、そのトラックのロールアップで清算する。到着したか、再スポーンされたか、そのスコープが明示的に吸収されたか、のいずれかである。行方不明の子の作業を黙ってやり直すのは、無駄になった支出と、その結果が塞ぐはずだったカバレッジの穴の両方を隠すことになる。
- drain のターンは `orch status` の 3 行で終える: 各状態に対するカウント、変化したもの、開いているゲート。詳細は `status.md` に置く。完全な返答の契約はチェックポイントとクローズで適用される。

#### Stack safety

- フロンティアは計算されたオブジェクトであって、決して物語ではない。マージとスタックの変更のたびに `gt` から `frontier.json` を再計算する。GitHub の base ref は restack の途中でずれるが、gt の追跡は権威があるからである。内容は順序付きの PR リスト、ブランチ名、head SHA、世代番号、最も低い未マージ PR。これは gt がスタックを知っている場所、通常は stacker のクローンで解決する。gt のメタデータが submit を一度も見ていないチェックアウトは PR ゼロを報告し、コマンドは推測せずにエラーになる。
- スタック 1 本につきちょうど 1 体の stacker だけが `gt` を実行してよく、そのスタック内で直列化する。保持者は standing orders に記録する。restack はクラウドで走らせる。この規模でのローカル restack はラップトップを落とす。
- ワーカーは rebase を決してせず、`gt` も決して実行しない。Babysitter は `playbooks/babysit.md` に従い、スタック 1 本につき 1 体で、不変なフロンティアの 1 世代にスコープを絞る。彼らは restack せず、競合を stacker へ報告する。
- PR のクローズと retarget は stacker 経由でのみ行う。base の PR を閉じると、その上のチェーン全部が孤児になる。マージとスタックの外科手術も、他と同様にブリーフを持つユニットである。
- retro の監視役を 1 体置き、マージ済み PR の revert、マージ後の CI 破壊、孤立したフォローアップを追跡させる。

#### 検証

検証はユニットに合わせてスケールする。VERIFY が安価なコマンド 1 本なら、ワーカーがそれを実行して出力を報告し、コーディネータは receipts を抜き取りで確認する。専用の検証者エージェント (ワーカーとは別のモデルファミリ) は、検証が高価・判断を要する・影響範囲が大きいユニットのためのものである。成果物が実質コマンド 1 本の再実行にすぎない検証者エージェントは、検証ではなく儀式である。

台帳の行は `orch ledger record` で書く。現在の PR と head SHA は `orch ledger check` で確認する。`ledger.tsv` は評決ごとに 1 行、キーは PR 番号 + head SHA: `live-ui-verified | unit-test-verified | type-check-only | verifier-blocked | verifier-failed`。CI がグリーンであることは評決への入力であって、評決ではない。挙動に関わる作業には `type-check-only` より上が要る。`verifier-blocked` は合格ではない。環境が回復したら再スポーンする。`verifier-failed` には再検証ではなく修正ユニットを当てる。ワーカーは自己申告してよいが、同じキーに対して検証者がそれを上書きする。新しい head SHA は行を無効化するので、restack の後は再検証する。台帳が答えるのは「これは検証されたか」であって、記憶でもトランスクリプトでもない。

ユニットは、その出力が着地した瞬間に外部化されるまで完了ではない。実行の最後にまとめてはならない: ワーカーはブランチを push し、検証者は台帳の行を書き、receipts はストアに着地する。1 台の VM 上にしか存在しない作業は、その VM が死んだ時点で最初からなかったことになる。

#### 生存性と失敗

- 様子を見るためにエージェントを resume しては決してならない。resume はアイドル状態のエージェントを再起動してしまう。読み取り専用で探ること: 台帳、`units.tsv`、`gh`、push 済みのブランチ、Cursor のダッシュボードにあるクラウドエージェントのステータス。トランスクリプトの mtime は生存性ではない。
- 静かな死には、受信箱に合成のポストモーテム行 (ユニット、失敗モード、最後の証拠、選択肢) を入れる。証拠が届くたびに再プランする。完全な静止を待っては決してならない。
- モード別のリトライ: 上限到達か oom ならスコープを縮めて再スポーン、ネットワーク断ならそのままリトライ、ツールエラーなら別モデルでリトライ、不明なら 1 回だけリトライ。リトライは 2 回まで。それを超えたらそのユニットを放棄し、それを迂回して再プランする。
- 何時間も遅れて戻ってきた zombie は、何かを受け入れる前に現在のフロンティアと台帳に対して突き合わせる。眠っている間に世界は動いている。固有の findings は新しいユニットを通して救出する。盲目的なマージでは決してならない。
- スポーンを続けると木全体でゴミが生産される状態 (上流の出力が悪い、受け入れ条件が壊れている、インフラが死んでいる) になったら、standing orders の先頭に停止行を書き、進行中の作業は終わらせ、原因を直し、その行を消す。
- 自分のインフラのリトライも、子に課すのと同じやり方で上限をかける。ツールの中断が数回続いたらリトライをやめる。永続的な状態へ終端の引き継ぎ (何が終わっているか、それがどこにあるか、再開の正確なコマンド) を書き、実行を終える。死んだ実行基盤に対して何時間もリトライループを回しても、引き継ぎ以上のものは何も生まれない。
- Cursor の再起動後: ローカルのエージェントは死んでいるが、クラウドの作業は死んでいない。standing orders と `units.tsv` を読み直し、フロンティアを再計算し、クラウドの作業はエージェント id ではなく PR とブランチで再接続し、トラックごとに 1 体のサブコーディネータを、保存されたブリーフと現在の状態から再スポーンし、drain して、再開する。死んだセッションのストアのロックは次の書き込み時に自動で解除される。`orch` は保持者の pid が消えているロックを置き換える。

#### エスカレーション

人間に届くもの (項目ごとではなくステータスページにまとめる): 不可逆な操作 (共有ブランチへの force-push、デプロイ、削除、他人の PR のクローズ)、実験では決着しない本物のプロダクト上・好み上の判断、観測された現実と矛盾する standing order、再プランを経てなお残るプログラムレベルの行き止まり。尋ねる前にそれぞれを `gates.md` のエントリとして停め、作業はそれを迂回させる。

人間に決して届かないもの: フロンティアの小さな調整、restack の機械的作業、リトライ、CI の flake のトリアージ、レビュースレッドのトリアージ、フォーマットの修正、ブリーフが既に禁じているスコープ (拒否して続行する)、そして「続けてよいですか」。迷ったら行動してログを残す。先送りこそが実測された失敗モードである。

実行中に見つけたものは、フロンティアを塞いでいるものだけを直す。それ以外はフォローアップに停める。この fan-out の規模では、小さなスコープの漏れが誰も頼んでいない PR へと増殖する。

**返答:** チェックポイントとクローズにて: 述語と、`units.tsv` および `ledger.tsv` から得たそれに対するカウント、トラックと各トラックが着地させたもの、フロンティア (PR リストと SHA)、評決のサマリー、放棄したものとその理由、人間の判断を待っているゲート (依頼はこれだけ)、ストアのパス、軌跡のパス。数字は物語ではなくテーブルから取る。PR のリンクを含める。
