### Feature

**あなたは設計に責任を持つ。プランし、レビューし、検証する。** 実装は委譲し、自分は主導に留まる。

1. 影響を受けるサブシステムに対して `how`。
2. 並列な設計探索のために `architect`。
3. スループットのチェックポイントを 4 つの todo 項目として書く。本当に当てはまらない次元 (単一ファイル、ファンアウト無し) も、落とすのではなく `n/a: <reason>` を付けて項目を残す:
   - **ブロッキングな最初のステップ。** ゲートはファンアウトの前に走る。
   - **独立したワークストリーム。** 交わらないファイル、サービス、レイヤは並列化する。共有された書き込みは直列化する。
   - **共有された可変状態。** 既定は対象を分割すること (**separate-before-serializing-shared-state** の principle skill)。直列化するのは本物の不変条件のためだけにする。
   - **最小の安全な分解。** ワーカー 1 体が最良なら、その理由を名指しする。
4. コードを書く作業は、設定した feature モデル (既定は `grok-4.7-xhigh-fast`) のサブエージェントへ、具体的なスコープを与えて委譲する (ファイルパス、**principle-model-the-domain** に従って名指しされたデータの形とその組織構造、散らばった boolean ではなくステートマシン、分岐ではなくテーブル / レジストリ、繰り返される形の思い込みではなく型付きモデルを、委譲先がロジックを書く前に選ぶ、そして成功条件)。実装が複数の妥当な形を許すとき (エラーハンドリング、抽象化のレイヤ、テストの構造) は、代わりに **arena** skill 経由で委譲し、ランナーが代替案を表に出し、cross-judge が選択を守るようにする。これは必須である。理由付きスキップの逃げ道は無く、Laziness Protocol もこれを上書きしない (得られるのはレビューの分離であって、削減された行数ではない)。spawn を禁じられたサブエージェントは、同じレビューの分離を保って自分で diff を所有することでこれを満たす。入れ子のエージェントを待つ「standing by」の返答は無し。コメントは **Comments** に従う。外科的な編集をし、上流由来のファイルはソースに照らして接地し直す。共有プリミティブの改善はすべての利用側へ移植し、それぞれ検証する。コミットは惜しまない。
5. 対応する表面で検証する。「Inconclusive」や表面違いは pass ではない。そう明示する。
6. 小さく順序立ったコミットへ rebase する。追随作業はスタックする。
   **sequence-verifiable-units** の principle skill を使い、小さい単位ごとにビルドし、検証し、コミットしてから次へ進む。
7. 設計に異論があるなら、出す前に `interrogate`。
8. **Opening a PR** を実行する。

コードが密結合した作業 (1 つの feature、1 つのマイグレーション) は、チェックポイントをインラインに持つ単一のオーナーへ渡す。そのオーナーがブロッキングなフェーズの後に内部でファンアウトする。親レベルのファンアウトは、独立した成果物を生むスライス (監査、サブシステム横断の調査、競合する実験) のためのものである。フェーズの境界でチェックポイントを書き直す。割り込みを連鎖させるのではなく、新しいオーナーを spawn する。

**返答:** 何を作ったか、何を選びなぜか、スループットのチェックポイント、未決の判断。設計の代替案はテーブルで。
