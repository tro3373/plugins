### Autopilot-full

**あなたが持つのは verdict であって、PR ではない。各 PR は 1 人の owner が build から merge まで走らせ、あなたの clean な swarm verdict なしには何も merge されない。** 「このキューを autopilot して」「full autopilot」「PR ごとに owner 1 人」のプログラム向け。Orchestrate は、coordinator 自身が検証済みの作業を着地させ、worker は決して merge しない常設プログラムを走らせる。こちらでは各 PR の owner がライフサイクル全体を merge まで担い、root は検証、副署、監査だけを保持する。

1. **operator の項目に印を付け、state-then-wait を守る。** operator が名指しした項目は operator のものだ。レビューするのも、クリックするのも operator であり、どの owner もそれを merge しない。プロトコルやプランを述べるよう求められたら、その言明を届けて止まる。実行が始まるのは operator の明示的な go の後だけだ。その go を受けたら、プログラムの目的全体を持つ `/goal` を装填する。goal はキューが終わるまでターンをまたいで継続する。
2. **PR ごとに owner を 1 体、フルライフサイクルと早期の trail 付きで起動する。** forge はプログラムにつき一度だけ解決する。GitHub CLI (`gh`) が既定だ。`command -v origin` が成功し、Origin がそのリポジトリを解決できるなら、PR の create、edit、view、watch、merge の操作に `origin pr ...` を使う。そうでなければ `gh` のままとし、フォールバックしたことを記録する。Graphite (`gt`) を必須にしてはならない。PR ごとに Cursor cloud agent を 1 体、build、最初の push、ready な PR、実物のアーティファクト上での self-proof (**prove-it-works** の principle skill)、`../references/bugbot-triage.md` に沿った懐疑的な Bugbot triage、slop-strip (`cursor-team-kit` プラグインの `deslop` skill (`/deslop`))、`/no-comments` (**no-comments** skill)、現在の trunk への rebase、green までの babysit ループ (`playbooks/babysit.md`)、そして merge そのものを担わせる。おおよそ 15 分以内に、各 owner は **show-me-your-work** skill に従って `decisions.tsv` の trail を開始し、最初のブランチのスナップショットを push し、PR を draft ではなく ready で開く。self-proof の前に PR を開くことで、URL、決定、チェックが持続する trail を形成する。`decisions.tsv` は未コミットのまま保ち、レポートと一緒に返す。サブエージェントが起動したらすぐ、owner はその ID、想定される実行時間 (少なくともその種類の過去最長の run)、状態を、同じように保つ `children.tsv` に加える。owner は code-ready レポートと babysit の前に、trunk が drift しているかどうかにかかわらず最初の rebase を行う。fix のラウンドでは、owner はその merge base を保つ。owner が再び rebase するのは、merge 準備 (ステップ 5) のとき、trunk との `git merge-tree` 競合のとき、または trunk 上の変更に由来する CI 失敗のときだけだ。出荷するコードが確定したら、slop-strip と `/no-comments` の後に、code-ready な head SHA を報告する。以降、パッチを変える push のたびにその SHA も報告する。その後 self-proof、CI、babysit は swarm と並行して走る。self-proof、CI、babysit が終わったら、owner は head SHA とともに merge-ready を報告する。ラウンドを始める push の前に、リポジトリの AGENTS.md ファイルとルールが対象パスに対して名指しする pre-review チェックを走らせる。それはコミット済みの head で走らせる。hook が通ることは証明にならない。各 rebase を公開するには、`ls-remote` での確認の後、owner 自身のブランチを `git push --force-with-lease` で push する。共有ブランチを force-push することは決してない。merge は owner が単独で踏めない唯一のステップだ。ステップ 4 がそれをゲートする。
3. **owner は真に並列で走らせ、決してスタックしない。** PR が自己完結しているなら、同時に多数の owner を走らせる。ブランチごとに writer は 1 人、ファイルは重ならず、PR をまたぐ drift は rebase が吸収する。直列化するのは本当に重なっている作業だけだ。自己完結した PR は main から直接生やし、順序のある作業は merge してから生やす。例外はひとつ。本当に依存している変更を分割せざるを得ない owner は、短命な private base-branch スタックを持ってよい。
4. **各ラウンドを merge の前に swarm で検証する。** ラウンドは owner の code-ready な head SHA で始まり、その後 PR のパッチを変える push のたびにも始まる。その SHA において、**swarm** skill に沿って独立した verifier を並列に展開し、ひとつの verdict に集約する。merge に必要なのは、merge-ready な head とパッチが一致するラウンドの clean な verdict だ。verdict の前に、merge-ready レポートのレシートを監査する。レーンは次の通り。その SHA でゲートを再実行する。変更が触れる実際の面の上で、荷重を支える挙動をライブで証明する (該当する control skill、たとえば `cursor-team-kit` の `control-cli` や `control-ui`、それが無ければ名指しされたドライバを使う)。PR の本文を信用せず、diff を監査する。この監査は、フルの brief を持つ 2 つ以上のレビューレーンとして走らせる。各レーンには、trunk とのコンシューマ側の一致、ライフタイムとレース、データや設定の安全性のような主眼をひとつ与える。**trunk に対する regression レーン。** 同じ荷重を支えるシナリオを現在の trunk 上で走らせる。trunk にその機能が無いなら、その事実を記録し、trunk が結果を出せるふりをする代わりに、diff が追加する挙動とユーザが待っている最終状態をゲートする。ライブのレーンが下限であり、それを欠く verdict は clean ではない。root の clean な verdict なしに merge は無い。レーンが結果を返したら、PR に対して証明されたすべての finding を 1 回の fix-forward で owner に送る。レーンが note として記録した欠陥も finding である。挙動に関する finding ごとに、同じ欠陥を持つすべての箇所をカバーする red test を求める。テストで欠陥を示せない場合は、代わりに repro のレシートを求める。その欠陥は次のラウンドのレビュー brief に加える。新しい head には新しい swarm と新しい verdict を与える。ただし `playbooks/shipping.md` の patch-id ルールの下で有効なままのレーンの結果は除く。
5. **clean な verdict が出たら owner が merge し、次の項目を取る。** owner が merge できるのは、trunk へ rebase したての head からだけだ。merge の準備がラウンドのレーン開始より先に来ることは無く、merge の直前の現在の trunk への rebase で終わる。merge 準備の rebase の後、owner は新しい head SHA を報告する。merge の前にその head で CI が通らねばならず、そのラウンドの verdict がなお有効かどうかは patch-id ルールが決める。merge の前に trunk がまた動いたら、`playbooks/shipping.md` の patch-id ルールが再検証を支配する。patch-id が変わっていない限り、新しい head は verdict を無効にする。owner は解決済みの forge を通じて自分の PR を squash-merge し、キューから次の自己完結した項目を拾う。operator の完全自律の付与と root の clean な verdict の組み合わせが merge の認可であり、babysit だけでは決して得られないものだ。operator が名指しした項目は merge-ready で止まり、operator のクリックを待つ。
6. **root のレイヤーを走らせる。** ピン留めされたゲートや予算の値 (CI が締める方向にしか許さない上限) を本当に新たに引き上げるには、あなたの新鮮な副署が要る。それは verifier の証明を得た後にだけ与えられる。operator の付与または standing order が承認をカバーしているなら、その副署が承認そのものとなる。owner はそれを、ツールの承認契約が許す形式で記録し、root の副署へのポインタを添える。レーンはその記録を副署と突き合わせて確認する。root は forge が強制する承認を、決して自ら与えたり回避したりしない。既に main に着地している値を取り込むのは raise ではなく drift だ。全 owner に対する監査 tick をおよそ 30 分ごとに回す。ローカルの root は各 tick を実際のターミナルの `/loop` として装填する。このループは monitored-shell の 30 分 sleep を使い、output-notification のセンチネルを発する。cloud の root は代わりに既存の cloud-sleeper の wake チェーンを使う。このリズムを記憶や、取りこぼしのある完了通知に委ねてはならない。各 tick で、`git show origin/main:pstack/skills/poteto-mode/playbooks/autopilot-full.md` により trunk からこの playbook を読み直し、次に装填した `/goal` を読み直す。その両方に照らして運用を監査する。その tick の中で drift を直す。各 owner を汎用の生存確認またはステータス確認で突き、決定の trail を集める。前進として数えるのは副作用だけだ。commit、push、PR やチェックの差分、そして store されたレポート。エラーになったレーン、または想定される実行時間を過ぎても副作用が無いレーンは stuck とみなす。直ちに停止させ、代替を投入する。礼儀正しい復帰を待たない。各 tick はまた、プラットフォームにエージェント一覧があればプログラムのエージェント一覧に対して、そして全 owner の `children.tsv` に対して、レーンの stuck テストを走らせる。stop が効くかどうかにかかわらず、root は owner に各 stuck なサブエージェントを stuck として記録させ、その作業がまだ必要なら置き換えさせる。stall した置き換えにも同じ手順を踏む。owner にできないときは root がその両方の手順を取る。stall はその作業を証明することも取り下げることも無い。merge がまとまったら、retro のパスと merge 後の bot コメントの掃討を走らせる。最後の merge の後であっても、委任した作業が残っていないときにだけ tick を終える。
7. **operator の stop で即座に stand down する。** operator の hold や stand-down は、書き込みゼロの命令として直ちに全 owner に届く。owner は operator が解放するまで brief を保持する。

**返答:** 各 PR の owner、状態、head SHA を含むキュー。各 verdict と、それを生んだ swarm。何が merge され、各 owner が次に何を取ったか。与えた副署とその理由。未処理の operator ゲート。集めた決定の trail の置き場所。
