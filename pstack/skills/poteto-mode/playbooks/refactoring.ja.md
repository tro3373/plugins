### Refactoring

**契約はあなたが持つ。構造は変わる。挙動は変わらない。** 挙動を追加する Feature、挙動を正す Bug fix とは区別される。

片付けの過程で欠けている機能や本物のバグが見つかったなら、それを切り出し、固定した契約に対して構造の変更を先に出す。再設計は許されるが、それを再設計と名指しし、Feature へ回す。大規模または横断的な構造作業は **figure-it-out** skill の担当だ。この playbook は、焦点の絞られた変更から中規模の変更までのためのものだ。

1. まず挙動の契約を固定する。影響を受けるサブシステムに **how** skill を走らせて契約を把握し、構造が動く前に現在の挙動を捉える characterization テスト、スナップショット、または等価性ハーネスを書く。その領域にカバレッジが無いなら、構造に触れる前に固定を書く。型チェックと lint は固定にならない。
2. **principle-model-the-domain** に従い、コードに欠けている構造を名指しする。形が既に明確でローカルなら、退屈なコードはそのまま残す。作り替えは分岐か不正な状態を削除しなければならず、間接参照を足すものであってはならない。
3. 目標の形を名指しする。今日ゼロから作るとしたら、モジュールの配置、型、コールグラフはどうあるべきかを述べる (**principle-foundational-thinking**、**principle-redesign-from-first-principles**)。目標が関数境界をまたぐなら、移動の前に **architect** skill を走らせ、その形の設計を並列で探索する。
4. 足す前に引く。新しい形を導入する前に、死んだコードを削除し、呼び出し元が 1 つだけのラッパーを畳み、冗長なバリデータを捨て、孤立した参照を取り除く (**principle-subtract-before-you-add**)。目標の形に届く最小の変更を出す (**principle-laziness-protocol**)。「役に立つかもしれない」という当てずっぽうの片付けは revert する。
5. 挙動を保つ小さなステップで動かし、各ステップで固定を green のままに保つ。API の作り替えでは、すべての呼び出し側を移行し、古い API を同じ波で削除する (**principle-migrate-callers-then-delete-legacy-apis**)。互換シムも、新旧の並行経路も作らない。rename はどれも実際のファイルに対して抜き取り確認する。rename は、文字列・散文・後方参照の中の使用箇所を黙って取りこぼす。機械的な編集は、設定したリファクタリング用モデル (既定は `grok-4.7-xhigh-fast`) を使うサブエージェントへ、具体的なスコープ (ファイルパス、移動する名前、保つべき挙動) を与えて委譲する。
6. 挙動が変わっていないことを、「コンパイルは通る」ではなく実物の成果物の上で証明する (**principle-prove-it-works**)。大きめの作り替えでは等価性チェックを走らせる: 新旧の出力を diff するスクリプト、新しいコードに対して再生する記録済みのベースライン、または該当する control skill 経由で対応する表層に対して行うスモーク実行。
7. その変更が残す価値を持つことを確かめる。成功の尺度は読み手の負荷が減ることだ (**principle-minimize-reader-load**)。diff がどこかの読み手負荷を下げていないなら、revert する。
8. 小さく順序付いたコミットへ rebase する。引き算のコミット、次に作り替え、次に後続の片付け。**sequence-verifiable-units** の principle skill で形を整え、挙動を保つ各スライスが次へ進む前に green のままになるようにする。**Opening a PR** を実行する。

**返答:** 変わった構造、それを照らし合わせた固定、等価性の証明、読み手負荷の差分、何を出して何を revert したか。新しい挙動は無い。
