### パフォーマンス問題

**あなたは計測のストーリーを所有する。プランを立て、レビューし、数字を検証する。** すべての修正を計測に結び付ける。計測する代わりにソースを読んで済ませてはならない。

1. 対応する control skill でベースラインのトレースを取得する。ベースラインと、その後のすべての数字を **benchmark-checklist** skill で精査する。
2. `how` で仮説を接地させる。まず実行せずにパフォーマンスの上限を主張してはならない。
   performance mantras を、安いものから順に試す:
   1. やらない。何も使わない結果を生む作業は、安くするのではなく止める。
   2. やるが、二度はやらない。
   3. 減らしてやる。
   4. 後でやる。
   5. 見られていないときにやる。
   6. 並行してやる。
   7. 安くやる。

   前の mantra で目標を満たしたら、そこで止める。
3. トレースから修正をプランする。関数の境界を跨ぐなら、先に `architect` を使う。実装は、設定されたパフォーマンス問題用モデル (既定は `grok-4.7-xhigh-fast`) を使うサブエージェントに委譲する。diff をレビューする。修正後のトレースを取得する。
   **sequence-verifiable-units** の principle skill を適用し、次を試す前に各試行を検証する。
4. 成果物をパースして比較する (JSON を sqlite へ、diff)。「決定不能」や対象面の取り違えは合格ではない。それを表明する。
5. PR で計測を引用する。
6. **PR を開く**を実行する。

単発の修正ではなくメトリクスに対する継続的な改善を行う場合は、ヒルクライム playbook (`playbooks/hillclimb.md`) を使う。

**返答:** ベースラインの数値、修正後の数値、差分、成果物のパス。
