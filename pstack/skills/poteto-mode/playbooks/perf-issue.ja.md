### パフォーマンス問題

**あなたは計測のストーリーを所有する。プランを立て、レビューし、数字を検証する。** すべての修正を計測に結び付ける。計測する代わりにソースを読んで済ませてはならない。

1. 対応する control skill でベースラインのトレースを取得する。
2. `how` で仮説を接地させる。まず実行せずにパフォーマンスの上限を主張してはならない。
   ほとんどの修正は 8 つの戦略ファミリから来る。これらはチェックリストではなく仮説生成器として使う。あるファミリが試行に値するのは、トレースがそのファミリの名指しするシグナルを示しているときだけである。
   - **除去。** ホットパスを最適化する前に、それが存在する必要があるかを問う。誰も消費しない計算、このユーザでは常にオフのフィーチャーゲート、状態を冗長にミラーする同期、「念のため」残されたレガシー経路。トレースは何が遅いかを示すが、それが削除可能であることは決して示さない。だからこのファミリはプロファイラではなく `how` のパスを必要とする。
   - **分割統治。** 支配的なコストが入力サイズに比例して増える。各部分が触る量が減るように仕事を分割する (チャンク化、シャーディング、探索空間の枝刈り) か、独立した部分を並列に実行する。
   - **キャッシング。** 同一の入力に対して同じ計算やフェッチが繰り返される。結果を保存して再利用する。勝利を主張する前に、何が無効化するかを名指しする。
   - **間接化。** ホットパスが、より安い中間物で吸収できる高コストな仕事をしている。スキャンの代わりのインデックス、対話スレッドから仕事を退かせるキュー、より安い実装に差し替えられるようにするハンドル。そのホップを追加するのは、クリティカルパスから取り除く量が追加する量を上回るときだけにする。
   - **バッチング。** 小さな操作がそれぞれ固定のオーバーヘッド (RPC、クエリ、システムコール、ドローコール) を払っている。まとめて、バッチごとに 1 回だけオーバーヘッドを払う。
   - **冗長化。** 待ちが 1 つの遅いインスタンスや試行に引っ掛かっている。仕事を複製し (レプリカ、hedged request、投機的実行)、最も速い結果を取る。トレースが待ちの支配とシステムの余裕を示していなければならない。
   - **遅延評価。** コストが、使われない結果やまだ必要でない結果に乗っている (ブートパスでの eager な初期化、画面外項目のレンダリング)。最初に使われるまで仕事を先送りする。
   - **スケジューリング。** その仕事は必ず起きなければならないが、対話の瞬間である必要はない。誰も待っていない場所に移す。アイドルコールバック、ブート後のバックグラウンドウォームアップ、ユーザが到着する前の事前計算、フレームのコミット後のクリーンアップ。得られるのは体感レイテンシなので、総作業量ではなく対話パスを計測する。
3. トレースから修正をプランする。関数の境界を跨ぐなら、先に `architect` を使う。実装は、設定されたパフォーマンス問題用モデル (既定は `grok-4.7-xhigh-fast`) を使うサブエージェントに委譲する。diff をレビューする。修正後のトレースを取得する。
   **sequence-verifiable-units** の principle skill を適用し、次を試す前に各試行を検証する。
4. 成果物をパースして比較する (JSON を sqlite へ、diff)。「決定不能」や対象面の取り違えは合格ではない。それを表明する。
5. PR で計測を引用する。
6. **PR を開く**を実行する。

単発の修正ではなくメトリクスに対する継続的な改善を行う場合は、ヒルクライム playbook (`playbooks/hillclimb.md`) を使う。

**返答:** ベースラインの数値、修正後の数値、差分、成果物のパス。
