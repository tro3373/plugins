### Shipping

**あなたは何が着地するかに責任を持つ。各 PR を独立に検証し、root から検証済みの連なりだけを着地させ、あとはスタックに手を出さない。**

1. **forge を確定し、そのうえで着地前に各 PR を独立に検証する。** GitHub CLI (`gh`) が既定。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、すべての PR 操作に `origin pr` を使う。そうでなければ `gh` のままにし、フォールバックしたことを記録する。Graphite (`gt`) を必須としてはならない。PR ごとに 1 体の検証者 (それぞれ Cursor のクラウドエージェント) が、対応する control skill (`cursor-team-kit` の `control-ui` や `control-cli` など) を使って、ユーザと同じ方法で親と head を比べながら変更を動かし、その PR に `PASS`、`PASS+NOTES`、`FAIL` のいずれかを投稿する。コードを書いていないエージェントの判定だけが数えられる。作者は作るつもりだったものを確かめるからである。CI がグリーンであることも、bot の承認レビューも判定ではない。どちらもユーザと同じ方法で変更を動かさないからである。
2. **最下段を根とする、連続した検証済みの連なりだけを着地させる。** 未マージの最下段 PR から上へ辿り、`PASS` も `PASS+NOTES` も無い最初の PR で止まる。それより下の PR が連なりであり、その最上段が天井である。未検証の PR の上に載っている検証済み PR は待つ。下のコード無しには着地できないからである。ブランチがそのコードを持たず必要ともしない PR は、trunk へ移して単独で着地させてよい。ただし先に新しい判定が要る。古い判定はそのコードが下にある状態で走ったもので、trunk にはそのコードが無いからである。
3. **判定が今もそのコードを説明しているか再確認する。** 判定が覆うのはパッチであり、チェーンの rebase は、チェックを 1 つも落とさないまま、その上のすべての PR を新しい SHA へ動かす。古い判定を信用する前に、判定時の SHA の `git patch-id` と現在の head のものを比べる。パッチの差がテスト、docs、lint 設定だけなら、各レーンが走らせたものが、ノイズを除いて両方の SHA で同じようにビルドされる限り、そのレーンの結果は有効のままとする。ノイズとは、判定時の SHA の 2 回のビルドの間にも現れる差、または埋め込まれたコミット SHA のことである。読み手が判断を確かめられるよう、ノイズの種類ごとにファイルを添えて報告する。変更そのものには、古い判定がそれを見ていないので、新しいチェックとレビューを行う。dev server のようにビルド出力の無いレーンはこれを示せないので、再実行し、ほかにずれたものも再検証する。
4. **下から 1 PR ずつ着地させる。** 常に連なりの未マージの最下段 PR を `origin pr merge <pr>` か `gh pr merge <pr> --squash` でマージする。Origin では素のコマンドが、指名した PR より下のすべての PR もマージする。GitHub では base がまだ親のブランチである PR は、trunk ではなくそのブランチへマージされる。マージコマンドは、マージキューが PR をキューに入れただけでも成功を報告しうるし、要求した auto-merge はマージではないので、結果は PR を読み戻して確かめる (`origin pr view <pr>` か `gh pr view <pr> --json state,mergedAt,baseRefName`)。着地した PR は、base が親のブランチではなく trunk の状態で merged と読める。`--auto` (Origin の merge-when-ready か GitHub の auto-merge) は、準備のできた head をそのまま着地させるので、判定が現在の head を覆っている PR にだけ arm する。マージが着地したら、base がそのマージ済みブランチだった PR を trunk へ付け替え (`origin pr edit <pr> --base <trunk>` か `gh pr edit <pr> --base <trunk>`)、そのパッチをマージ結果の上へ移し、`--force-with-lease` で push する。判定が覆うのはパッチであってコミットではないので、判定が生き残るかはステップ 3 の patch-id の規則が決める。チェックが通り、判定が生き残ったらマージする。
5. **着地している間、スタックに手を触れない。** ステップ 4 の次の PR の移動が、ブランチや base への唯一の変更である。マージは、判定の有無にかかわらず、その時点でブランチと base が持っているものをそのまま着地させるからである。GitHub では `playbooks/babysit.md` の queued watcher (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`) を `/loop` の下で使い、天井で `COMPLETE` を報告するまで連なりを見張る。Origin では `origin pr checks <pr> --watch` が返るたびに `origin pr view <pr> --checks` で現在の PR を読み直し、天井が merged と読めるまで続ける。親がマージされたときに base が trunk へ動くのは想定どおりであり、直すべき損傷ではない。マージが止まったら、何かを変える前に理由を突き止める。
6. **天井で止まる。** 連なりを伸ばすには新しい判定が要るので、それはステップ 1 からの新しいパスである。

**返答:** 検証済みの連なりとその天井、各 PR の判定と誰が出したか、何が着地しどう確認したか、次の隙間には何が必要か。
