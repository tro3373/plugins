### Shipping

**あなたは何が着地するかに責任を持つ。各 PR を独立に検証し、root から検証済みの連なりだけを着地させ、あとはキューに手を出さない。**

これは `playbooks/babysit.md` の後半である。

1. **forge を確定し、そのうえで各 PR を独立に検証する。** GitHub CLI (`gh`) が既定。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、PR の view、watch、edit、merge の各操作に `origin pr ...` を使う。そうでなければ `gh` のままにし、フォールバックしたことを記録する。Graphite (`gt`) を必須にしてはならない。PR 1 本につきサブエージェント 1 体、まとめない。各々が Cursor のクラウドエージェントで、各々が、対応する control skill (`cursor-team-kit` の `control-ui` や `control-cli` など) で実際の表面を parent 対 head で動かす。各々が `PASS`、`PASS+NOTES`、`FAIL` を返し、その判定を自分の PR に投稿する。safe とは、コードを書いていないエージェントからの判定を意味する。CI が green なのは判定ではない。承認した bot のレビューも判定ではない。
2. **最下段を根とする、連続した検証済みの連なりだけを着地させる。** 未マージの最下段 PR から上へ辿り、合格判定の無い最初の PR で止まる。ここでは `PASS` と `PASS+NOTES` の両方が合格である。未検証の PR の上に載っている検証済み PR は着地できない。天井を PR 番号として報告し、何が連鎖を断ち切っているかを述べる。
3. **各判定が今もそのパッチを説明しているか再確認する。** 判定時の head SHA、base SHA、その PR の base から head への diff の安定した `git patch-id` を記録する。rebase や base の付け替えは SHA を書き換え、チェックに触れないまま判定を静かに無効化しうる。PR を着地させる前に、記録した patch-id と現在の base から head への patch-id を比較する。2 つのパッチがテスト・ドキュメント・lint 設定でしか違わないなら、各 lane が走らせたものをビルドする。判定時の SHA で 2 回、現在の head で 1 回ビルドする。判定時の SHA での 2 回のビルドでも同じ差が出るなら、あるいはそれが埋め込まれたコミット SHA であるなら、その差は noise である。ファイル単位ではなく差分ごとに判断し、noise の種類ごとにそのファイルとともに報告する。noise しか違わないなら、その lane の結果は有効なまま保たれ、checks とその変更のレビューは新しく実行し直す。dev サーバや、ビルド出力の無い何かからの lane の結果を使い回してはならない。その lane を再実行する。それ以外は、パッチが変わっていたら再検証する。変わっていなければ、コードに対する判定は保ちつつ、現在の head でマージ可能性と CI を再実行する。コミットメッセージの一致や、古い SHA の green チェックを代用にしてはならない。
4. **最下段の PR だけを準備する。** 現在の trunk を fetch する。必要なら検証済みの最下段ブランチを trunk の tip ちょうどへ rebase して push し、その PR だけを `origin pr edit <pr> --base <trunk>` か `gh pr edit <pr> --base <trunk>` で trunk へ付け替える。push の後にステップ 3 を再実行する。子孫の付け替え・arm・マージはまだしない。
5. **1 度に 1 PR ずつ着地させる。** 最下段の PR が今マージ可能なら、`origin pr merge <pr> --squash` か `gh pr merge <pr> --squash` で squash する。要件がまだ実行中で、ユーザが merge-when-ready を求めているなら、その PR だけを `origin pr merge <pr> --squash --auto` か `gh pr merge <pr> --squash --auto` で arm する。Origin の `--auto` は Origin の merge-when-ready である。GitHub の `--auto` は GitHub の auto-merge である。その PR がマージされるまで待ってから、次を準備する。
6. **GitHub の `autoMergeRequest` をスタックの準備完了と読んではならない。** それが言えるのはせいぜい、ある 1 つの GitHub PR に GitHub auto-merge が要求された、ということだけである。Origin の merge-when-ready が arm されていることも、子孫がキューに入っていることも、パッチに対する判定が最新であることも、連続したスタックが安全であることも証明しない。現在の最下段 PR について、稼働中の forge の状態を確認する。稼働中の forge が報告できないなら、状態は不明であると述べる。
7. **マージのたびに計算し直す。** trunk を fetch し、マージ済みの SHA があることを確認し、凍結した下から上のリストからマージ済み PR を落とし、新しい最下段 PR の base、head、checks、patch-id を調べる。ホストが子を自動で付け替えることはあるが、そうしたと仮定してはならない。その 1 PR についてステップ 3 から 6 を繰り返す。独立した作業はこの連鎖の外に留まり、それ自身で出荷される。
8. **現在の frontier を、マージされるか失敗するまで見張る。その周りのキューを変更しない。** Origin では `origin pr view <pr> --checks --comments` と `origin pr checks <pr> --watch` を使い、その PR が merged か blocked を報告するまで読み直す。GitHub では `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>` をイベントによる起床としてだけ使い、起床のたびに `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest` をポーリングする。`mergedAt` が非 null になるか `state` が `MERGED` になるまで `READY` は無視する。そうなってはじめてステップ 7 を実行する。ハードに失敗と扱うのは、`state` が `CLOSED` で `mergedAt` が無いとき、必須チェックが `FAILURE` か `CANCELLED` で終わり、auto-merge がもう保留でなくなった後にマージをブロックしているとき、あるいは auto-merge が保留でない状態で `mergeStateStatus` が `UNSTABLE` か `DIRTY` のときだけである。チェックが保留中、または auto-merge が arm されている間の `BLOCKED` は失敗ではない。Babysit のキュー済み `WAITING`/`merge-queue` の停止条件をここで使ってはならない。見張りは `/loop` の dynamic モードで保持する。各マージと新しい天井を報告する。キューが止まったら、変更する前に診断する。
9. **天井で止まる。** 検証済みの連なりがマージされたら、何が着地したか、次の未検証 PR は何か、それを検証するには何が要るかを報告する。連なりを伸ばすのはステップ 1 からの新しいパスである。

**返答:** 検証済みの連なりとその天井、各 PR の判定と誰が出したか、何を arm しどう確認したか、何が着地したか、次の隙間には何が必要か。
