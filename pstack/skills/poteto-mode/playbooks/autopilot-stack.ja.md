### Autopilot-stack

**あなたが所有するのはスタックであって、着地ではない。完全な自律でキューを構築・検証し、オペレータがレビューして着地させる 1 本の線形なベースブランチスタックを渡す。** **Autopilot-full** の兄弟だ。

1. **オーナーループはそのまま実行する。** フォージはプログラムにつき一度だけ解決する。既定は GitHub CLI (`gh`)。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、PR の create、edit、view、watch、merge の各操作に `origin pr ...` を使う。そうでなければ `gh` のままにし、フォールバックしたことを記録する。Graphite (`gt`) を必須にしてはならない。1 PR につき 1 つの Cursor クラウドエージェントが、その変更を端から端まで所有する: ビルド、初回 push、セルフプルーフ前に開く ready な PR、セルフプルーフ (ゲート、CI、レシート)、`../references/bugbot-triage.md` に従った懐疑的な Bugbot トリアージ、slop の除去 (`cursor-team-kit` プラグインの `deslop` skill (`/deslop`))、`/no-comments` (**no-comments** skill)、そして `playbooks/babysit.md` に従ってグリーンになるまでのお守り。作業が自己完結しているとき、オーナーは並列化する。約 15 分以内に、すべてのオーナーが **show-me-your-work** skill に従って `decisions.tsv` の軌跡を開始し、最初のブランチスナップショットを push し、PR を draft ではなく ready で開く。軌跡はコミットせず、レポートで返す。オーナーは Autopilot-full ステップ 2 の `children.tsv` も保持する。
2. **wake チェーン上で監査する。** root はおよそ 30 分ごとに監査ティックを実行する。ローカルの root は各ティックを実際のターミナルの `/loop` として仕込む。ループは監視付きシェルの 30 分スリープを使い、出力通知のセンチネルを発する。クラウドの root は代わりに既存のクラウドスリーパの wake チェーンを使う。周期を記憶や欠落しうる完了通知に委ねてはならない。各ティックで、`git show origin/main:pstack/skills/poteto-mode/playbooks/autopilot-stack.md` で trunk からこのプレイブックを読み直し、次に仕込まれた `/goal` を読み直す。両者に照らして運用を監査する。そのティックの間にドリフトを直す。各オーナーを汎用の生存確認またはステータス確認で探る。進捗として数えるのは副作用だけだ: コミット、push、PR やチェックの差分、そしてストアのレポート。想定実行時間を副作用なしで超えたレーンは詰まっているとみなす。直ちに停止させ、代替を派遣する。丁寧な返答を待たない。すべてのサブエージェントを探り、Autopilot-full ステップ 6 に従ってティックを終える。
3. **オペレータのゲートを守る。** state-then-wait であり、プランを述べよという要求は go ではない。オペレータの明示的な go を受けたら、プログラム全体の目的を持つ `/goal` を仕込む。ゴールはチェーンが終わるまでターンをまたいで継続する。オペレータの stop を受けたら、すべてのオーナーが即座に書き込みゼロで停止する。
4. **各ラウンドで検証する。** オーナーは、出荷するコードが確定したら code-ready の head SHA を報告し、そのループがグリーンになったら正確な head SHA とともに STACK-READY を報告する。root は Autopilot-full ステップ 4 に従って各ラウンドを検証する。merge-ready の代わりに STACK-READY を使う点が違う。未検証のものはスタックに入らない。
5. **クリーンな評決で追記する。決して ship しない。** どのオーナーもマージせず、auto-merge を仕込まず、クローズしない。クリーンな評決は、その PR を 1 本の線形なベースブランチスタックへ、検証された順序かオペレータが指定した順序で追記する。
6. **トポロジは単一の書き手、ビルドは並列の書き手。** オーナーは自分のブランチだけを push し、tip、現在のベース、意図する親を報告する。root だけがトポロジの書き手だ。PR を追記するには、意図する親を fetch し、子ブランチをその親の tip にちょうど rebase し、`ls-remote` で確認してからのみ `--force-with-lease` で push し、PR のベースを親ブランチに設定する。解決したフォージに応じて `origin pr create --status open --base <parent-branch>` か `gh pr create --base <parent-branch>` で作成する。既存の PR の再ターゲットは `origin pr edit <pr> --base <parent-branch>` か `gh pr edit <pr> --base <parent-branch>` で行う。trunk を対象にするのは root の PR だけだ。チェーンを `gt` 経由で submit または登録してはならない。
7. **ドリフトは root で吸収し、動いたものを再検証する。** root は現在の trunk を fetch し、チェーンを下から上へ rebase する。rebase があるオーナーのファイルで競合を表面化させたら、そのオーナーが自分の担当分を直し、root が結果を push する。rebase はその上のすべての SHA を書き換え、旧 SHA での評決を無効にする。各評決 SHA で `playbooks/shipping.md` の patch-id ルールを適用する。もはや有効でないものは、配送前にこのプレイブックのステップ 4 を通し直す。patch-id が変わっていなくても、書き換えて push するたびにマージ可能性と CI を再実行する。カウンターサインのルールは Autopilot-full から変わらない。本当に新しいピンは root の新たなカウンターサインのために stop を起こす。着地済みの値のドリフトを吸収することは stop の理由にならない。
8. **チェーンを配送する。** 成果物は検証済み PR の線形なチェーン 1 本であり、解決したフォージで下から上へレビューでき、各リンクは PR 本文かコメントに検証者の評決を持つ。オペレータがそれをレビューし、自分のクリックか、自分で仕込む merge-when-ready で着地させる。

**どちらの autopilot を選ぶか。** PR が独立していて着地の権限が与えられているなら Autopilot-full。オペレータが着地前のレビューを望むとき、作業が順序付けられているか結合しているとき、あるいはマージ権限が与えられていないなら Autopilot-stack。

**Reply:** スタックの root と tip へのリンク、リンクごとの 1 行の評決サマリー、そして保留または除外したものとその理由。
