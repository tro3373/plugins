# 呼び出し元を移行してからレガシー API を削除する

新しい API が正しい設計だと判断したら、互換レイヤを保つのではなく、同じリファクタの波で呼び出し元を移行し、古い API を取り除く。

**ルール:**
- 内部の呼び出し元がまだ存在するというだけの理由で、レガシー API の経路を維持しない
- 呼び出し元を棚卸しし、移行し、古い API を直ちに削除する
- 一時的なアダプタは既定のアーキテクチャではなく、例外的かつ期限付きのものとして扱う
- テストは新しい契約を検証するよう更新し、リファクタ前の実装詳細を守るだけのテストは削除する

**これが当てはまる場面:**
- 後方互換性に依存する外部ユーザがいない
- プロジェクトが協調した破壊的変更を吸収できる
- 新しい API が単純化またはリファクタの取り組みの一部である

古い API と新しい API の両方を保つと、二重経路の複雑さが生まれ、後片付けが遅くなり、コードベースが追記専用のように感じられるようになる。
