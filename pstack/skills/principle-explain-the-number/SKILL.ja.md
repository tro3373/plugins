# Explain the Number

計測した数値は、システムについての主張である。信じる前に、報告する前に、それに基づいて動く前に、何がそれを制限しているかを見つけ、別の何かを計測した可能性を排除する。

**なぜか:** うまくいかなかった実行でも、もっともらしい数値は出る。失敗したリクエスト、作業を飛ばしたキャッシュ、走らなかったコード、デフォルト設定のまま放置された片側、実行ごとのノイズは、どれも問題なく見える結果を生む。数値がなぜ 2 倍良くないのかを言えないなら、自分が何を計測したのか分かっていない。

**パターン:**

- **「なぜ 2 倍ではないのか?」と問う。** 結果を縛っているリソースやコードパスを名指しする。コア、ロック、ディスク、ネットワーク、あるいは負荷生成側そのものなど。それを実行中に取ったプロファイルかシステムカウンタから得て、ソースに対応付ける。コードを読んで推測しただけのものは律速要因ではない。
- **その数値が他に何を計測している可能性があるかを列挙し、それぞれを証拠で排除する。** よくある容疑者は、エラー、飛ばされた作業やキャッシュされた作業、チューニングされていない片側、ノイズ、end-to-end で見ると小さすぎて効かない部分である。
- **証拠を数値と一緒に保つ。** 実行回数、ばらつき、律速要因をノートかリンクした artifact に置き、読み手が主張を確認できるようにする。

性能の数値については、[benchmark-checklist](../benchmark-checklist/SKILL.md) skill で手順を一通り実行する。eval の結果については、試行に同じことを問う。すべての実行がタスクをこなしたか、差は試行とモデルをまたいで保たれるか、そのシナリオは重要か。

数値の裏付けとなる証拠に実行回数もばらつきも名指しされた律速要因も無いとき、または短縮された時間が変更した部分にかかっていた時間より大きいとき、これを飛ばしている。

[Prove It Works](../principle-prove-it-works/SKILL.md) とは別物だ。あちらは出力が本物であることを確認する。こちらは計測した数値が、自分が言っている意味を持つことを確認する。
