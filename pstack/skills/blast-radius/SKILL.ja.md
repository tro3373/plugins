# Blast radius

変更が出荷される前に、どこか別の場所で何を壊すかを見つける。"blast radius of X"、"what could this break"、まだ信用しきれていない小さな diff のレビューに使う。

`how` と `why` の相棒である。`how` はコードが何をするかを教える。`why` はなぜその形なのかを教える。blast radius はどこか別の場所で何を壊すかを教える。

呼び出し元を列挙するのは仕事ではない。エージェントは 1 秒で grep できる。仕事は grep では見えない破壊である。

## 自分の書き上げたものを信用するな

もっともらしく聞こえる blast-radius の文書は無価値である。真であろうと偽であろうと説得力があるように読める。だから文書を渡すな。全体が依存している 1 つか 2 つの事実を見つけ、コードを実行して証明せよ。

### どれだけ確かか

変更の安全性が依存する各事実について、安価にできる範囲でこのリストを下まで進め、どこで止まったかを述べる。

1. そう言った。それ単体では無価値。
2. その行を指した。本物の `file:line`、あるいはライブラリ自身のソース。
3. まずいケースが起こりえないことを示した。失敗を 1 ステップずつ辿り、そこに到達しない。
4. 実行した。実際のコードを呼び、間違っていれば大きく失敗するスクリプトかテスト。
5. 動いているアプリで再現した。

ステップ 4 はたいてい、アプリが出荷するのと同じライブラリを import し、心配している当の関数を呼ぶ小さなスクリプト 1 本である。

## 手順

1. 変更を読む。diff、追加・変更・削除されるシンボル、そして今や何が違う挙動になるか - diff が明示していない部分も含めて。PR とコミットを引くには `why` のステップ 2 を使う。
2. それが安全である根拠となる 1 つの事実を見つける。リスクに見える変更のほとんどは、たった 1 つの事実 - 「この呼び出しは既に死んでいるキャッシュエントリを落とすだけで、他には何もしない」のような - によって安全である。その事実を見つける。それが成り立てば、リスクの高いケースのほとんどが一度に片付く。あり得るかもしれないことの長いリストではなく、ここに時間を使う。
3. grep が止まるところを見る。呼び出しているライブラリのソースを読み、pin されたバージョンとローカルパッチを確認する。何がいつ走るかを割り出す - microtask、unmount と teardown、Solid と React の違い。シンボル検索が取りこぼすものを追う - API が返す JSON、DB のカラム、ワイヤフォーマット、同じバイト列を読む別の言語、フィーチャーフラグ、3 ホップ下流のコード。
4. 各リスクについて正直であれ。起こる現実的な確率と、起きたときの現実的なコストを付ける。確認できたリスクは残す。確認して問題なしとしたものは別に列挙する。ルールは `why` と同じ。本物の `file:line` を引用し、何も見つからない検索も答えの 1 つであり、呼び出し元や API を捏造してはならない。
5. その 1 つの事実を証明する。実際のコードを走らせるスクリプトかテストを書き、実行し、起きたことを貼る。
6. 大きい変更や広い変更では `arena` として走らせる。複数のモデルに同じ問いを投げ、答えをマージする。異なるモデルは異なる本物のバグを捕まえる。

## 何を返すか

- **何をするか。** 何が変わったか - 自明でない部分も含めて。
- **それが安全である根拠となる 1 つの事実。** それを述べ、どのステップまで到達したかを言い、証明を示す。証明できなかったなら未証明と書く。
- **リスク。** それぞれについて、どう壊れるか、`file:line`、確からしさと深刻さ、確認方法を挙げる。重要なものは証明を貼る。
- **問題なしとしたもの。** 何を確認し、なぜ大丈夫なのか。
- **マージ前に。** 本物のバグを捕まえる最も安価なテストか再現手順 - 書いたスクリプトを含めて。

`unslop` を通して書き、本物のコードを引用し、公開される場所へ出す前に非公開の情報を全て除く。

**返答:** 上記の文書。安全性の 1 事実は証明済みか未証明と明記されていること。
