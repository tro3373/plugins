# Why

コードの背後にある動機と意図を調査する。

`how` skill の対になる skill。`how` はコードが何をし、どう動くかに答える。`why` はどんな力がその形をもたらしたかに答える。

以下の起動それぞれは、`pstack-models.mdc` ルール内のロール行と既定値を指す。`model` にはその行の値を設定する。ルールやその行が無ければ既定値を設定する。値が `auto` または `inherit-parent` の場合は `model` を未設定のままにする。Task ツールがスラッグを拒否したら既定値を使い、その旨を述べる。既定値も拒否されたら、そのエラーメッセージから同じファミリーの最も近い有効なスラッグを使う。

## 動作姿勢

**注意深く、慎重で、精密な調査者**として振る舞う。自分が知っていることと推論していることについて正直であること。確信度のフレームワークと表現ガイドの全体は `references/epistemics.md` を読むこと。統合者はそれに従わなければならない。

## Step 1. 対象と質問を理解する

ユーザが何を尋ねているかを解析する。**対象**はたいていコードの一塊、パターン、機能、または名前の付いた設計判断である。**質問**はたいてい、設計判断の根拠、トレードオフ、動機となったエッジケース、外部の制約、デッドコード、または広範な歴史のスイープのいずれかである。

対象が曖昧なとき (指示対象がはっきりしないまま「なぜこうしているのか」と聞かれた場合)、会話のコンテキスト (開いているファイル、直近の編集、カーソル位置、直前に話していたこと) から最善の推測をする。外していたらユーザが修正できるよう、自分の解釈を簡潔に述べてから進める。

## Step 2. コードのアンカーを確立する

調査者を起動する前に、調査を具体的なコードに固定する。必要なもの:

- 関連するファイルパスと行範囲
- 主要なシンボル (関数名、クラス名、定数)
- 初期のコミット一覧。対象に触れた直近のいくつかのコミット。
- マージコミットからの PR 番号 (件名行の `(#1234)` パターン)

これはインラインで組み立てる。

```bash
# Blame target lines for last-touch commits
git blame -L <start>,<end> <file>

# Full file history, with patches, through renames
git log --follow -p -- <file>

# Last N commits touching the file, PR numbers visible
git log --oneline -20 -- <file>

# Extract PR numbers from a commit message
git log -1 --format=%B <commit>
```

実質的なコミットについては、`gh` で PR 本文と議論を取得する:

```bash
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

これをシードコンテキスト (ファイルパス、シンボル、コミット、PR 番号、リンクされたチケット ID) として捕捉する。調査者に渡す。

## Step 3. 並列の調査者を起動する (既定の姿勢)

**既定は完全な並列調査。**

### 検出

調査者を起動する前に、Cursor 環境から利用可能な MCP を一覧する。available-tools マップがあればそれを使う。無ければ、Cursor が公開する `mcps/` ディレクトリを調べて有効な MCP サーバを確認する。

利用可能な各 MCP を 1 つの証拠カテゴリにマップする:

1. ソース管理の履歴
2. issue / チケットトラッカー
3. 長文ドキュメント
4. リアルタイムのチームチャット
5. インフラ observability
6. エラー / 例外トラッキング
7. プロダクト分析ウェアハウス

ソース管理は git と `gh` を通じて常に利用できる。残る 6 つは、MCP 名、サーバの instructions、ツール名、リソース記述子を使って分類する。ある MCP が複数のカテゴリに当てはまりうるなら、その主要な証拠に合う方を選ぶ。曖昧なケースはカバレッジマップに記録する。

最小ではなく、完全な**カバレッジマップ**を目指す。空振りを記録すること。検索をスキップしてはならない。

同時に走るよう、マッチしたすべての調査者を 1 つのメッセージで起動する。1 つのエージェントに複数の MCP を担当させてはならない。

サブエージェントの設定 (各自):
- `subagent_type`: `generalPurpose`
- `model`: `why investigators` の行、既定は `grok-4.7-xhigh-fast`
- `readonly`: `false` (agent モード)。**readonly / Ask モードを使ってはならない。** MCP アクセスが剥がされ、MCP 依存の調査者がまるごと機能しなくなる。調査者はいずれにせよ何も書き込むべきではない。

各調査者に渡すもの:
1. `references/investigator-prompt.md` のベースプロンプト
2. 選択した MCP に対応するカテゴリのプレイブック `references/sources/<source>.md`。`references/source-playbook.md` の例から適応させる
3. **対象コードが防御的に見える場合** (null チェック、リトライ処理、タイムアウト処理、レート制限、フィーチャーフラグ、egress ガード、OOM ハンドラ) は、横断的な `references/sources/incident-postmortem.md`
4. Step 2 のコードアンカー (ファイルパス、シンボル、コミットハッシュ、PR 番号、チケット ID)
5. ユーザの元の質問

### 調査者の陣容。利用可能な証拠カテゴリごとに 1 つ

マッチする MCP があるカテゴリごとに調査者を 1 つ起動する。各自がちょうど 1 つのツールまたは MCP を担当する。

各項目には、そのカテゴリの名前と、それが独自に浮かび上がらせる「なぜ」の種類が書かれている。何が返ってくるかを知り、カテゴリが空で返ったときにギャップをどう名付けるかを知り、(証明可能に無関係というまれなケースに限り) スキップを正当化するために使う。

1. **ソース管理の調査者**。git の履歴、PR のための `gh`、コードコメント、テスト。常に起動する。唯一保証された情報源である。*レビュー中に捕捉された実装時の根拠*を浮かび上がらせるのが最も得意。

2. **issue / チケットトラッカーの調査者** (例: Linear, Jira, GitHub Issues, Plane, Shortcut の MCP)。*プロダクトまたはビジネス上の強制力*を浮かび上がらせるのが最も得意。なぜがエンジニアリングの外側にあるときに最も強い。

3. **長文ドキュメントの調査者** (例: Notion, Confluence, Google Docs, Coda の MCP)。*長文で書かれた設計判断の根拠*を浮かび上がらせるのが最も得意。なぜがコードになる前に書き出される場所である。

4. **リアルタイムのチームチャットの調査者** (例: Slack, Discord, Microsoft Teams, Mattermost の MCP)。*ドキュメントに至らなかったリアルタイムの議論*を浮かび上がらせるのが最も得意。ソース管理・チケット・ドキュメントの紙の跡が薄いときに特に重要。

5. **インフラ observability の調査者** (例: Datadog, New Relic, Honeycomb, Grafana, Splunk の MCP)。インフラ / ランタイムの視点。*コードを動機づけたインフラとランタイムの現実*を浮かび上がらせるのが最も得意。対象がインフラのシグナル (タイムアウト、リトライ、レート制限、サーキットブレーカ) に反応しているときに最も強い。

6. **エラー / 例外トラッキングの調査者** (例: Sentry, Rollbar, Bugsnag, Airbrake の MCP)。*防御的または是正的なコードを動機づけた具体的な例外とエラーの軌跡*を浮かび上がらせるのが最も得意。catch ブロック、null ガード、型チェック、リトライ、その他の防御に対して最も強い。

7. **プロダクト分析ウェアハウスの調査者** (例: Databricks, Snowflake, BigQuery, ClickHouse, dbt, Redshift の MCP)。プロダクト / データの視点。*コードを形づくったプロダクトとデータの現実*を浮かび上がらせるのが最も得意。フラグでゲートされたコード、実験駆動の出荷、データマイグレーション、「この数字はどこから来たのか」という質問に対して最も強い。

### 調査者をスキップしてよいとき

最終出力の「参照した情報源」の節に載せる**明示的で文章化された正当化**がある場合に限りスキップする。妥当な理由は 2 つ:

- この環境に**そのカテゴリに対応する MCP が無い**。これは選択ではなくギャップとして明示する。例: 「リアルタイムのチームチャットはスキップ。対応する MCP が無く、会話の記録は検索できなかった」
- **情報源が証明可能に無関係である**。「たぶん無関係」ではない。ハードルは高い。例: 「エラー / 例外トラッキングはスキップ。対象はランタイムのコードパスを持たないビルド時スクリプトである」。

スコープの見立てから、PR の説明にすでに完全な答えが含まれている単一コミットの些末な対象だと判断したなら、利用可能な 7 カテゴリすべての検索が冗長になると確認した**後に限り**、インラインで答えてよい。その旨を明示すること。これはまれであるべきだ。

## Step 4. 統合する

統合者のサブエージェントを 1 つ起動する:

- `subagent_type`: `generalPurpose`
- `model`: `why synthesizer` の行、既定は `claude-opus-5-5-max`
- `readonly`: `false` (agent モード)。統合者の品質チェックは引用を抜き取り検証し、それには MCP アクセスが要ることがある。readonly / Ask モードは MCP を剥がしてこれを台無しにする。

統合者に渡すもの:
1. 調査者の発見。空振りと、正当化付きでスキップしたカテゴリを含む
2. Step 2 のコードアンカー (ファイルパス、シンボル、コミットハッシュ、PR 番号、チケット ID)
3. ユーザの元の質問
4. `references/epistemics.md` のエピステミクスのフレームワーク
5. `references/synthesizer-prompt.md` の統合者プロンプトのテンプレート

## Step 5. 提示する

統合者の出力を受け取り、ユーザに提示する。明確さのために軽く手を入れたり、会話からコンテキストを加えたりしてよいが、**確信度の表現を書き換えてはならない**。

## 出力フォーマット

出力の構造は `references/synthesizer-prompt.md` にあるもの、すなわち The Question、The Code in Question、What We Found、What We Can Reasonably Infer、Competing Hypotheses、What We Don't Know、Sources Consulted、Confidence Summary である。必要に応じて適応させてよいが、確信度の区別は保つこと。また Sources Consulted は、何も返さなかったものやスキップしたものも理由付きで含め、調査者 1 つにつき 1 行のまま保つこと。

「参照した情報源」ブロックの後、ユーザの `why` の質問が実際にこのコードを変更する前段階であるなら、系譜の発見を、変更のプランニングに使える Preserve / Change / Avoid / Risk の制約セットに変換する。

## 避けるべきよくある失敗モード

- **直近バイアス**。最新のコミットが決定的だと思い込むこと。現在の形はしばしば、より早い多くの決定の堆積である。遡ること。

## リファレンスファイル

- `references/epistemics.md`。確信度の階層と表現ガイド。統合者はこれに従わなければならない。
- `references/investigator-prompt.md`。調査者サブエージェント用のベースプロンプトテンプレート。
- `references/source-playbook.md`。下記のカテゴリ別プレイブックを指す索引。
- `references/sources/*.md`。カテゴリごとに自己完結した例のプレイブック 1 つずつと、横断的な `incident-postmortem.md`。調査者にはそのカテゴリに合う 1 ファイルだけを渡し、利用可能な MCP に合わせて適応させる。
- `references/synthesizer-prompt.md`。統合者サブエージェント用のプロンプトテンプレート。出力フォーマットを含む。
