# Why

コードの背後にある動機と意図を調査する。対になる `how` skill は、コードが何をし、どう動くかに答える。`why` は、どんな力がその形をもたらしたかに答える。

以下の起動それぞれは、`pstack-models.mdc` ルール内のロール行と既定値を指す。`model` にはその行の値を設定する。ルールやその行が無ければ既定値を設定する。値が `auto` または `inherit-parent` の場合は `model` を未設定のままにする。Task ツールがスラッグを拒否したら既定値を使い、その旨を述べる。既定値も拒否されたら、そのエラーメッセージから同じファミリーの最も近い有効なスラッグを使う。各サブエージェントの reasoning level と fast / standard の速度は、**poteto-mode** skill の Subagents セクションに従って仕事ごとに選ぶ。

起動はすべて `generalPurpose`、`readonly: false` (agent モード)。**readonly / Ask モードを使ってはならない。** MCP アクセスが剥がされ、MCP 依存の調査者と、統合者の引用の抜き取り検証が機能しなくなる。調査者はいずれにせよ何も書き込むべきではない。

## 動作姿勢

**注意深く、慎重で、精密な調査者**として振る舞う。自分が知っていることと推論していることについて正直であること。確信度のフレームワークと表現ガイドの全体は `references/epistemics.md` を読むこと。統合者はそれに従わなければならない。

## Step 1. 対象と質問を理解する

**対象**はたいていコードの一塊、パターン、機能、または名前の付いた設計判断である。**質問**はたいてい、設計判断の根拠、トレードオフ、動機となったエッジケース、外部の制約、デッドコード、または広範な歴史のスイープのいずれかである。

対象が曖昧なとき (指示対象がはっきりしないまま「なぜこうしているのか」と聞かれた場合)、会話のコンテキスト (開いているファイル、直近の編集、カーソル位置、直前に話していたこと) から最善の推測をする。外していたらユーザが修正できるよう、自分の解釈を簡潔に述べてから進める。

## Step 2. コードのアンカーを確立する

調査者を起動する前に、シードコンテキストをインラインで組み立てる: ファイルパスと行範囲、主要なシンボル (関数名、クラス名、定数)、対象に触れた直近のいくつかのコミット、マージコミットからの PR 番号 (件名行の `(#1234)` パターン)、リンクされたチケット ID。最後に触れたコミットは `git blame -L <start>,<end> <file>`、リネームをまたぐパッチ付きの全履歴は `git log --follow -p -- <file>`、PR 番号が見える直近のコミットは `git log --oneline -20 -- <file>`、PR 番号の抽出は `git log -1 --format=%B <commit>` で得る。そのうえで、実質的なコミットについて PR 本文と議論を取得する: `gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews`。このアンカーはすべての調査者と統合者に渡す。

## Step 3. 並列の調査者を起動する

**既定は完全な並列調査。** 目指すのは最小ではなく、完全なカバレッジマップである。空振りを記録すること。検索をスキップしてはならない。

### 検出

調査者を起動する前に、Cursor 環境から利用可能な MCP を一覧する。available-tools マップがあればそれを使う。無ければ、Cursor が公開する `mcps/` ディレクトリを調べて有効な MCP サーバを確認する。

利用可能な各 MCP を 1 つの証拠カテゴリにマップする:

1. ソース管理の履歴
2. issue / チケットトラッカー
3. 長文ドキュメント
4. リアルタイムのチームチャット
5. インフラ observability
6. エラー / 例外トラッキング
7. プロダクト分析ウェアハウス

ソース管理は git と `gh` を通じて常に利用できる。残る 6 つは、MCP 名、サーバの instructions、ツール名、リソース記述子を使って分類する。ある MCP が複数のカテゴリに当てはまりうるなら、その主要な証拠に合う方を選ぶ。曖昧なケースはカバレッジマップに記録する。

マッチする MCP があるカテゴリごとに調査者を 1 つ、同時に走るよう 1 つのメッセージですべて起動する。各自がちょうど 1 つのツールまたは MCP を担当する。1 つのエージェントに複数の MCP を担当させてはならない。`model`: `why investigators` の行、既定は `grok-4.7-xhigh-fast`。

各調査者のプロンプトは、埋めた `references/investigator-prompt.md` に次を加えたもの:
- 選択した MCP に対応するカテゴリのプレイブック `references/sources/<source>.md`。`references/source-playbook.md` の例から適応させる
- **対象コードが防御的に見える場合** (null チェック、リトライ処理、タイムアウト処理、レート制限、フィーチャーフラグ、egress ガード、OOM ハンドラ) は、横断的な `references/sources/incident-postmortem.md`
- コードアンカーとユーザの元の質問

### 調査者の陣容、利用可能な証拠カテゴリごとに 1 つ

以下の各カテゴリは、「最も得意」の前に示す「なぜ」の一種類を独自に浮かび上がらせる。何が返ってくるかを知り、カテゴリが空で返ったときにギャップを名付け、(証明可能に無関係というまれなケースに限り) スキップを正当化するために使う。

1. **ソース管理** (git の履歴、PR のための `gh`、コードコメント、テスト)。常に起動する。唯一保証された情報源である。*レビュー中に捕捉された実装時の根拠*が最も得意。
2. **issue / チケットトラッカー** (例: Linear, Jira, GitHub Issues, Plane, Shortcut の MCP)。*プロダクトまたはビジネス上の強制力*が最も得意。なぜがエンジニアリングの外側にあるときに最も強い。
3. **長文ドキュメント** (例: Notion, Confluence, Google Docs, Coda の MCP)。コードになる前に書き出された*長文の設計判断の根拠*が最も得意。
4. **リアルタイムのチームチャット** (例: Slack, Discord, Microsoft Teams, Mattermost の MCP)。*ドキュメントに至らなかったリアルタイムの議論*が最も得意。ソース管理・チケット・ドキュメントの紙の跡が薄いときに特に重要。
5. **インフラ observability** (例: Datadog, New Relic, Honeycomb, Grafana, Splunk の MCP)。*コードを動機づけたインフラとランタイムの現実*が最も得意。対象がインフラのシグナル (タイムアウト、リトライ、レート制限、サーキットブレーカ) に反応しているときに最も強い。
6. **エラー / 例外トラッキング** (例: Sentry, Rollbar, Bugsnag, Airbrake の MCP)。*防御的または是正的なコードを動機づけた具体的な例外とエラーの軌跡*が最も得意。catch ブロック、null ガード、型チェック、リトライ、その他の防御に対して最も強い。
7. **プロダクト分析ウェアハウス** (例: Databricks, Snowflake, BigQuery, ClickHouse, dbt, Redshift の MCP)。*コードを形づくったプロダクトとデータの現実*が最も得意。フラグでゲートされたコード、実験駆動の出荷、データマイグレーション、「この数字はどこから来たのか」という質問に対して最も強い。

### 調査者をスキップしてよいとき

最終出力の Sources Consulted に載せる**明示的で文章化された正当化**がある場合に限る。妥当な理由は 2 つ:

- この環境に**そのカテゴリに対応する MCP が無い**。これは選択ではなくギャップとして明示する: 「リアルタイムのチームチャットはスキップ。対応する MCP が無く、会話の記録は検索できなかった」
- **情報源が証明可能に無関係である**。「たぶん無関係」ではない。ハードルは高い: 「エラー / 例外トラッキングはスキップ。対象はランタイムのコードパスを持たないビルド時スクリプトである」。

スコープの見立てから、PR の説明にすでに完全な答えが含まれている単一コミットの些末な対象だと判断したなら、利用可能な 7 カテゴリすべての検索が冗長になると確認した**後に限り**、インラインで答えてよい。その旨を明示すること。これはまれであるべきだ。

## Step 4. 統合する

統合者を 1 つ起動する。`model`: `why synthesizer` の行、既定は `claude-opus-5-5-xhigh`。渡すもの:
1. 調査者の発見。空振りと、正当化付きでスキップしたカテゴリを含む
2. コードアンカー
3. ユーザの元の質問
4. `references/epistemics.md` のエピステミクスのフレームワーク
5. `references/synthesizer-prompt.md` の統合者プロンプトのテンプレート

## Step 5. 提示する

統合者の出力をユーザに提示する。明確さのために軽く手を入れたり、会話からコンテキストを加えたりしてよいが、**確信度の表現を書き換えてはならない**。

## 出力フォーマット

構造は `references/synthesizer-prompt.md` にあるもの、すなわち The Question、The Code in Question、What We Found、What We Can Reasonably Infer、Competing Hypotheses、What We Don't Know、Sources Consulted、Confidence Summary である。必要に応じて適応させてよいが、確信度の区別は保つこと。また Sources Consulted は、何も返さなかったものやスキップしたものも理由付きで含め、調査者 1 つにつき 1 行のまま保つこと。

Sources Consulted の後、ユーザの `why` の質問がこのコードを変更する前段階であるなら、系譜の発見を、変更のプランニングに使える Preserve / Change / Avoid / Risk の制約セットに変換する。

## 避けるべきよくある失敗モード

- **直近バイアス**。最新のコミットが決定的だと思い込むこと。現在の形はしばしば、より早い多くの決定の堆積である。遡ること。
