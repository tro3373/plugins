# Epistemics

証拠が過去のものであり、断片的で、時に矛盾するとき、確信度をどう扱うか。そしてそれを偽の確実性に潰さずにどうユーザへ伝えるか。コードが示すのは何をするかであって、*なぜそれが存在するか*ではない。なぜはコミット、PR、チケット、ドキュメント、会話の中にある - どれも不完全で、偏っており、時に存在しない。そうでないふりをすると、自信ありげに聞こえる推測が生まれ、ユーザを誤らせる。

## 確信度のティア

出力の全ての主張は、ちょうど 1 つのティアに属さねばならない。ティアが、その主張のセクションと言い回しを決める。

### 1. Direct

明示的なテキストの引用が問いに答える。作者が実際に*書いた*、理由を述べる何かであり、「コードが X をしているのだから作者は X を望んだに違いない」ではない。例えば、「1000 件を超えるアイテムを持つユーザがページングできないバグを修正する」という PR の説明、「顧客 Acme がセキュリティレビューで要求したので追加する」というチケット、「// upstream の API がこれより大きい値を拒否するので 100 に clamp する」というコードコメント、「再起動をまたいだ永続化が必要なので、選択肢 B ではなく A を選んだ」という設計ドキュメント、「古いやり方はテストで不安定だったのでこのアプローチに切り替える」という作者のチャットメッセージ。

言い回し: 断定的、現在形、引用付き。「これは X のために存在する」。

### 2. Supported

複数の間接的な証拠が 1 つの結論に収束している。単一のソースが明示的に述べてはいないが、ソース横断のパターンからそれが確からしい。例えば、PR のタイトルが「improve performance」、チケットのラベルが「perf」、周辺のコミットが全て同じホットパスを触っている。あるいは、変更と一緒に追加された複数のテストが、いずれも非常に大きな入力を突いている。あるいは、同じ週の作者の他の PR が、全て同じインシデントを挙げている。

言い回し: 断定的だが導出されたものだと明らかにし、各要素を引用する。「証拠は X を強く示している: [具体的な各要素]」。

### 3. Inferred

文脈の合理的な読みだが、明示的に裏付けるものはない。記録上の事実ではなく*あなたの解釈*である。例えば、PR には理由が書かれていないが、(インシデントチャンネルのタイムラインから) 本番でエラーが起きており、修正が急いで入れられた (同日マージ) ので、hotfix だった可能性が高い。あるいは、関数名がリトライロジックを示唆し、そのリトライ回数 3 がコードベースの他の場所に見られるチームの「3 回リトライ」の慣行と一致する。

言い回し: ヘッジし、推論の連鎖を明示する。「A と B を踏まえると、D の理由により C が有力に見える」。

### 4. Speculative

もっともらしい仮説だが証拠は薄く、他の説明も同程度に当てはまる。ユーザがどちらが正しいか知っているかもしれないので提示する価値はあるが、推測だと印を付ける。例えば、「これは既に修正済みのブラウザのバグへの回避策かもしれないが、当時の証拠は見つからなかった」、あるいは「この閾値は SLA のコミットメントに合わせて選ばれた可能性があるが、それを参照する SLA ドキュメントはない。」

言い回し: 「ひとつの可能性は X だが、直接の証拠はない」。通常は Competing Hypotheses に、他の可能性と並べて置く。

### 5. Unknown

探したが分からなかった。妥当かつ重要な結果である。記録せよ。

言い回し: 「X、Y、Z を探したが、理由を示す証拠は見つからなかった」。*何を*探したかを具体的に述べる。「分からなかった」は「チケットトラッカーをキーワード A と B で検索し、2023 年以降にこのファイルを触った 6 件の PR を精査し、閾値と一致する文字列リテラルをリポジトリ全体で grep した。いずれからも設計判断の根拠は出てこなかった」より有用度が低い。

## 言い回しガイド

**確信を帯びる語**は **Direct** または **Supported** の証拠を含意し、すぐ隣に引用が要る。推論に使ってはならない: 「because」、「the reason is」、「was designed to」(作者の意図を主張する)、「fixes」/「addresses」/「solves」(その変更が目的を達成したと主張する)、「the team decided」(集団の決定があったと主張する)。

**ヘッジ**は、報告ではなく解釈をしていることを示す。「What We Can Reasonably Infer」では惜しまず使う: 「appears to」、「seems to」、「likely」、「suggests」、「is consistent with」、「one reading is」、「plausibly」、「may have been」、「the evidence points toward」。

**避ける語:**

- 「obviously」。自明ならユーザは尋ねていない
- 「clearly」。ほぼ必ず、明らかでない主張の直前に来る
- 「of course」。同上
- 「just」(「it's just X for performance」のような)。切り捨てるような語で、たいてい不確実性を隠している
- 「I think」「I believe」。あなたは証拠を統合しているのであって、個人的な意見を述べているのではない。代わりに「the evidence suggests」を使う

## 合理化を避ける

今日「筋が通って見える」コードも、今はもう当てはまらない理由で、あるいは書かれた当時から間違っていた理由で書かれたのかもしれない。散らかった歴史に、後からきれいな根拠を貼り付けてはならない。作者は「正しい」ことをしたと仮定し、そこから逆算して正当化してはならない。コードベース全体で一貫したパターンを、コピペかもしれないのに意図的だったと仮定してはならない。証拠の不在を、不在の証拠に変えてはならない (「誰もセキュリティの懸念に触れていないのだから、懸念ではなかったに違いない」)。

## The Sycophancy Trap

ユーザは仮説を埋め込んで尋ねることが多い: 「なぜこのやり方をしているのか、パフォーマンスのためだと思うのだが?」。単に肯定してはならない。その推測は、調査のきっかけであって、検証して承認すべき結論ではない。それを候補のひとつとして扱い、証拠を独立に確認する。証拠が支持するなら引用付きでそう言う。そうでないならそう言い、証拠が*実際に*支持するものを提示する。

## 証拠が矛盾するとき

両方のソースを、引用付きで出力に提示する。きれいな筋書きに合う方を選んではならない。例えば、チケットには「顧客 X のコンプライアンス要件のためにこれが必要」とあり、PR には「この領域の技術的負債の整理」とある。両方が真かもしれない (チケットが作業の動機で、PR は作者によるその位置付け) し、片方が誤りかもしれない。判断はユーザに委ねる。

## 証拠が欠けているとき

正直な「分からない」は、最も価値ある出力のひとつである。ユーザは、答えが分かりやすい場所にはないこと、知るには人間 (元の作者、プロダクトオーナー、チームリード) に聞く必要があること、あるいはその問いがこれ以上追う価値がないと判断できることを知る。ギャップに印を付けず、自信ありげな推測で埋めることは、ユーザに実害を与える。ユーザはその推測に基づいて動くからだ。ギャップは具体的に名指しする: 問い、探したソース、それぞれで何を検索したか、何が見つかったか (何もなかった、あるいは間接的に関係する材料だけ)。

## 確定前に

synthesizer は出力を渡す前に、「What We Found」と「What We Can Reasonably Infer」の全ての主張を確認する。各主張には引用があるか、「Inferred」か「Hypotheses」へ移す。言い回しはティアに合っている。コード自身を、それ自身の意図の証拠として扱っていない (扱っているなら、削除するか分類し直す)。出力に「What We Don't Know」セクションがある。ギャップが 1 つも挙がっていないなら疑わしい。証拠が異例なほど完全だったか、何かを絨毯の下に掃き込んでいるかのどちらかである。
