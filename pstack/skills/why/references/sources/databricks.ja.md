# Databricks のアナリティクスとシステムテーブル

## この情報源に含まれるもの

Databricks はプロダクトアナリティクス、データパイプライン、ウェアハウスのテレメトリを担う層である。Datadog を補完する。Datadog が*インフラ / ランタイム*の視点なのに対し、Databricks は*プロダクト / データ*の視点だ (ユーザが何をしたか、どの実験が走ったか、機能の利用がどう推移したか、閾値の定数がどこから来たか)。

- **プロダクトアナリティクスのイベント。** `your_warehouse.events.analytics_track_event` (生データ) と、イベントごとに型付け・重複排除された dbt モデル `<your_analytics_db>.<schema>.<table>`。ユーザの行動: 機能の呼び出し、クリック、accept / reject、送信、クライアントが報告したエラー。
- **使用量と課金のイベント。** `your_warehouse.events.usage_event` / `<your_analytics_db>.<schema>.stg_usage_events`、および `your_warehouse.events.raw_model_event` / `<your_analytics_db>.<schema>.stg_raw_model_events`。コストや量に駆動される判断のために使う。
- **実験 / フィーチャーフラグのデータ。** 露出と結果のテーブル。**スキーマは企業ごとに異なる。** 名前を仮定する前に `SHOW TABLES` で探る。
- **システムテーブル。** `system.query.history`、`system.compute.warehouses`、`system.billing.*`、`system.access.audit`。「このクエリは高価だったか?」「これを実行した人はどれくらいいたか?」「ウェアハウスの負荷はいつ跳ねたか?」に答える。
- **dbt のリネージ。** `<your_analytics_db>.<schema>` のモデルは、どのパイプラインがあるテーブル / フィールドに依存しているかを明かす。上流の変更は、しばしば消費側コードの変更の動機になっている。
- **Databricks のノートブック。** エンジニアがコード変更の前に書いた探索的な分析。**SQL MCP からはクエリできない。** 設計判断の根拠がノートブックにあると疑うなら、それをギャップとして名指しする。

## 検索の仕方

Databricks SQL MCP を使う。主要ツールは `execute_sql_read_only`。`statement_id` が返ってきたら、再実行するのではなく `poll_sql_result` でポーリングする。

**クエリの前に方向を掴む。** スキーマは企業ごとに異なる。テーブル名を信じる前に探ること。

```sql
SHOW TABLES IN <your_analytics_db>.<schema> LIKE '*<keyword>*';
DESCRIBE TABLE <your_analytics_db>.<schema>.stg_<event>;
```

**すべてのクエリに時間の範囲を切る。** これらのテーブルは巨大で、制約のないスキャンはタイムアウトする。`_timestamp` (イベント) または `start_time` (`system.query.history`) でフィルタし、出荷日を挟む窓 (通常は前後 30 日程度) を指定する。強い理由があるときだけ広げる。

**生テーブルより型付き dbt モデルを優先する。** `<your_analytics_db>.<schema>.<table>` は重複排除済み・型付き・liquid clustering 済みである。`your_warehouse.events.analytics_track_event` には重複があり、`properties_json` は型無しだ。モデル名のパターンは `stg_<source>_<event_name_with_underscores>` で、`<source>` は `app`、`backend`、`website`、`cli` のいずれか。パターンだけで一意に定まらないときは `SHOW TABLES` で正確なモデル名を確認する。生テーブルに落ちるのは、まだ dbt モデルが無いとき、または dbt のリフレッシュ遅延の内側にあるイベントが必要なときだけだ。

**型付き dbt モデルのカラム規約** (これを知っていれば `DESCRIBE` の往復を省ける):

- `_timestamp`、`_id`、`_auth_id`、`_request_id`、`event_name`。すべてのモデルに標準で存在する
- `properties_<name>`。型付き・アンダースコア区切りのイベントプロパティ (`properties_entrypoint`、`properties_size_bytes`、…)
- `context_team_id`、`context_client_version`、`context_country`、`context_client_os`。事前に抽出されたクライアントのコンテキスト

### 実りやすい調査パターン

対象に合うテーブルとカラムの組み合わせを選ぶ。

1. **イベント利用の推移。** PR のマージ日を挟む ±30 日の窓で、該当する `stg_*` モデルの日次カウントを取る。マージから 1 - 2 日以内にゼロから安定した量へ跳ね上がるステップ関数は、その PR が機能をローンチしたことの強い状況証拠だ。ゼロへの減衰は非推奨化か削除を示唆する。
2. **ガードレール / 防御的チェックの由来。** PR の*前*の 14 日間について、該当する `properties_<name>` カラムの分布 (中央値 / p99 / 最大) を取る。対象の閾値定数と一致する p99 は、その数字がデータから選ばれたことを示唆する。
3. **実験 / フィーチャーフラグの照会。** `SHOW TABLES ... LIKE '*experiment*'` で露出テーブルを見つけ、PR の日付付近における該当フラグキーのバリアント別露出数を引く。
4. **マイグレーション・バックフィル・性能書き換えに対するクエリ履歴の証拠。** `system.query.history` を `statement_text ILIKE '%<table_or_symbol>%'` で絞り、`start_time` の窓をきつく切ると、その変更の動機になったであろう高価なクエリが浮かび上がる (`total_duration_ms` でソートするか、`SUM(read_bytes)`、`COUNT(*)` で集計する)。
5. **dbt のリネージ。** 対象が `<your_analytics_db>.<schema>` のモデルから読む、あるいはそこへ書き込むなら、そのモデル自身の git 履歴 (このリポジトリ内) に設計判断の根拠があることが多い。その手掛かりは自分で追わず、git の調査担当へ渡す。

## ここでの良い証拠とは

上のパターンの形に加えて、次のようなもの。

- エラーを分類するイベントのカウントが、防御的コードの PR の後の数日でほぼゼロまで落ちる。その PR がそのエラークラスを解消したことを示唆する
- 露出テーブルの行が、対象のフィーチャーフラグキーを名指しし、PR の出荷日付近に「shipped」/「concluded」の判断を持っている

## よくある落とし穴

- **計装されている ≠ 原因である。** イベントが存在するということは、誰かがそれを記録する程度には気にしていたということであって、対象のコードがそのイベント*ゆえに*存在するということではない。因果を主張する前に、git の調査担当が挙げた PR / コミットの引用と組み合わせること。
- **静かな計装の変更。** イベント量のステップ関数は、ユーザの行動が変わったのではなく、新しいイベントが記録され始めただけかもしれない。立ち上がりを機能ローンチのシグナルと読む前に、同じ窓の計装 PR を確認する。
- **スキーマのドリフト。** イベントのプロパティは進化する。今日の型付き dbt モデルにあるカラムが、対象が書かれた当時には存在しなかったかもしれない。古いデータでは、そのプロパティが生の `properties_json` の中にしか無いこともある。
- **dbt のリフレッシュ遅延。** `<your_analytics_db>.<schema>.*` はスケジュールで (多くは毎時 / 毎日) 再構築される。直近数時間のイベントには `your_warehouse.events.*` にフォールバックし、`_id` で重複排除する。
- **企業ごとに異なるテーブル。** 実験、フィーチャーフラグ、課金、使用量のテーブルはまちまちだ。存在を確認していないテーブルからの結果を報告するのは、典型的な失敗パターンである。まず `SHOW TABLES` / `DESCRIBE TABLE` で探ること。
- **保持期間の崖。** 対象の窓がテーブルの保持期間や dbt モデルの作成日より前なら、それはヌルの結果ではなく*ギャップ*である。統合担当が「結果なし」を「活動なし」と読まないよう、明示的に名指しする。
- **ノートブックはクエリできない。** SQL MCP は Databricks のノートブックを見られない。設計判断の根拠がノートブックにあると疑うなら、ギャップとして返す。

## 何を返すか

関連する発見ごとに、次を返す。
- 種別 (プロダクトイベント / 実験の露出 / 使用量または課金のイベント / システムテーブルの行 / dbt モデル)
- 完全修飾のテーブル名と、実際に実行したクエリ
- クエリした時間の窓
- コンパクトな数値サマリ (カウント、パーセンタイル、初出 / 最終の時刻)。**生の行をダンプしてはならない。**
- 対象の出荷日との時間的な相関 (例: 「初回の行は 2024-08-15。PR #49074 は 2024-08-14 にマージ」)
- 関連性と強さ: direct / circumstantial / weak
