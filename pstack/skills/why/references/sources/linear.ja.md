# Linear Tickets

## このソースに含まれるもの

- 機能・バグとその動機を記述した issue
- issue に添付されたプロジェクトドキュメント (多くは PRD や仕様)
- 親 / 子 issue の関係 (より広いイニシアチブ => 具体的なチケット)
- issue へのコメント (補足、スコープ変更、「なぜこれをやるのか」の設計判断の根拠)
- 動機の種類を示すラベル (例: `compliance`、`customer-request`、`perf`)
- スコープ変更を説明するステータス更新
- 添付ファイルとリンクされた GitHub PR

Linear は、プロダクト / ビジネスの文脈がしばしば存在する場所である - 「顧客 X が求めたからこれをやる」「これは Q3 のコンプライアンス施策のためだ」という層である。

## 検索方法

Linear MCP を使う。

1. **リンクされたチケットから始める。** 起点のコミットや PR がチケット ID (例: `ENG-1234`、`[BUG-567]`) を参照しているなら、まず `get_issue` でそれを取得する。コメントを含めて issue 全文を読む。
2. **キーワードで関連 issue を列挙する。** `list_issues` で機能名、鍵となるシンボル、ビジネス用語のテキスト検索をする。複数の言い回しを試す。
3. **issue のツリーを辿る。** 子 issue に行き当たったら親を取得する。子 issue は戦術的であり、「なぜ」は親が持っていることが多い。
4. **プロジェクトドキュメントを読む。** issue がプロジェクトに属するなら `get_project` を使い、添付ドキュメントを確認する。仕様と設計判断の根拠が最も多く記録されているのはプロジェクトレベルのドキュメントである。
5. **ラベルとマイルストーンを確認する。** ラベルは動機のカテゴリ (customer-request、incident-followup、compliance) を示唆する。マイルストーンは作業を締め切りに結び付けており、そこから動機が見えることが多い。

## ここでの良い証拠とは

- ビジネス上の問題を述べた issue の説明: 「顧客 Acme は SOC2 監査のため X を必要としている」
- 決定を記録したコメント: 「アプローチ A は billing サービスに手を入れる必要があるため、B で行くことにした」
- イニシアチブらしいタイトルの親 issue: 「Q3 Enterprise Readiness」「Reduce Payment Failures」
- 添付された PRD や仕様
- `customer:acme`、`incident-followup`、`compliance`、`perf-regression` のようなラベル

## よくある落とし穴

- **スコープのドリフト。** PR が参照しているチケットは、いったんクローズされて別のスコープで再オープンされたかもしれない。履歴全体を読む。
- **形骸化したテンプレート。** 「Why」セクションを必須にしているが定型文で埋めているチームもある。汎用的な文言 (「ユーザ体験の改善」) はおそらく本当の答えではない。
- **古いチケット。** 古いチケットは、その後変わった計画のあるバージョンを反映していることが多い。日付を確認し、コードの出荷日と突き合わせる。
- **重複クローズの連鎖。** duplicate-of の関係を辿って正典のチケットまで遡る。
- **非公開ワークスペースの内容。** issue にアクセスできないなら、推測せずにギャップとして記録する。

## 何を返すか

関連する各チケットについて:
- チケット ID とタイトル
- 説明やコメントから引用した問題 / 動機 (言い換えない。synthesizer が引用するには正確なテキストが要る)
- ラベル、親 issue、プロジェクト
- 作成者、作成日、クローズ日
- 可能ならチケットへのリンク
