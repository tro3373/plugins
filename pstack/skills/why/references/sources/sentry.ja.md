# Sentry のエラー履歴

## この情報源に含まれるもの

Sentry はうまくいかなかったことのアーカイブである。防御的なコード、訂正的なコード、エラーハンドリングのコードについては、直接の動機を保持していることが多い。誰かにチェック、catch、リトライ、フォールバックを追加させた具体的な例外、スタックトレース、頻度である。

- **Issues.** グルーピングされたエラー。件数、初回/最終検知のタイムスタンプ、影響を受けたリリース、コメントを持つ
- **Events.** 1 つの issue 内の個別のエラー実例 (スタックトレース、タグ、ユーザコンテキスト)
- **Releases.** 関連する issue を伴うデプロイ記録 (「どのバージョンがこれを直したか?」に有用)
- **Replays.** ユーザに見えるエラーのセッション記録 (有効な場合)
- **Profiles.** パフォーマンスプロファイリングのデータ (「なぜ」にはあまり役立たず、「どれだけ遅いか」向け)
- **Issue のコメントとアサイン.** 根本原因についてのエンジニアのメモを含むことがある

Sentry が提供する最も価値あるものは**時間的な相関**である。「issue X は 2024-01-02 に作成され、1 日 500 events でピークを迎え、2024-01-15 のリリース v2.14.0 以降は出なくなった。そのリリースこそが防御的チェックを出したものだ」。

## 検索の仕方

Sentry MCP を使う。

1. **方向を定める。** project slug と organization が分からない場合:

   ```
   find_organizations
   find_projects
   ```

2. **対象に関連する issue を検索する。**

   ```
   search_issues (natural language, e.g., "errors in PaymentService timeout", "unhandled exceptions in uploadFile")
   ```

   良いクエリの構成要素: 対象が処理している例外クラス名、対象の関数名やクラス名、対象がチェックしているエラーメッセージ文字列、対象のファイルパス。

3. **リリースと時間ウィンドウで絞る。**

   ```
   search_issue_events (filter by release, time, environment, trace ID, tags)
   get_issue_tag_values (for an issue, see distribution across versions, users, environments)
   ```

   疑わしい issue については、以下を確認する:
   - **初回検知 (First seen).** そのエラーはいつ現れ始めたか?
   - **最終検知 (Last seen).** いつ止まったか? 対象が出荷された日付と一致するか?
   - **影響を受けたリリース.** どのバージョンで発生したか? どれが修正か?
   - **頻度の推移.** スパイクした後、解消したか?

4. **文脈のためにイベント全体を取得する。**

   ```
   get_sentry_resource (pass a Sentry URL or type+ID)
   ```

   スタックトレースは対象のコードを通っているか? タグと breadcrumb は、対象が防御している条件と一致するか?

5. **対象の近くに着地したリリースを確認する。**

   ```
   find_releases (around the commit date of the target)
   ```

   リリースバージョンと PR のマージ日を突き合わせる。

6. **Seer は控えめに使う。**

   ```
   analyze_issue_with_seer
   ```

   Seer は AI による根本原因分析を生成する。仮説生成器としては有用だが、推論として扱い、権威あるものとしては扱わない。実際のイベントとスタックトレースが一次証拠であり、Seer の物語は二次的である。

## ここでの良い証拠とは

- **初回検知**が対象の PR の直前で、**最終検知**がその直後である issue。対象がこのエラーに対処したことを示唆する
- 対象の関数を通る、あるいはそこに着地するスタックトレース。防御されている厳密な失敗モードを示す
- 修正について述べた PR 作成者による issue へのコメント
- Sentry の issue URL または ID を参照している、対象の PR 説明文やコミットメッセージ
- イベント数が多く、対象を含むリリース以降に止まっている issue

## よくある落とし穴

- **グルーピングのずれ。** Sentry はエラーを fingerprint でグルーピングする。リファクタやリネームにより「同じ」エラーが新しい issue ID の下で追跡されることがある。issue が突然終わっている場合、そのエラーは単に再グルーピングされただけかもしれない。直後に新しい issue が無いか確認する。
- **リリースの相関はノイズが多い。** 1 つのリリースには多くのコミットが含まれる。issue が v2.14.0 で止まったからといって、対象がそれを直した証明にはならない。同じリリース内の別の変更が直したのかもしれない。対象の厳密なコミットと突き合わせる。
- **静かな修正。** 防御的コードのおかげではなく、上流が変わったためにエラーが止まることもある。相関は修正を示唆するが、誰が直したかを証明しない。
- **Resolved != fixed.** issue はコード変更なしに手動で「resolved」にできる。`resolved` は人間が付けたマーカーとして扱い、コードが直した証拠として扱わない。
- **Seer のハルシネーション。** Seer は自信ありげでいて正しくない説明を生成しうる。主張をするときは、実際のイベント、スタックトレース、タイムスタンプに立ち返る。
- **サンプリング.** プロジェクトによってはイベントを強くサンプリングしている。イベント数が少ないのは、稀なエラーではなく単にサンプリング率が高いだけかもしれない。疑わしいときは、その欠落を書き添える。

## 何を返すか

関連する issue ごとに:
- Issue ID とタイトル
- Project と organization
- 初回検知 / 最終検知のタイムスタンプ
- イベント数 (分かればサンプリング率も)
- 影響を受けたリリース
- 対象との関連を示す代表的なスタックトレースの抜粋 (要約ではなく逐語の抜粋)
- 対象の出荷日との初回/最終検知の相関
- issue へのリンク
- 作者のコメントや解決ノート
