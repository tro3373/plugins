# Notion のドキュメント

## このソースに含まれるもの

- PRD (プロダクト要求仕様書)
- 技術仕様と RFC
- アーキテクチャ決定記録 (ADR)
- 設計レビューの議事録
- ドメインの文脈を持つチームページ
- インシデントのポストモーテム
- 防御的なコードの説明になりうる runbook
- 優先度を定める戦略ドキュメント

Notion は、「なぜ」がコードになる前に長文の形で置かれていることが多い場所だ。重要な機能には、たいていドキュメントがある。

## 探し方

Notion MCP を使う。

1. **`notion-search` でのキーワード検索。** 次を試す:
   - 機能名
   - 対象コードの主要なシンボル / クラス名
   - 著者のハンドル (設計ドキュメントはコードが着地する前に書かれることが多い)
   - エラー文字列や、ユーザから見える用語
   - コードがいつ出たか分かっているなら、期間で区切ったクエリ
2. **`notion-fetch` で候補ページを取得する。** プレビューではなく全文を読む。設計判断の根拠はドキュメントの中ほどに埋もれていることが多い。
3. **バックリンクと子ページを辿る。** 設計ドキュメントには、検討した代替案、付録、実装メモのサブページがあることが多い。
4. **関連するデータベースを確認する。** `notion-query-data-sources` と `notion-query-meeting-notes` は、その決定を議論した議事録を浮かび上がらせられる。
5. **著者ごとのスペースを探す。** PR の著者が個人のノートブックを持っているなら (一部の会社ではよくある)、コードに先立つ探索的な思考がそこにあるかもしれない。

## ここでの良い証拠とはどんなものか

- 対象コードの目的と一致する "Problem statement" または "Motivation" のセクションを持つ PRD
- "Alternatives considered" または "Rejected approaches" のセクション
- 対象コードを、特定のインシデントに対する修正として名指ししているポストモーテム
- 「Y なので X に決めた」と記録され、PR と同じ著者 / 日付の範囲に結び付く議事録
- 非自明に埋められた ADR のテンプレート (status、context、decision、consequences)

## よくある落とし穴

- **古びたドキュメント。** 仕様は実装より前に書かれ、更新されないことが多い。そのドキュメントは、後に変更された計画を記述しているかもしれない。実際の PR と突き合わせる。
- **ドキュメントと現実の乖離。** 仕様は「X をやる」と言っているのに、コードは実際には Y をやっていることがある。その食い違いを指摘する。統合役が矛盾を表に出す。
- **形式的なテンプレート。** 組織によっては "Why" のセクションが必須で、それが中身のない文言で埋められる。具体性を探す。
- **どこからもリンクされていないドキュメント。** 最も関連の深いドキュメントが、どこからもリンクされていないことがある。広めのキーワード検索が助けになる。
- **複数の草稿。** 1 つのトピックに複数のドキュメントがあるなら、確定したものか、最も新しく更新されたものを見つける。日付を確認する。
- **アクセス制限されたページ。** ページにアクセスできないなら、それを欠落として書き留める。

## 何を返すか

関連する各ドキュメントについて:
- タイトルと URL
- 著者と最終更新日
- 動機の記述 (逐語の引用)。ページ / セクションの位置を添える
- 関連するリンク先のページ (統合役が引用できるように)
- そのドキュメントが確定版か草稿か
