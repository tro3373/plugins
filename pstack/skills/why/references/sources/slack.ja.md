# Slack の会話

## このソースに含まれるもの

- 問題と決定のリアルタイムな議論
- 火消しの最中に決定が下されたインシデントチャンネル
- トレードオフが議論された設計ディスカッションのスレッド
- ドキュメントに残らなかった、シニアエンジニアが答えた質問
- 何かが見直された理由を説明する、マージ後の議論
- DM (通常は検索できない。それを前提にスコープを決める)

Slack は、特にドキュメントを書くほどではない小さな変更において、*本当の*決定が下された場所であることが多い。同時に最も儚いソースでもある。スレッドは削除され、チャンネルはアーカイブされ、検索品質は時間とともに劣化する。

## 検索の仕方

Slack の MCP ツールはまちまちだ。どの Slack MCP が使えるかを確認し、まずそのツールスキーマを調べる。`mcp_auth` が必要かもしれない。認証に失敗したら、止めてその欠落を報告する。

1. **著者で絞った検索。** PR のマージ日前後の、PR 作者によるメッセージ。スコープを劇的に絞り込め、当たりを引くことが多い。
2. **機能名と主要シンボルのキーワード検索。** 綴り間違いやくだけた言い回しも含める。
3. **PR の URL 検索。** レビューや議論の際、Slack には PR がリンクされることが多い。PR の URL (または単に `/pull/<number>`) を検索する。
4. **エラー文字列の検索。** コードが特定のエラーを扱っているなら、そのエラー文字列を検索する。インシデントのスレッドが浮上することが多い。
5. **チャンネルを絞った検索。** ありそうなチャンネルに絞る:
   - `#eng-*`。エンジニアリングの議論
   - `#proj-*`。プロジェクトのチャンネル
   - `#incident-*` / `#sev-*`。インシデントのチャンネル
   - 所有チームのチーム固有チャンネル
   - デザインレビューのチャンネル
6. **スレッドの走査。** 関連するメッセージを見つけたら、スレッド全体を取得する。決定はしばしば返信の中にある。

## ここでの良い証拠とは

- トレードオフが明示的に議論されたスレッド ("I was going to use A but B is better because...")
- そのコードが防いでいるバグを記述したインシデントチャンネルのメッセージ
- レビュワーからの質問と、作者またはリードによる権威ある回答
- 決定が下された会議への言及
- 顧客の要望を説明するプロダクトマネージャや顧客対応エンジニアからのメッセージ

## よくある落とし穴

- **チャンネル考古学の限界。** ごく古いメッセージは保持ポリシーにより消えている可能性がある。ある日付より前に何も見つからないなら、その保持の断崖を記録する。
- **検索できない DM。** 多くの決定は検索できない DM で起きる。それらは取りこぼす。既知の限界だ。
- **憶測の冗談を「決定」と見なすこと。** Slack はくだけている。"Lol just do the thing" は、たとえコミットの直前にあっても決定ではない。熟慮された議論を探す。
- **単一メッセージでの文脈の崩壊。** スレッドが無いと、単一のメッセージは文脈の中とは違って読めることが多い。常にスレッドを取得する。
- **認証の失敗。** MCP が認証されていないなら、止める。発見をでっち上げない。Slack が検索できなかったと報告する。

## 何を返すか

関連する各スレッドについて:
- チャンネル名
- パーマリンクまたはスレッド ID
- 参加者
- 議論の日付範囲
- 主要な引用 (逐語) と帰属
- 文脈: どのスレッド / インシデント / 議論の一部だったか
