# インシデントとポストモーテムの文脈

独立したソースではなく、**横断的な切り口**だ。インシデントはしばしば防御的なコードの動機になる (「X の障害の後にこのチェックを足した」)。だから対象が防御的に見えるなら (null チェック、リトライのロジック、タイムアウト処理、レート制限、フィーチャーフラグ)、利用できるすべてのソースを横断して、インシデントの履歴を狙って探す:

- **Notion**: 対象のファイル、機能、エラー文字列に言及しているポストモーテムを検索する
- **Linear**: `incident`、`sev-*`、`postmortem-action-item`、`reliability` のラベルが付いたチケットを探す
- **Slack**: 対象コードが追加された日付の周辺で `#sev-*` と `#incident-*` のチャンネルを検索する
- **Git**: "fix for incident"、"add defensive check"、"revert" の後に "re-apply with..." が続く、といったメッセージのコミットは強い信号だ
- **Datadog**: タイムライン付きの正式なインシデント記録には `search_datadog_incidents`。ポストモーテムのアクションアイテムとして作られたダッシュボードやモニタも
- **Sentry**: first-seen / last-seen の窓が対象の PR の出荷日と揃う issue。対象を通るスタックトレース
- **Databricks**: エラー状態を分類するプロダクト分析のイベント (クライアントから報告された失敗、ユーザから見えるリトライのイベントなど) は、インシデントの期間中に急増することが多い。対象の PR が出た後にそのイベント数が落ちることは、Datadog / Sentry の信号がノイジーな場合でも、対象コードがユーザから見える症状を解消したという状況証拠になる。

インシデントへのリンクを見つけたら、ポストモーテムの全文を取得する。ポストモーテムには通常、コードの変更に直接結び付く "Action Items" のセクションがある。複数のソースが互いを裏付けるとき (Datadog のインシデント ID が Linear のチケットに現れ、それが Notion のポストモーテムに現れ、それが対象の PR にリンクする Slack のスレッドに現れ、さらに修正後に Databricks のエラーイベント数が落ちる)、その証拠はとりわけ強い。

コードの防御的な性格ゆえにインシデント由来という起源がもっともらしいときは、時間を割く価値がある。防御的に見えないコードでは飛ばす。
