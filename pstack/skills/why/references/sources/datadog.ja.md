# Datadog Telemetry

## このソースに含まれるもの

Datadog はランタイムの記録を保持する。計画や議論の内容ではなく、本番で実際に何が起きたかである。

- **メトリクス。** チームが計装したカウンタ、ゲージ、ヒストグラム。メトリクスが*存在すること*自体が証拠である - 誰かがこの数値を見る価値があると考えたということだ。
- **モニタとアラート。** 誰かを叩き起こすに値するとチームが判断した条件。`rate_limit_hit > 10/min` で発火するモニタは、チームがその閾値を気にしていた直接の証拠である。
- **ダッシュボード。** 選び抜かれたビュー。そのチャートは、あるサブシステムについてチームが何を重要と考えているかを教える。
- **APM のトレースとスパン。** リクエスト単位のランタイムデータ。「なぜこれが遅いのか」「なぜここでタイムアウトするのか」という問いに有用。
- **ログ。** 大量のイベント記録。防御的なコードを書く動機になったエラー条件が含まれていることが多い。
- **インシデント。** タイムラインとリンクされたポストモーテムを持つ正式なインシデント記録。
- **ノートブック。** 探索的な調査。仮説と分析が含まれていることが多い。

Datadog は「このコードが書かれた頃、本番の現実はどうだったか?」に答える。それがコードの形をしばしば説明する。

## 検索方法

Datadog MCP を使う。広く始めて、絞り込む。

1. **担当サービスを特定する。**

   ```
   search_datadog_services (filter by name or team)
   search_datadog_service_dependencies (see upstream/downstream)
   ```

2. **まずダッシュボードとモニタ。チームが何を気にしているかを教えてくれる。**

   ```
   search_datadog_dashboards (query: feature name, service name, symbol)
   search_datadog_monitors   (same queries)
   ```

   対象をカバーするダッシュボードやモニタがあれば、そのクエリと監視している閾値を記録する。その閾値が「なぜ N で頭打ちにしているのか?」の答えであることは頻繁にある。

3. **対象周辺のメトリクス。**

   ```
   search_datadog_metrics (by name pattern, e.g., the feature or symbol)
   get_datadog_metric_context (metadata: description, units, tags)
   get_datadog_metric (timeseries; "was there a spike around the PR date?")
   ```

   メトリクスの推移を対象の追加日 / 変更日と突き合わせるのは強い傍証になる: 「`payment_timeout` メトリクスは 2023-11-03 にスパイクし、リトライロジックは 2023-11-06 にマージされた」。

4. **ログ。絞る。ダンプしない。**

   ```
   search_datadog_logs (raw log patterns near the target, set use_log_patterns=true)
   analyze_datadog_logs (SQL-style aggregations, only when you need counts)
   ```

   シンボル、エラー文字列、機能名で検索する。**時間で範囲を切ったクエリを強く優先せよ** (例: 変更の前後 30 日)。ログの量は膨大であり、制約のない検索は時間を浪費し、タイムアウトすることもある。

5. **APM のスパンとトレース。**

   ```
   aggregate_spans    (stats: "how often does this endpoint fail?")
   search_datadog_spans (inspect individual spans)
   get_datadog_trace  (a specific trace ID)
   ```

   タイムアウト、リトライ、遅い経路、サービス間の挙動に有用。

6. **インシデント。**

   ```
   search_datadog_incidents (by title, team, date range)
   get_datadog_incident     (full detail for a specific incident)
   ```

   対象が防御的に見えるなら、それが追加された時期前後のインシデントを検索する。タイムラインに「X に対する防御チェックを追加」とあるインシデントは、ほぼ直接の証拠である。

## ここでの良い証拠とは

- クエリと閾値が、コードが強制している制約と一致するモニタ (コードが 100 で頭打ちにし、モニタはリクエストが 100/min を超えたときにアラートする)
- 対象の作者が作ったダッシュボードで、そのウィジェットがコードの計測対象や防御対象に対応しているもの
- コードがマージされる直前に本番でスパイクし、その後は安定していることを示すメトリクス
- 対象コード、同じシンボル、同じエラー文字列に言及しているインシデント記録
- 防御的なコードが防ぐであろう特定のエラーパターンを示し、変更前の期間にタイムスタンプが付いているログ

## よくある落とし穴

- **相関は因果ではない。** PR の前のスパイクと後の安定化は示唆的ではあるが決定的ではない。同じ期間に別の変更が入っているかもしれない。近隣の PR を確認する。
- **見つけたチャートへの過剰適合。** Datadog の可視化は人間が*作った*ものであり、その人のフレーミングを反映している。「retry success rate」という名前のチャートは、チームがリトライの成功を気にしていた証拠であって、特定の 1 行のコードが存在する理由の証拠ではない。
- **消えたテレメトリ。** メトリクスは改名・削除されることがあり、保持期間が短いこともある。該当期間のデータが見つからないなら、それは null の結果ではなくギャップである。
- **規模によるノイズ。** よくある文字列でログを検索すると数千件がヒットする。サービス、タグ、時間で徹底的に絞る。生ログをダンプするのではなく `analyze_datadog_logs` で集計する。
- **計装されている != 原因である。** メトリクスの存在は、誰かが何かを測る価値があると考えたことを教えるだけで、そのせいでコードが追加されたことを意味しない。コミット / PR の日付と突き合わせる。

## 何を返すか

関連する各項目について:
- 種別 (ダッシュボード / モニタ / メトリクス / ログパターン / トレース / インシデント / ノートブック)
- タイトルまたは名前
- リンクまたは識別子 (ダッシュボード ID、モニタ ID、メトリクス名、インシデント ID)
- オーナー / 作成者と、作成日 / 更新日
- 問いに関係する具体的な条件、クエリ、引用 (可能な限り原文どおり)
- 関連性: これが対象コードについて何を示唆するか、その結び付きはどれくらい強いか
