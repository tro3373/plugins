# プロンプトの言い方

プロンプトは意図と完了のチェックを述べる。手順はプレイブックが供給するので、仕様書より平易な数文の方が勝る。

## 入れるもの

- ゴール。何がおかしいのか、ユーザが何を望んでいるのかを言う。
- 完了のチェック。pass か fail かになるもの。「良くして」や期間はチェックではない。
- 見せてほしい証明。実際のコマンド出力、フローの動画、保存された値、before と after の数値を求める。
- ユーザが既に知っていること。症状、再現手順、ログ、リンクがあれば、エージェントの検索を省ける。
- 本当の制約。"repro first"、"don't change any code yet"、"zero behavior change"、"let me review before proceeding" は、それぞれエージェントの行動を変える。

## 入れないもの

- やり方。何を達成するかを言い、より良いやり方を見つける余地をエージェントに残す。
- skill や手順のリスト。手で書いた順序は、プレイブックなら保つ手順を落としたり並べ替えたりする。skill を名指しするのは、1 つの選択を上書きするときだけにする。
- 原因についてのユーザ自身の仮説。エージェントが問題を言い直すまでは入れない。述べられた推測は探索を狭める。

## 先に文脈を読み込ませる

- ノイズの多い報告では、何よりも先に、根底にある問題を自分の言葉で平易な英語で言い直すようエージェントに頼む。読み違いが、コードが存在する前に表に出る。
- 新しいチャットでは、そのトピックに関する以前の作業を `/recall` する。古いチャットには新しいエージェントに欠けている文脈がある。
- 馴染みの無いコードを変更する前に、`/how` に仕組みを、`/why` に理由を聞く。辿った理解のモデルを持たないエージェントは、最初にもっともらしく見えた箇所で症状を直す。
- "convince me it fixes the cause and not the symptom" のように、選択の論拠を述べるよう `/teach` に頼む。論拠は要約より確認しやすい。

## 計画の前に設計する

- 最初の設計を決して採らない。いくつかの選択肢のプロトタイプを、UI ならスクリーンショットか動画付きで求め、証拠から選ぶ。
- 未決の問いにはプロトタイプに答えさせる。抽象的な計画を敵対的にレビューしない。レビュワーは決して起きないリスクを作り出すからだ。
- 共有パッケージや API では、まず README かチュートリアルを求め、そこからコードへ遡る。そのドキュメントが、エージェントが自分を照らし合わせる目標になる。
- 計画を求めるのは設計が固まってからにする。計画の各手順はチェックで終わる。

## 追いの指示は短く

- チャットがタスクを保持していれば、"do it"、"continue"、"keep going until done" はそれだけで完結したプロンプトになる。
- 話題が変わるときは "new task" で始める。そうしないと、モードはそのメッセージを次の手順として扱う。

## 離席する前に

- "im going to bed" や "im stepping away" と言い、エージェントが質問してこないようにする。
- 完了を、どの反復でも走らせられるチェックとして書き、その述語を `/loop` に渡す。
- 名前を指定したベースから切った新しい worktree を求める。
- エージェントが止まりそうな点に先回りして答えておく。例えば "don't ask me before committing"。
- 後で監査できる決定ログを求める。
- 出口を与える: "if you're truly stuck after a few hours, stop and write up why"。

## 1 行で舵を取る

- ゴールを言い直す: "i said the goal is to repro. i did not ask for a fix yet."
- principle を名指しする: "apply prove it works. show me the real output, not the build log."
- principle の名前が効くのは、エージェントが既にそのルールを読んでいるからだ。その返答は、ルールが変えた判断を名指しする。
