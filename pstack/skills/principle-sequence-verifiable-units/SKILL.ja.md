# 作業を検証可能な単位へ並べる

作業を、それぞれが確認できる状態で終わる小さな単位の並びとして順序付け、今の単位が green になるまで先へ進まない。

**なぜ:** 壊れをそれを引き起こした単位で捕まえれば、局所化は安く済む。まとめて処理した後で捕まえた壊れは埋もれており、しかも壊れた土台の上に既にさらに積み上げてしまっている。その同じ単位を、レビュワーが再生できる届け方へ並べれば、「信じてくれ」が「red になり、次に green になるのを見てくれ」に変わる。

**実行。** 一括処理、移行、あるいは似た編集の連続では、次を始める前に各変更を検証する。各単位は前後の括りだ: 既知の良好な状態、1 つの変更、チェックの実行、そして次へ。まず綺麗な trunk へ rebase し、どのチェックも本当のベースラインに対して測るようにする。レバーが編集を行うときは単位ごとのチェックはほぼ無料だ。それでも実行する。

**デリバリ。** その作業を証明する順序でコミットと PR を積む。定石の形は、失敗するテストが先で、その上に修正が乗る形だ。他の物語の順序としては、作り替えの前の引き算、処置の前のベースライン取得、機能の前の足場がある。各コミットは単独で land でき、その並びは 1 つの論証として読める。

各チェックを本物に保つ **prove-it-works** の principle skill、そして単位ごとのチェックを安くする **build-the-lever** の principle skill に対する、順序付けの側の補完だ。
