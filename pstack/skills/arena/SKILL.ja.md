# Arena

同じタスクへの並列試行を N 個ファンアウトする。どの候補も端から端まで読む。最も強いものをベースに選ぶ。他の候補の最良のアイデアをそこへ接ぎ木する。統合された結果を検証する。

## 開始

何かを起動する前に、フェーズごとに 1 項目の todolist を開く。

1. フレーム設定
2. ファンアウト
3. クロスジャッジ
4. 選定
5. 接ぎ木
6. 検証

## フェーズ A: フレーム設定

N 個の候補は同じプロンプトを受け取る。つまりプロンプトが契約だ。

1. 各候補が作る成果物を明言する。
2. ルーブリックを導く。*この*タスクにとって成功がどう見えるかを述べ、それを 3-6 個の具体的で採点可能な基準に変える。ルーブリックはフェーズ D で選定者が使う道具だ。候補にはタスクしか見えない。
3. ランナーを選ぶ。`~/.cursor/rules/pstack-models.mdc` の `arena runners` の行を使う。そのルールまたはその行が無ければ、既定として `claude-opus-5-5-max`、`gpt-5.6-sol-max`、`grok-4.7-xhigh-fast` に 1 つずつ割り当てる。この行またはクロスジャッジの行の `auto` または `inherit-parent` というエントリは親モデルを意味するので、そのエントリでは `model` を省く。Task ツールが設定済みのエントリを拒否したら、その席はそのファミリの既定モデルで走らせ、その旨を述べる。ファミリは接頭辞で判定する: `claude-*`、`gpt-*`、`grok-*`。どのファミリにも一致しなければ `claude-opus-5-5-max` を使う。既定モデルすら拒否されたら、そのエラーメッセージから同じファミリの最も近い有効な slug を使う。arena が複数の設計方向をカバーするなら、より多く起動する。作業が判断に敏感というより生成量に律速されるなら、同じモデルを N 回使う。
4. 出力パスを割り当てる。各候補は自分専用の場所に書く (可能なら git の worktree、それが無理なら `/tmp/arena-<slug>/candidate-<n>/`)。**separate-before-serializing-shared-state** の principle skill に従う。

## フェーズ B: ファンアウト

N 個のサブエージェントを `run_in_background: true` で 1 通のメッセージにまとめて起動する。それぞれにタスク、共有された接地情報へのパス、自分専用の出力パス、そして成果物と短い設計判断の根拠の両方を出せという指示を渡す。

各根拠は、その候補が検討した代替案と、何を却下したかを挙げる。

候補が出力を作れなかったら、N-1 で進め、その脱落を統合の記録に書き留める。

## フェーズ C: クロスジャッジ

フェーズ B の候補がすべて完了した後、`~/.cursor/rules/pstack-models.mdc` の `arena cross-judge pool` の行からモデルを 1 つ選ぶ。そのルールまたはその行が無ければ、`claude-opus-5-5-max`、`gpt-5.6-sol-max`、`grok-4.7-xhigh-fast` から選ぶ。親とは別のモデルファミリを優先する。そのモデルで読み取り専用のジャッジのサブエージェントを 1 つ起動する。ジャッジはルーブリックと、パスのラベルで示された候補群を見て、基準ごとに採点し、根拠付きでベースを推薦する。ジャッジは候補そのものとではなく、フェーズ D で親が読むのと並列に走る。候補がまだ書いている最中にジャッジを起動してはならない。

## フェーズ D: ベースを選ぶ

選ぶ前に、どの候補も端から端まで読む。

全体的な感触ではなく、ルーブリックの基準ごとに各候補を採点する。クロスジャッジと突き合わせる。ベースが一致すれば、その選定は裏付けられる。食い違うなら、どちらかが偏っているか、ルーブリックが曖昧だったということだ。決める前に双方の根拠を読む。

将来の保守者が不変条件を壊さずに最も容易に拡張できるのはどの候補か、でベースを選ぶ。2 つが互角に感じられるときは、Laziness Protocol に従って、より綺麗な境界か、より小さい API を優先する。

選定とその理由を、クロスジャッジの評決も含めて、ベースの成果物と並べた短い統合ノートに記録する。

## フェーズ E: 接ぎ木

敗れた各候補をもう一度歩き、ベースへ移植する価値があるものを見極める。信号は通常、候補 1 つにつき 1 つか 2 つであって、その大半ではない。

**redesign-from-first-principles** の principle skill に従い、各接ぎ木は手で織り込む。機械的に貼り付けない。結果は 1 つのメンタルモデルの下で一貫していなければならない。

何を、どの候補から接ぎ木したか、そして何をなぜ却下したかを記録する。

N 個の候補が同じ形に収束したなら、それは強い合意の信号だ。収束を記録に書き留め、合意された形を出す。接ぎ木は要らない。N 個の候補が大きく発散したなら、フェーズ A の仕様が足りなかったということだ。発散を平均するのではなく、枠を組み直して再実行する。

## フェーズ F: 検証

**prove-it-works** の principle skill に従い、統合された成果物は他のどの出力とも同じ精査に耐えなければならない。

検証が arena では捕まえられなかった問題を露わにしたなら、フェーズ A が間違っていたか (枠を組み直して再実行)、ある候補はそれを捉えていたのに接ぎ木を見落としたか (フェーズ E に戻る) のどちらかだ。取り繕わない。

## 出力

統合された成果物 1 つ。それと並ぶ短い統合ノート 1 つ。ノートにはベース、接ぎ木 (元となった候補付き)、却下、あれば脱落、そして検証結果を挙げる。
