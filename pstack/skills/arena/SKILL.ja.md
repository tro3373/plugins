# Arena

何かを起動する前に、フェーズごとに 1 項目 (フレーム設定、ファンアウト、クロスジャッジ、選定、接ぎ木、検証) の todolist を開く。

## フェーズ A: フレーム設定

どの候補も同じプロンプトを受け取る。つまりプロンプトが契約だ。

1. 各候補が作る成果物を明言する。
2. ルーブリックを導く。*この*タスクにとって成功がどう見えるかを、3-6 個の具体的で採点可能な基準にする。ルーブリックはフェーズ D で選定者が使う道具だ。候補にはタスクしか見えない。
3. ランナーを選ぶ。`~/.cursor/rules/pstack-models.mdc` の `arena runners` の行を使う。そのルールまたはその行が無ければ、既定として `claude-opus-5-5-xhigh` と `grok-4.7-xhigh-fast` に 1 つずつ割り当てる。この行またはクロスジャッジの行の `auto` または `inherit-parent` というエントリは親モデルを意味するので、そのエントリでは `model` を省く。Task ツールが設定済みのエントリを拒否したら、その席はそのファミリの既定モデルで走らせ、その旨を述べる。ファミリは接頭辞で判定する: `claude-*`、および `grok-*` (`cursor-grok-*` と `composer-*` を含む)。拒否された `composer-*` のエントリは `grok-4.7-xhigh-fast` で走らせる。どのファミリにも一致しなければ `claude-opus-5-5-xhigh` を使う。既定モデルすら拒否されたら、そのエラーメッセージから同じファミリの最も近い有効な slug を使う。arena が複数の設計方向をカバーするなら、ランナーをより多く起動する。作業が判断に敏感というより生成量に律速されるなら、同じモデルを N 回使う。各サブエージェントの推論レベルと fast か standard かの速度は、**poteto-mode** skill の Subagents 節に従い、作業に合わせて選ぶ。
4. 各候補に自分専用の出力場所を与える (可能なら git の worktree、それが無理なら `/tmp/arena-<slug>/candidate-<n>/`)。**separate-before-serializing-shared-state** の principle skill に従う。

## フェーズ B: ファンアウト

N 個のサブエージェントを `run_in_background: true` で 1 通のメッセージにまとめて起動する。それぞれにタスク、共有された接地情報へのパス、自分専用の出力パス、そして成果物と、検討した代替案と何を却下したかを挙げる短い根拠を出せという指示を渡す。

候補が出力を作れなかったら、N-1 で進め、その脱落を書き留める。

## フェーズ C: クロスジャッジ

フェーズ B の候補がすべて完了した後、`~/.cursor/rules/pstack-models.mdc` の `arena cross-judge pool` の行からモデルを 1 つ選ぶ。そのルールまたはその行が無ければ、`claude-opus-5-5-xhigh` と `grok-4.7-xhigh-fast` から選ぶ。親とは別のモデルファミリを優先する。そのモデルで読み取り専用のジャッジのサブエージェントを 1 つ起動する。ジャッジはルーブリックと、パスのラベルで示された候補群を見て、基準ごとに採点し、根拠付きでベースを推薦する。ジャッジはフェーズ D であなたが読むのと並列に走る。候補がまだ書いている最中に起動してはならない。

## フェーズ D: ベースを選ぶ

選ぶ前に、どの候補も端から端まで読む。全体的な感触ではなく、ルーブリックの基準ごとに各候補を採点し、クロスジャッジと突き合わせる。ベースが一致すれば、その選定は裏付けられる。食い違うなら、どちらかが偏っているか、ルーブリックが曖昧だったということだ。決める前に双方の根拠を読む。

将来の保守者が不変条件を壊さずに最も容易に拡張できる候補をベースに選ぶ。2 つが互角に感じられるときは、Laziness Protocol に従って、より綺麗な境界か、より小さい API を優先する。

## フェーズ E: 接ぎ木

敗れた各候補をもう一度歩き、ベースへ移植する価値があるものを見極める。通常は候補 1 つにつき 1 つか 2 つであって、その大半ではない。各接ぎ木は、**redesign-from-first-principles** の principle skill に従って手で織り込み、結果を 1 つのメンタルモデルの下で一貫させる。機械的に貼り付けない。

候補が 1 つの形に収束したなら、それは強い合意だ。それを書き留め、合意された形を出す。接ぎ木は要らない。候補が大きく発散したなら、フェーズ A の仕様が足りなかったということだ。発散を平均するのではなく、枠を組み直して再実行する。

## フェーズ F: 検証

統合された成果物を、**prove-it-works** の principle skill に従い、他のどの出力とも同じように検証する。検証が arena では捕まえられなかった問題を見つけたなら、フェーズ A が間違っていたか (枠を組み直して再実行)、ある候補はそれを捉えていたのに接ぎ木を見落としたか (フェーズ E に戻る) のどちらかだ。取り繕わない。

## 出力

統合された成果物 1 つと、それと並ぶ短い統合ノート。ノートにはベースとその理由、クロスジャッジの評決、各接ぎ木 (元となった候補付き)、却下したものとその理由、収束や脱落があればそれ、そして検証結果を挙げる。
