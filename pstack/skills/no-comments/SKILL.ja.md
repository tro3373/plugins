# No comments

Comment Sicko を起動する。受け入れた指摘に基づいて動く。

Comment Sicko の新鮮な視点に従うこと。

## スコープ

呼び出し側のファイルまたは diff を使う。無ければ、ベースブランチ (既定 `main`) に対する現在の diff を、作業ツリーを含めて使う。

## 手順

1. `subagent_type: "Comment Sicko"` で `Task` を起動する。スコープを渡す。そのルールを言い直してはならない。
2. その報告と diff を検査する。アプリケーションコードの編集、スコープからの逸脱、例外で保護された削除、誤って述べられた `MUST KILL` の理由、意図的に残されたコードを有罪扱いするフラグは却下する。自分たちのコードの驚きに対する reshape フラグは実行可能なまま残す。それらのコメントを復元してはならない。keep が生き残るのは、自分たちには変えられないものについてだと証明できた場合だけである。スコープ内で見落とされた lint と TypeScript の suppression を監査する。正しさや安全性に関する suppression は実行可能な `MUST KILL` のまま残す。削除を復元するのは、正確な例外とスコープ内の証明がある場合だけである。根拠の薄い `IMPORTANT` や `do not remove` の kill / keep を受け入れる前に、そのシンボルに対して `/how` または `/why` を走らせる。kill が曖昧なら復元しない。keep が反証されたか、なお曖昧なら削除する。却下した報告は 1 度だけ、失敗を名指しした上で差し戻して再実行する。2 度目を却下したら、それをオープンとして報告し `/no-comments` を失敗させる。
3. 些末な受け入れ済みフラグは、デッドパスの削除、パラメータの除去、本物の API の使用によって直接修正する。修正に形が必要なら、受け入れた集合とその周辺コードに対して `/architect` を 1 回走らせる。スケッチで止める。architect は形を作る。手順 4 が実装する。
4. スコープ内で最小の根本原因の修正を実装する。名指しされた回避策はすべて除去する。根本原因がスコープ外なら、スコープ内で最小の修正を入れ、残りをオープンとして報告する。**principle-fix-root-causes** と **principle-redesign-from-first-principles** の skill は意図のみを導く。どちらも囲いを広げることや、囲いの外の事例を直すことを許すものではない。症状を抑えるガードは決して継ぎ足さない。
5. 制約コメントとは `do not remove`、`do not change wording`、`talk to X before changing` と書かれたものである。自分たちには変えられないものについての keep は残す。スコープ内で最も安価な型・ランタイム・テスト・CI の lint を提案する。対話的な承認を待つ。無人実行と eval では呼び出し側の事前承認が要る。承認されたら符号化してから削除する。されなければ削除し、その制約をオープンとして報告し、スコープ外の作業を素描する。
6. 削除件数、復元したコメント、再実行、architect のスケッチ、修正、符号化の提案、符号化、強制されなかった制約、その他のオープンな作業を報告する。
