# Build the Lever

作業が非自明なら、手作業でやる代わりに、それを実行するツールを作る。

**なぜ:** 見返りは 2 つある。スループット: codemod、ジェネレータ、スクリプトは毎回同じやり方で作業をこなし、再実行はタダである。確信: ツールはレビュワーが読み、再実行して作業を検証できる 1 つの成果物である。手作業の変更は、やり直すことでしか再検証できない。決定的なスクリプトは「信じてくれ」を「これを実行しろ」に変える。

**パターン:** 既定でレバーを作る。飛ばしてよいのは、作業が自明なとき - 一目で見て取れる自明な編集が 2, 3 個というときだけである。

- 最初の 1 単位を手作業でやってレシピを学び、それからツールを作る。その単位に対して再実行し、手作業版と diff を取って証明する。レバーは再実行しても安全にする。
- 編集には codemod かスクリプト、繰り返しのファイルにはジェネレータ、分析には dump-to-sqlite クエリ、検証には再実行可能なチェック。
- 決定的なレバーはファンアウトに勝る。ツールが 1 パスで全単位を処理できるなら自分で実行する。スクリプトでできることを手作業で適用させるために委譲先へファンアウトしてはならない。
- サブエージェントへ作業をファンアウトするときは、全員が読む skill としてレバーを書く。レシピ、検証の契約、触るなというフェンスを 1 つの成果物にまとめる。委譲先の書き込みスコープの外に置き、契約をこっそり編集できないようにする。
- この原則を適用すればファイルが 1 つできる。これを引用したのに diff の中に codemod、スクリプト、ジェネレータ、委譲先 skill がないなら、適用していない。
- 作業がセッションより長生きするならレバーをコミットする。

**バランス:** 基準は自明性であって、繰り返しの有無ではない。1 回限りの作業でも、レバーこそが作業を検証可能にするなら、レバーを作る価値がある。[Laziness Protocol](../principle-laziness-protocol/SKILL.md) に従い、仕事を実行するか証明する最小のスクリプトを作る。フレームワークは決して作らない。

[Encode Lessons in Structure](../principle-encode-lessons-in-structure/SKILL.md) とは別物である。あちらは繰り返される指示を耐久性のあるガードレールにする。こちらは目の前の作業のスループットとレビュー可能性である。検証そのものをスクリプト化する話は [Prove It Works](../principle-prove-it-works/SKILL.md) を見よ。
