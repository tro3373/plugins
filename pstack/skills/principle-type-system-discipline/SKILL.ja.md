# Type System Discipline

型チェッカは証明支援系である。ありえない状態、噛み合わないプリミティブ、扱われていないバリアントを、コンパイル時に潰すために使う。型が無視を許したケースは、コンパイラが止められたはずのランタイム障害になる。ハンドラを増やすより、エラーと特殊ケースを存在ごと定義から消すことを優先する。表現不能な状態、全域関数、インターフェースの再設計 (下記のパターン) がその道具だ。

型付き言語すべてに適用される。`typescript-best-practices` のような skill が、これを具体的な構文に接地させる。

**パターン:**

- **不正な状態を表現不能にする。** バリアントは直和型でモデル化する。TypeScript なら discriminated union、Rust / Swift / Kotlin ならペイロード付き enum、Scala なら sealed class、Haskell / OCaml なら ADT。矛盾する組み合わせがコンパイルできてしまうオプショナルフィールドの寄せ集めとして状態をモデル化してはならない。微妙なアンチパターンがある。`{ completed: boolean; completedAt?: Date }` は `completed: true; completedAt: undefined` を許すが、これは無意味だ。boolean は `completedAt !== null` のような単一の情報源から導出するか、`{ kind: 'open' } | { kind: 'done'; at: Date }` のようにバリアントを明示的にモデル化する。バグによって「待て、この組み合わせは実際に起こりうるのか?」という問いが生じたなら、その型は緩すぎる。
- **型は制限ではなく構成である。** より緩い型からチェックで削り出すのではなく、欲しい値から型を積み上げる。refinement 型が要るように見える不変条件は、たいてい構成の仕方ひとつで済む。非空リストとは、先頭要素と残りであって、長さチェック付きのリストではない。妥当な時間範囲とは、開始時刻と継続時間であって、順序を保ち続けねばならない 2 つのタイムスタンプではない。特権的な表現などない。ペアのリストは、そう解釈するなら偶数長のリストである。だから不正な値を作れない形を選び、その上に呼び出し側が必要とするインターフェースを載せる。
- **意味を持つプリミティブをブランド化する。** `UserId` と `OrderId` は内部的には文字列だが、互換であってはならない。Rust の newtype、Swift の opaque type、Kotlin の value class、Haskell の phantom type、TypeScript の branded intersection。生成時に一度だけ検証し、以降は型を信頼する。
- **外部データはパースするまで型無しである。** RPC ペイロード、JSON、IPC メッセージ、CLI 引数、設定ファイル、環境変数、データベースの行。すべての境界に、構造化されていない入力を型付きモデルへ変える parse 関数を置く。バリデーションをどこに置くかは **boundary-discipline** の原則 skill を参照。
- **型システムに嘘をつくな。** キャスト、安全でない強制変換、コンパイラを迂回するアサーション関数は、待機中のランタイムクラッシュだ。コンパイラがある事実を証明できないなら、こちらが証明する (検証する、絞り込む、モデルを洗練する) か、そのキャストは危険物だと受け入れる。
- **網羅的なマッチはコンパイラの仕事である。** 直和型に対してマッチするとき、新しいバリアントが未処理のまま追加されたらコンパイラがコンパイルを失敗させねばならない。言語が用意しているイディオムを使う。TypeScript なら `never` 型の束縛、Rust なら注釈なしの `match`、Haskell なら `-Wincomplete-patterns`、Kotlin なら sealed class のマッチ網羅性。
- **正典のスキーマから型を導出する。** protocol buffer、OpenAPI 仕様、GraphQL スキーマ、データベースマイグレーション、デザインシステムのトークンファイルが形を定義しているなら、並行する型を手書きするのではなくそこから導出する。**encode-lessons-in-structure** の原則 skill を参照。
- **型を強めるのは、部分性が現れた場所だけにする。** ランタイムのアサーション、null チェック、「ここには来ないはず」の throw は、型が弱すぎる場所の目印だ。そのチェックを型へ押し上げる。そこで止める。型システムの仕事は、各使用箇所が扱わねばならないケースを追跡することであって、データをできるだけ精密に記述することではない。全域関数を選ぶ。空リストの `sum` は 0 なので、素のリストを受け取る。空リストの `head` には答えが無いので、非空リストを要求する。

**テスト:**

- 「このフィールドの組み合わせがいつ妥当なのかを説明するコメントを書けるか?」書けるなら、その型は緩すぎる。直和型に分割せよ。
- 「2 つの引数が同じプリミティブ型を共有しながら別の意味を持っていないか?」ならブランド化せよ。
- 「この `any`、この `as`、この `assertNotNull` はどこから来たのか?」境界まで辿り、そこで検証せよ。
- 「来月新しいバリアントが追加されたとき、コンパイラは次のエージェントにケースの追加場所を教えてくれるか?」ノーなら、そのマッチは網羅的でない。
- 「この型は別のファイルが所有する形を複製していないか?」なら導出せよ。
- 「この型を強めているのは、操作を全域に保つためか、それとも単に精密にしたいだけか?」何もパニックしないのなら、素の型のままにせよ。
