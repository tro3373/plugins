## セッションが実際に使った skill とツールにスコープを絞る

指摘は、このトランスクリプト内で呼び出された skill、ツール、MCP を指していなければならない。親が一度も開いていない skill への推測的なルーティングは数に入らない。skill が使われたかを確認するには、トランスクリプト中の次を走査せよ:

- 任意の `SKILL.md` ファイルに対する `Read` ツール呼び出し (ワークスペースの `.cursor/skills/`、ユーザレベルの `~/.cursor/skills/`、`~/.cursor/plugins/` 配下のプラグイン導入パス)
- skill のパスを名指しする `Task` プロンプト
- skill のドキュメントに載っているコマンドと一致するツール呼び出し (Shell、Grep、MCP など)

妥当な指摘の形は 2 つ:

- 親がその skill を呼び出しており、その本文に実在のギャップを見つけた場合。その skill の該当セクションへルーティングする。
- その skill はカタログ上見えていたが、役立ったはずの場面で発火しなかった場合。今後のエージェントが拾えるように skill の description を調整する。`tune description: <skill path>` としてルーティングする。

上の「呼び出されるべきだったのに呼ばれなかった skill」の項目が、発火漏れの典型例である。それらは `tune description` へルーティングせよ。呼び出されてもおらず発火漏れの候補でもない skill は落とせ。

見つけた耐久性のある学びをそれぞれ挙げよ。各件について:
- 原則: 逆張りな観察または二次的な観察を 1 文で名指しする。明らかな学びを言い直さない。その下にあるものを名指しせよ。
- 証拠: トランスクリプト中の正確な箇所 (ターン番号または短い引用。何が言われたか AND 何が言われなかったかを含める)。
- ルーティング: 最も関連する既存の skill (トランスクリプトに現れるとおりの `SKILL.md` パスを示す)、または skill が発火すべきだったのにしなかった場合は `tune description: <skill path>`、または「new skill: <kebab-name>」。

些末なものは飛ばせ。親が従った既存の skill から既に明らかなものは飛ばせ。ドリフトする実装詳細 (特定の SHA、現在のファイルパス、バージョン番号、正確なバイト数) は飛ばせ。コードのドリフトを生き延びる原則とパターンだけを挙げよ。
