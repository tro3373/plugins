# Boundary Discipline

validation、型の絞り込み、エラーハンドリングはシステム境界に置く。内部のコードは無条件に信頼する。ビジネスロジックは純粋関数に置く。シェルは薄く機械的に保つ。

**なぜ:** 散らばった validation はノイズであり、冗長であり、偽りの安心感を与える。ロジックをフレームワークの配線から切り離し、フレームワーク無しでテストできるようにする。

**パターン:**
- **境界では** (CLI 引数、設定ファイル、外部 API、ネットワークプロトコル): 検証し、エラーを返し、防御的に扱う。
- **システム内部では:** 型付きデータ、エラーの伝播、再検証はしない。型を信頼する。
- **境界をまたぐときは。** 境界側の内部表現ではなく、ドメインの概念を公開する。汎用的なメカニズムは内側に、特定用途のポリシーは端に置く。

**適用例:**

validation とエラーハンドリング:
- config はビジネスロジックの中ではなく、パース時 (= 境界) に検証する
- 生データは境界でドメイン型にパースする
- transport・storage・framework・wire の型を公開面から再エクスポートしない
- 境界で検証済みなら、呼び出し連鎖の深部で冗長な nil チェックをしない

コードの構成:
- ビジネスロジックはフレームワーク依存の無い純粋関数に置く
- パース関数: 生バイトから型付き状態への純粋な変換
- プロンプト構築: 構造化された状態を入れ、文字列を出す
- スコアリングと評価: 状態から結果への純粋な変換

**判定基準:**
- 「このデータは今まさにシステム境界をまたいでいるか?」 またいでいないなら、その validation は冗長だ。
- 「これはシェルが呼ぶだけの純粋関数にできるか?」 できるなら、切り出せ。
