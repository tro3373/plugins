# verification skill を保守する

feature map はアプリが変わった瞬間に腐る。この skill は、`/create-verification-skill` が生成した skill (または feature map を持つ任意のプロジェクトローカルな verification skill) のための保守ループである。厳密さの単位は feature であって、1 文ずつではない。すべての feature ファイルをソースからカバーし、すべての feature を live で動かす。ただし全箇条書きをターミナルで潰しにいくわけではない。

## 結果

1 つを選び、どれかを述べる:

- **clean** - すべての feature がソースと live のカバレッジを得た。出すに値するものは無い。ブランチ無し、PR 無し。
- **changed** - 証明済みの doc、harness、map の修正を 1 本の PR で出す。
- **blocked** - カバレッジを終えられなかったか、証明済みの修正を安全に出せなかった。何がブロックしたかを正確に述べる。

## 編集スコープ

verification skill 自身のディレクトリ (その SKILL.md、features/、それが所有する harness スクリプト) だけを編集する。実行中にプロダクトコードを編集してはならない。map が記述している挙動をアプリがもう行わないなら、それはドキュメントのドリフト (map を直す) か、プロダクトのリグレッション (報告する。ドキュメントで塗り潰さない) のどちらかである。

## パス

0. **対象を特定する。** 保守すべき verification skill を見つける。本文に launch / drive のセクションと feature map を持つ、プロジェクトローカルな skill である (たいてい `.cursor/skills/verify-*/`)。候補が複数あるなら => どれかを聞く。1 つも無いなら => 止まり、対象をでっち上げる代わりに `/create-verification-skill` を指す。

1. **索引の衛生。** feature map の README を読み、その兄弟ファイルを glob する。欠落、余分、重複、死んだエントリを直す。軽量に。生成されたインベントリは作らない。

2. **ソースの波。** feature ファイル 1 つにつき読み取り専用のサブエージェント 1 体を、同時に起動する。各々がソースから「このユーザ向け feature はどう動くか?」を説明し、ドキュメントのドリフトの疑いを引用付きで指摘し、簡潔な live 検証レシピを 1 つ返す。子はアプリを駆動せず、ファイルを編集しない。返す形: feature の要約 / ソースのエントリポイント / ドリフトの疑い、または無し / レシピ 1 つ。

3. **突き合わせ。** すべての feature ファイルに返ってきた要約がある。重なるレシピは、実用上できるだけ少ないアプリ状態へ統合する。引用されたドリフトはスポットチェックする。clean という主張を証明し直さない。map に無いユーザ向けの表面がないか、最近の変更を掃引する。欠落していると言う前に、具体的なソースパスを要求する。

4. **live パス。** ソースが clean に見えても必須である。駆動はすべてコーディネータが所有する。verification skill 自身の launch モデルに従うこと。サーバや UI なら長命のインスタンス 1 つを直列に駆動し、短命の CLI なら駆動ごとに新しい隔離セッションを立てる (決めるのはその skill の Launch セクションであって、この skill ではない)。すべての feature を少なくとも 1 回動かし、どんな失敗が起きようとパス全体で 3 つの不変条件を保つ。(1) 直近で驚くような挙動をして以降ヘルスチェックしていないインスタンスを駆動しない。最初の駆動の前に doctor、セッションが単位ならセッションを新しく立てるたびに doctor、駆動が失敗したらもう一度 doctor。doctor が失敗を見られない場合 (プロセスは健全なのに UI が固着した状態) は、期待するのではなく既知の状態へリセットするか再起動する。(2) それまでに取得した証拠は、いかなるクリーンアップも生き延びる。名指しした場所で存在を確認し、あると仮定しない。(3) 駆動が始めたものは、その駆動の有用性より長生きしない。失敗したイテレーションの残骸は、セッションが固着していようが、終了していようが、共有されていようが片付ける (共有インスタンスなら、片付けるのは残骸であってインスタンスではない)。skill のドリフトが原因の doctor 失敗はドリフトである。編集スコープの範囲で直し、1 回だけリトライする。修正によって無効化されたものだけを再起動し、それ以上はしない。そのうえでなお駄目なら `blocked` と呼ぶ。到達できない feature を `verified-unreachable` と呼べるのは、具体的な前提条件 (auth、entitlement、OS、外部状態) と試した経路を伴うときだけである。map がその前提条件を書いていないなら、それはドリフトである。triage から出た harness の修正は、出荷前に live で駆動し直す。最終的な後片付けは、その実行の最後の駆動 (これらの再証明を含む) の後に行い、実行より長生きするものが何も残らないようにする (証拠は skill に従って残る)。

5. **Triage。** ユーザ視点の記述が誤っている・欠けている => ドキュメントのドリフト。直す。挙動は動くのに harness が駆動できない => harness のギャップ。直す。harness の修正は生成時と同じ helpers ルールに従う (スクリプトは実行可能、呼び出し方は skill 本文に記載)。アプリの挙動が実際に壊れている => プロダクトのギャップ。ユーザ向けに記録し、この PR には入れない。

6. **出すか止まるか。** changed の場合: 証明済みの修正を 1 本の PR に。まず変更した全ファイルを読み直す。clean か blocked の場合: PR は無し。結果とカバレッジを正直に報告する。

実行のメモ (カバーした feature、到達できない前提条件、確認されたドリフト、結果) は簡潔にスクラッチな場所へ残す。コミットしない。
