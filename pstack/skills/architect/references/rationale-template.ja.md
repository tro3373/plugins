# 設計判断の根拠のテンプレート

型スケッチと一緒に出す散文。1 ページ。見出しは Sentence case、定型文は書かない。イタリックの注記は実際の内容に置き換える。

## 問題

*1 段落。何をしようとしているか、そして既存システムや制約の何が、その形を自明でなくしているか。[Phase A](../SKILL.md#phase-a-ground-the-problem) が設計の尊重すべき制約 (相互運用が必要な既存の型、壊せない呼び出し元、境界をまたいだ不変条件) を明らかにしたなら、読み手が自分と同じ制約を見られるようここに書く。*

## 使い方 (呼び出し側の視点)

*型スケッチより先に、これを最初に書く。利用者が読む README やクイックスタートに加えて、彼ら自身のコードでの現実的な呼び出し箇所を 2 つか 3 つ示す。何を import し、何を呼び、何が返るか。[形](#形) の型スケッチはこれから導かれる。両者は一致していなければならない。乖離したら、スケッチを使い方に合わせるのであって、逆ではない。呼び出し側の体験が仕様である。型はそれに仕える。*

## 形

*推奨するアーキテクチャ。まずデータ構造、次にシグネチャを通じてデータがどう流れるか。要となる決定を明示する。どの不変条件が型に符号化されているか、バリデーションがどこにあるか、システムが意図的にやらないことは何かを述べる。インターフェースの深さを明示的に評価する。公開面が隠している複雑さ、呼び出し側に露出したままの複雑さ、そしてインターフェースが必要以上に大きくない理由を述べる。各決定の背後にある原則を引用する (例: `per boundary-discipline`)。原則そのものを言い直さない。*

## 統合の判断

*[arena](../../arena/SKILL.md) が埋める。どの候補がベースになりその理由は何か、他の候補から何を取り入れたか、何を棄却しその理由は何かを記録する。*

## 受け入れたトレードオフ

*選んだ形が行うトレードオフ 1 つにつき 1 項目。形式は「Y と引き換えに X を受け入れる」。将来の読み手が見落としと誤解しかねないものは、時期尚早な最適化や時期尚早な単純化に見えるものも含めて明示する。*

## 検討した代替案

*必須。具体的な代替の形を少なくとも 1 つ挙げ、それが負けた理由を 1 行で書く。各代替案は実装の単純さだけでなく、インターフェースの深さで評価する。それが呼び出し側に露出する複雑さと、隠す複雑さを明示する。設計空間に本物の対抗馬がいたなら、2 つか 3 つの代替案がここに入る。制約が答えを強制したなら 1 つでよく、結論は「これが唯一実行可能な形だった。理由は……」と表現する。同じ形の変種を並べるのは避ける。この節が扱うのは、選んだ形が検討して棄却した設計上の代替案であって、他のランナー候補ではない。*

## 未解決の問いとリスク

*スケッチ中に気づいた、人間の判断を要するもの。および実装開始前に挙げておく価値のあるリスク。人間の答えが解決になるよう、断定ではなく問いの形で書く。*

## 次の実装ステップ

*スケッチに対して最初に作るもの。1 文。統合の直後 (チェックポイントを選んだなら Phase D のサインオフの直後) にすぐ書き始めるもの。*
