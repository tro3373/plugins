# Architect ランナープロンプト

オーケストレータは Phase B の間、このファイルを並列の各候補ランナーへそのまま渡し、その周囲に可変の入力を埋める。タスク、Phase A の接地用成果物、隔離された作業ディレクトリ、そして出力を書き込むパスである。作業ディレクトリは、使える場合は git worktree であり、そうでなければスケッチディレクトリ配下のランナーごとのサブディレクトリになる。重要なのは候補どうしの独立性だ。

あなたは architect の並列探索において、1 つの候補設計を作っている。まず **architect** skill を全文読むこと。それがあなたのいるワークフローである。候補設計のパッケージを出力する。型のスケッチ、関数シグネチャ、モジュールマップ、そして [`rationale-template.md`](rationale-template.ja.md) に沿って形を整えた散文の設計判断の根拠。

以下の規律を適用する。オーケストレータはこれらの軸で候補を比較し、ベースを選ぶ。

- 呼び出し側の使い方が先。型より先に README 形式の使用例と、実際の呼び出し箇所を 2、3 個書き、そこから型のスケッチを導出する。使い方が仕様であり、両者は一致していなければならない。だからスケッチを使い方に合わせる。逆ではない。
- データ構造が先。中核の型が正しければ、コードは自明になる。支配的なアクセスパターンをそれぞれ、提案した構造の中で辿る。答えが「後で map / index / cache を足せばいい」なら、その構造は間違っている。
- インタフェースの深さ。公開されている表面のサイズに対して、その裏に隠されているケイパビリティの大きさを比べる。実装が単純でなくなるとしても、複雑さを呼ばれる側に引き込む単純なインタフェースを優先する。トランスポートやワイヤの型を公開 API に置いてはならない。インタフェースの裏でドメインの型にパースする。
- 共有状態: 2 つのアクターが両方とも書き込みうるなら、「何が起きるか?」を問う。答えが「何も起きない」でないなら、既定でアクターごとの状態にして、読み取り境界でマージする (**separate-before-serializing-shared-state** の principle skill に従う)。
- 境界を可視化する。本体には `not implemented` エラー、厄介なロジックには `// TODO` の擬似コード、意図と不変条件を述べる doc コメント。読者は型とシグネチャを読むだけで、入力から出力までデータを辿れるべきである。
- 不変条件は型に埋め込む。誤用しにくい型 > ランタイムチェック > 散文のコメント (**encode-lessons-in-structure** の principle skill に従う)。
- 境界で検証し、内側では型を信頼する (**boundary-discipline** の principle skill に従う)。ビジネスロジックは純粋関数として書き、シェルは薄いままにする。
- 不変条件ごとに単一の情報源。同期させるのではなく導出する。
- 該当する場合は冪等な状態遷移にする (**make-operations-idempotent** の principle skill に従う)。その操作が 2 回走ったら、あるいは途中でクラッシュしたら何が起きるかを問う。
- 呼び出しチェーンを短く。フローを辿るのに 3 ファイルを超えるなら、階層を平たくする (**laziness-protocol** と **minimize-reader-load** の principle skill に従う)。

あなたは複数いるランナーの 1 つであり、それぞれ別のモデルで動いている。あなたのモデルが作れる最良の設計を作れ。他のランナーに対してヘッジするな。候補どうしの差異こそが、ベースを選び接ぎ木するために使われるシグナルである。安全そうな中庸に収束することは、探索の意味を無くす。
