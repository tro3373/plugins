# Architect

実装の前に設計する。型、関数シグネチャ、クラスの形、モジュール境界を、`not implemented` の本体と擬似コードでスケッチする。複数のモデルの視点を横断して統合し、選ばれたスケッチに対してコードを埋めていく。実装がスケッチの誤りを証明したら、捨てて設計し直す。

## 開始

始める前に、フェーズごとに 1 項目の todolist を開く。

1. Ground
2. Sketch
3. Agree
4. Implement
5. Scrap

## Phase A: 問題を地に足の着いたものにする

新しいコードが触れるすべてのシステムについて、本物のメンタルモデルを作る。関連するサブシステムに対して **how** skill を走らせる。

ファイルの名前を挙げることは grounding ではない。`how` が規定する追跡済みのモデルを作ること。設計が所有権やレイヤリングを再定義するなら、既存の形に対して **why** skill も走らせ、その根拠が推測ではなく制約になるようにする。

Phase A を飛ばしてよいのは、統合すべき周辺システムが存在しない、正真正銘のグリーンフィールドの作業のときだけである。

## Phase B: スケッチ

design-sketch タスクと Phase A の grounding 成果物を渡して **arena** skill を走らせる。各ランナーのプロンプトとして `references/runner-prompt.md` を渡す。各候補は `references/rationale-template.md` の形の設計パッケージを生成する。

ランナーは、`arena runners` の行の代わりに `pstack-models.mdc` ルールの `architect runners` の行から取る。ルールやその行が無い場合は `claude-opus-5-5-max`、`gpt-5.6-sol-max`、`grok-4.7-xhigh-fast` を使う。エイリアスと却下エントリは **arena** skill の Phase A のランナー規則に従う。

2 回設計する。最初のものが十分に見えても、統合の前に構造的に異なる候補を最低 2 つ要求する。これは **exhaust-the-design-space** の原則 skill を具体化したものである。1 つの形の内部での部分的な修正ではなく、形そのものの代替案を出す。

統合の前に、すべての候補を [`references/design-red-flags.md`](references/design-red-flags.md) に照らして選別する。浅いモジュール、情報の漏洩、時間的分解、パススルーメソッドは却下または修正する。

存続可能な候補をインターフェースの深さで比較する。より小さくシンプルな公開面の裏に、より多くの複雑さを隠す設計を選ぶ。リッチなインターフェースは、能力をレイヤーに散らすのではなく集約することで、呼び出し連鎖を短く保てる。

arena は統合された設計パッケージを 1 つ返す。統合の判断が、根拠の「Synthesis decision」の節を埋める。

## Phase C: 合意する (opt-in)

既定: 統合された設計のまま実装へ直接進む。人間のチェックポイントは無し。

チェックポイントを入れるのは、呼び出し側が明示的に求めたときだけ:「/architect with checkpoint」「実装前に見せて止まって」など。そのときは統合された設計を提示し、承認を待って停止する。

いずれの場合も、統合結果はそれ自体を **foundational-thinking** の原則 skill の「まず足場」モードとして 1 コミットで出せる。埋め込み中の計画された範囲内の破壊は、**outcome-oriented-execution** の原則 skill に従い問題ない。実装前に設計へ敵対的な圧力をかけたいなら、統合されたスケッチに対して **interrogate** skill を走らせる。

人間が形について押し返してきたら (チェックポイントでも事後でも)、それを Phase A の証拠として扱う。さらにコードを書く前に、grounding をやり直し Phase B を再実行する。

## Phase D: スケッチに対して実装する

`not implemented` の本体をコードで、擬似コードをロジックで置き換える。統合されたスケッチが契約である。

スケッチからの逸脱は、黙って吸収すべき摩擦ではなく、表に出す価値のあるシグナルである。ある関数がスケッチの想定しなかったパラメータを必要とするなら、スケッチが間違っていたのか、要件を見落としていたのか、実装がやり過ぎているのかを問う。

## Phase E: アーキテクチャが間違っているなら捨てる

実装がスケッチの吸収できない摩擦を生み続けるなら、スケッチを捨てる。**redesign-from-first-principles** と **fix-root-causes** の原則 skill に従い、誤った設計に修正を継ぎ足してはならない。

シグナルは単発の事例ではなく*パターン*である。兆候:

- 無関係なコードにまたがって、同じ形の回避策が繰り返し現れる。
- 無関係な複数のエッジケースが、いずれも特別扱いの分岐を必要とする。
- コンパイルを通すために型が脱出ハッチ (`any`、キャスト、実際には常に設定されるオプショナルフィールド) を必要とする。
- スケッチでは状態は共有されないとしていたのに「ロックが要る」という反射が出る。
- 呼び出し側が、抽象を使うためにその内部規則を知らねばならない。
- 実装全体で、同じ形の独立した Phase D の逸脱が 2 つ以上ある。

判断を使うこと。いくつかのエッジケースがアーキテクチャを断罪するわけではない。正当に複雑な問題もある。データの複雑さは設計の複雑さではない。

捨てるときは:

1. 作られたものに対して **how** skill を再実行する。
2. redesign-from-first-principles に従い、新しい制約が初日からの前提だったかのように設計し直す。
3. **subtract-before-you-add** の原則 skill に従い、加える前に引く。新しいスケッチは、育つ前に古いものより小さくあるべきだ。
4. Phase B に戻り arena を再実行する。

## 成果物

呼び出し側の使用例を最初に書き、そこから型のスケッチを導く。小さな変更なら新しい型とシグネチャを含む 1 ファイル。より大きな作業ならモジュールマップと型定義。根拠は `references/rationale-template.md` の形で並べて出し、使用例のスケッチと統合の判断を含める。
