# Test Behavior, Not Implementation

テストは、コードがそのユーザー (呼び出し元、エンドユーザー、別のサービス) のために何をするかについての主張である。挙動とは、ユーザーが使うインターフェースを通して観測できるものだ。戻り値、エラー、読み戻せる状態、コードの外のシステムへの作用 (送られたリクエスト、書かれた行、発行されたメッセージ) が含まれる。実装とは、ユーザーが観測できないものだ。private なヘルパー、内部の呼び出し順、中間データ、内部のどの協調オブジェクトが仕事をしたか。

各テストを、想像上の 2 つの編集に照らして判定する。

- **挙動を壊す。** コードに誤った値を返させる、作用を飛ばす、作用を 2 回行わせる。それでもテストが通るなら、そのテストは何も証明していない。よくある原因は、契約より緩いアサーション、テスト対象のコードが計算した期待値、それを読むコードを実行しない言い換えた定数やプロンプト文字列、テスト自身が組み立てたデータへのアサーションである。
- **内部を変える。** 観測できる結果をすべて同じに保ったまま、下のコードを組み替える。それでテストが失敗するなら、そのテストは実装に固定されている。リファクタのたびに書き直しが要り、それでもバグは捕まえない。

1 つ目の編集を捕まえ、2 つ目に耐えるテストを残す。残りは書き直すか削除する。両方を満たすテストを書くには、具体的な入力でユーザーのインターフェースを通してコードを駆動する。期待値は、コードを実行した結果ではなく、要件から導く。契約が約束することを、過不足なくアサートする。

決めるのは契約であって、アサーションの形ではない。「空のカートは決して課金しない」が約束なら、決済クライアントが呼ばれなかったというアサーションは挙動である。課金が起きるケースと対にして、そのテストが呼び出しを検出できることを示す。モック化した外部サービスが受け取るペイロードは、そのサービスが観測するので挙動である。内部ヘルパーの呼び出しは、どのユーザーにも見えないので実装である。空のリストは、該当するレコードが無いときは正確な答えであり、何らかの結果が出ればよいだけのテストでは空疎なチェックである。正確なエラーメッセージは、どの呼び出し元も読まない文言に固定する。呼び出し元が分岐に使うエラーの型が契約である。

テストは、呼び出しではなく不変条件に固定してもよい。2 つのテーブルに存在しなければならないキーや、コンパイル時の型チェックなどである。その不変条件が挙動である。
