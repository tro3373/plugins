# Correct

オペレータは、この repo でエージェントが同じ間違いをするたびに訂正し続けている。次のエージェントがそれをできないよう repo を変える。

すべてのコントリビュータは、開いたファイルしか見ず、最も近い例をコピーし、コンパイルが通る最短の道を取るエージェントだと仮定する。1 つのファイルから見て正しく見える変更が、repo 全体にとっても正しくなるよう repo を設計する。

## 間違いのクラスを見つける

まず、最近のコミット、revert、レビューコメント、エージェント向けの指示ファイル、ワークアラウンドを説明するコメントを読む。間違いをクラスにまとめる。2 回起きた時点でクラスとして数える。

## 各クラスを、効く中で最も高いレベルで直す

1. **アーキテクチャで消す。** 状態ごとに所有者を 1 つ、タスクごとにサポートされた方法を 1 つにする。内部を隠し、間違った import が失敗するようにする。手で同期しているリストを単一の信頼できる情報源に置き換える。エージェントがコピーしそうな古いやり方とデッドコードを削除する。
2. **型で強制し、悪い状態を書けないようにする。** 悪いコードがそれでもコンパイルを通るなら、代わりに使うべきファイル、型、関数をエラーで名指しする lint か CI チェックを追加する。そのパターンが既に広く使われているなら、変更がそれを増やしたときだけ失敗させる。
3. **振る舞いをテストする。** 検証している挙動が壊れても通ってしまうテスト、あるいは内部だけが変わって落ちるテストは、直すか削除する。
4. **ドキュメントやエージェント向けルールは最後に、判断が要る場面のためだけに書く。** エージェントがそれを読み飛ばしても、何も失敗しない。

## 直して証明する

次に、最も頻度の高いクラスを今すぐ、1 クラス 1 コミットで直す。新しいチェックが実際の過去の間違いで失敗することを証明する。ローカルと CI で同じコマンドを走らせる。例外は、違反している行に、理由、期限、人間の承認を添えて書く。

## ルール表を保つ

最後に、エージェント向けの指示ファイルに、各ルールとそれを強制する仕組みを対にした表を保つ。オペレータに訂正されたら、間違いを直し、ルールを追加する。ルールが既にあって何もそれを強制していなかったなら、それは再発だ。同じ変更の中で、最も高いレベルで直す。間違いが起こり得なくなったら、そのルールは外す。

**返答:** 各クラスとその証拠、選んだレベル、それより高いレベルが効かなかった理由。
