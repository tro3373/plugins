# Recall

**作業を始める、あるいは再開する前に、ユーザの直近の作業文脈を再構築し、今どこにいて次に何をすべきかを凝縮したカプセルとして返す。**

凝縮し、話題から外れないこと。スコープ内のスレッドが必要とするものだけを読み、そこで止める。

あなたの文脈は 2 つの記録に存在する。自分のチャット履歴は、何をして何を決めたかを持っている。共有記録は、同じコードの周りで別の名前の下に起きたすべてを持っている。ユーザが繰り返し報告する症状、出荷されて revert された修正、本番でまだ発火しているエラーなどである。その 2 つ目の記録こそ **why** skill が探索する対象であり、ソース管理、イシュートラッカー、チャットとイシューのチャンネル、長文ドキュメント、エラートラッキングにまたがる。バグの尾を長く引く機能は、その物語の大半をそこに置いている。だから自分のトランスクリプトだけから再構成してはならない。

トランスクリプトは `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl` にある。`<slug>` はワークスペースのパスから先頭のスラッシュを落とし、各 "/" を "-" に変えたものである (よって `/Users/you/proj` は `Users-you-proj` になる)。1 行が 1 チャットメッセージである。

1. 分類し、それからルーティングする。再開すべき特定の過去チャットが 1 つあるなら、それは `session-pickup` のプレイブックであってこれではない。習慣を耐久性のある skill に変えるのは `automate-me`。自分の作業の人間向けサマリーは別のタスクである。Recall は行動の前に、直近の複数チャットにまたがる作業文脈をロードする。ユーザが既に完全な状態カプセル (パス、ブランチ、変更内容) を渡しているなら、それを使って発掘は飛ばす。
2. 探索の前にスコープを固定する。ウィンドウ (「recent」は実在の範囲であり、既定は直近 7 日)、名指しされていればトピック、そしてワークスペース (既定はアクティブなもの。頼まれない限り他プロジェクトのトランスクリプトを決して読まない) を確定する。スコープを言い返す。「all」を黙って「recent N」に変えてはならない。
3. 自分のチャット履歴に fan-out する。速く安いモデルで並列サブエージェントをスポーンし、それぞれにコーパスの一部を担当させる。すべてのサブエージェントに次を伝える: 候補は UUID 名ではなく実際の更新時刻 (`ls -t`) で並べること、まずトピックを grep し、それからマッチしたチャットだけを、しかもその関連する箇所だけを読むこと、現在のチャットと明らかなノイズ (サブエージェント、eval、テストのチャット) は飛ばすこと。各サブエージェントは同じスキーマで、チャット 1 件につき 1 ブロックを返す: トピック、ユーザのゴール、決定、未解決のスレッド、苦戦と修正、アーティファクト (PR、チケット、ブランチ)。それぞれチャットの UUID を引用する。チャットが 1-2 件なら fan-out せず直接探索する。生のトランスクリプトはサブエージェント側に留まる。メインスレッドが受け取るのは findings だけである。
4. トピックが機能、ファイル、サブシステム、領域、バグを名指ししているときは常に共有記録を掃く。これは既定であって判断の余地はなく、「my work on X」であっても免除されない。掃引は **why** skill のソース調査担当に渡すが、質問は「なぜこう作られたか」から「現在の状態は何か、何が試されて定着しなかったか、ユーザが今も報告しているものは何か」へ向け直す。why のソース別プレイブックを再利用し、調査担当はチャット履歴の発掘と並列に走らせ、その姿勢も引き継ぐ: ソース 1 つにつき調査担当 1 体、null な結果も findings、利用できない MCP は飛ばしてその旨を述べる。返ってきたものはブリーフへ畳み込む。この手順を飛ばしてよいのは、名指しされた対象のない純粋な活動の想起 (「what did I do this week」) だけであり、そこでは自分の履歴とライブな状態が答えのすべてである。
5. ライブな状態と突き合わせて検証する。発掘と掃引が浮かび上がらせた PR、ブランチ、チケットを `git` と `gh` で確認する。答えがエージェントが実際に何をしたか (実行したツール、読んだファイル、遭遇したエラー) に懸かっているときは、切り詰めたローカルのコピーではなく完全なトランスクリプトを読む。
6. 下記の契約に沿ってブリーフを書く。スレッドごとにまとめる。名指しされたトピックから外れない。

## 出力の契約

まずカプセル、次にスレッドの状況、次に問題、最後に次の一手。より深い詳細は下に置くか、切り落とす。

- **カプセル。** 最大 5 個の箇条書き。この作業が何であり、全体としてどこにあるか。
- **スレッド。** 各 1 行。次のいずれか 1 つのステータスタグを必ず前置する: `[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]`、`[planned, not started]`。タグのないスレッドはまだ終わっていないのだから、タグを付けよ。
- **問題。** 最大 5 件、繰り返し起きているもの。ユーザが繰り返し報告している症状と、出荷されて revert された修正があればそれを含める。次の試みが前回の失敗地点から始められるようにするためである。
- **次の一手。** 最も有用な次の行動を 1 つ、具体的に。

隣接する機能やチケットは、これをブロックしていない限り含めない。カプセルとスレッドの行が 1 画面に収まらなくなったら、スレッドを削る前に詳細を削る。ブリーフは **unslop** skill を通して書き、チャット由来の findings は UUID で、共有記録由来の findings はそのソース (PR 番号、チケット ID、チャットのパーマリンク、エラートラッカーのイシュー) で引用し、公開する出力の前にはプライベートな文脈をサニタイズする。

**返答:** 上記の契約に沿ったブリーフ。
