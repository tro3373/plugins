# Model the Domain

現実のドメインを、条件分岐に散らすのではなくデータ構造で表現する。

**なぜ:** 散らばった boolean、繰り返される形状の仮定、複数ファイルに広がる分岐は偶発的複雑性である。ドメインに合致する構造は不正な状態を表現不能にし、分岐を削除する。書く時点で選ぶのは安価だが、後から回収しようとするとリファクタとして扱われ、先送りされる。

**次のような構造に手を伸ばせ:**

- 散らばった boolean、フェーズ、ライフサイクルチェックの代わりにステートマシン。
- ゆるいパラメータや繰り返される形状の仮定の代わりに型付きのオブジェクト / モデル。
- 複数ファイルに広がる分岐の代わりに map、レジストリ、ルックアップテーブル、判別可能な union。
- 場当たり的な状態変更の代わりに reducer やコマンド / イベントモデル。
- load、validate、transform、save のような手順の並びではなく、1 つのドメイン知識のまとまりを軸に構成したモジュール。実行順序は所有権ではない。
- 繰り返される振る舞い、所有権、不変条件をまとめる小さなモジュール境界。
- データアクセスパターンがそれを求めるなら、キュー、キャッシュ、インデックス、グラフ / ツリー、正規化されたコレクション。
- その他、当てはまる任意の構造。どれも当てはまらないなら、コードが決して許してはならないことは何かと、データがどう読まれるかを洗い出し、それをちょうど表現する構造を見つける。

抽象を無理に作ってはならない。今の形が既に明快でローカルであり、成長しそうにないなら、退屈なコードを選ぶ。分岐、重複したルール、不正な状態、ライフサイクルのリスクを取り除かずに間接層だけ増やす抽象には懐疑的であれ。

これを飛ばした兆候は、既存の if/else 連鎖に分岐が 1 つ増える新機能、あるいは最初の boolean と同期を保たねばならない 2 つ目の boolean である。時系列による分解も別の兆候である。フェーズ名のモジュールは、同じドメインルールを各ステップで繰り返す。
