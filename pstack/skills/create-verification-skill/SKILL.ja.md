# verification skill を作る

真剣なプロジェクトにはどれも、実物のアプリを動かして挙動を証明する、スクリプト化された手段が要る: 起動し、ユーザがやるように機能を動かし、証拠を取る。この skill は、それをリポジトリに合わせたプロジェクトローカルな skill (`.cursor/skills/verify-<app>/`) として生成する。生成物は人間ではなく次のエージェントに向けて書く: それは、そのアプリを見たことのないエージェントによって、タスクの途中に予備知識なしで読まれる。

## 1. ユーザではなく、リポジトリに聞き込む

以下をコードベースから答え、観察できないことだけをユーザに聞く:

- **表層:** ユーザが実際に触れるのは何か? web UI か、CLI/TUI か、デスクトップアプリか、API か、モバイルアプリか、ライブラリか? 1 つのリポジトリが複数を持つこともある。主要なものを 1 つ選び、残りは書き留める。
- **起動:** アプリはローカルでどう起動するのか? リポジトリ自身が文書化している dev コマンド (package のスクリプト、Makefile、README のクイックスタート) を優先する。ポート、環境変数、シードデータ、認証を書き留める。
- **操作:** エージェントはどうやってプログラム的にそれとやり取りできるのか? まず既存のハーネス - Playwright/Cypress のスペック、expect スクリプト、PTY ヘルパー、curl できるエンドポイント、デバッグポート。それから初めて汎用のレシピを選ぶ: web と Electron にはブラウザ/CDP、CLI/TUI には tmux/PTY のハーネス、サービスには素の HTTP。
- **観察:** どんな証拠を取れるのか? スクリーンショット、ターミナルのトランスクリプト、レスポンスボディ、ログ、終了コード、DB の状態。
- **隔離:** 2 つのインスタンスを並べて動かせるか (ポート、データディレクトリ、プロファイル)? できないなら、生成する skill にそう書く: 共有インスタンスを二重に操作することを拒む方が、ユーザのセッションを壊すよりましだ。

チェックアウトした状態でビルドも起動もしないなら、生成の前にまずそれを直す (または正確に報告する)。壊れた土台に対して書かれた skill は、誤った手順を教える。無関係な欠落資産が起動を妨げるとき (API が決して配信しない静的ディレクトリ、サンプル設定) は、生成する skill がそれを作ってもよい。ただし検証用の足場だと明確に印を付け、後始末で取り除くこと。

## 2. skill を生成する

`.cursor/skills/verify-<app>/SKILL.md` を、YAML frontmatter (`name: verify-<app>` と、アプリ名・表層・どんなときに手を伸ばすかを示す `description`。frontmatter が無ければ skill は決して登録されない) と、以下のセクションで書く。各セクションは、聞き込みで実際に判明したことに接地させる (プレースホルダを残さない):

- **起動:** 検証のためにアプリを起動する正確なコマンドと、準備ができたことをどう見分けるか (ログの行、応答するポート、プロンプト)。停止手順も含める。短命な CLI や TUI には、生かし続けるサーバが無い: 起動とは、バイナリのビルド (または依存の導入) を一度行い、その後は各操作をそれぞれ隔離された PTY か tmux セッションで開始することを意味する。
- **ドクター:** 「このインスタンスは操作する価値があるか?」に答える読み取り専用のチェックを 1 つ - プロセスが上がっている、バージョン/ビルドが正しい、ポートを自分たちが握っている、認証が有効。何かがおかしく見えるときは、エージェントはまずこれを実行する。
- **操作:** このリポジトリの実物のセレクタ/コマンドを使ったハーネスのレシピ。例示ではない。座標やタブ順ではなく、安定したハンドル (ARIA ラベル、data 属性、プロンプト文字列、ルートのパス) を優先する。
- **証拠:** 証明のために何を取り、それがどこへ行くか。証明の基準を明示する: 内部のセッターやテスト専用のエンドポイントではなく、実際のユーザ経路を動かす。最終画面だけでなく、操作とその結果の状態を取る。目に見えるものと並べて、副作用 (書かれたファイル、挿入された行、送られたメッセージ) も検証する。モックは、本番の境界が既に外部システムを隔離している箇所にのみ使う。安全な経路が dry-run やテストモードであるときは、それが実際に何を飛ばすのかを、名前を信じるのではなく観察 (ファイル、ネットワーク、git の ref) によって検証する: dry-run の中には、それでもネットワークに触れたりブラウザを開いたりするものがある。
- **後始末:** その実行が作ったインスタンスをどう畳むか。プロセス名で kill してはならない。自分が起動したものを kill する。後始末はインスタンスと一時的な状態を取り除くが、証拠は決して取り除かない: 証明の成果物は、skill が名前を挙げた場所で、取り壊しを生き延びる。
- **ヘルパー:** skill が同梱するスクリプトはどれも実行可能であり、その呼び出し方が skill の本文に示されている。読み手がリバースエンジニアリングしなければならないヘルパーは、ヘルパーではない。

## 3. feature map の種を蒔く

`.cursor/skills/verify-<app>/features/README.md` と、識別できたユーザ向け機能ごとに 1 ファイルを作る (まずは上位 3-5 個を目安に、ルート、コマンド、メニュー、ドキュメントから拾う)。[`references/feature-map-example/`](references/feature-map-example/) の形に従い、README のインデックスと、機能ごとに 1 ファイルを置く。各ファイルは、ユーザの視点から次に答える: その機能が何か、どうやってそこへ辿り着くか、ハーネスでどう操作するか、そしてどの観察可能な最終状態がそれが動くことを証明するか。4 つの H2 は `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、`Gotchas` だ。この map は、リポジトリで保守される検証のソースだ。map が他の入口も挙げているのに、都合の良い入口を 1 つだけ操作した証明は不完全だ。

## 4. 引き渡す前に、生成した skill を証明する

その skill 自身の手順を、端から端まで一度実行する: 起動、ドクター、map に載った機能を 1 つ操作 (1 つで十分だ。残りは後の実行でカバーできるように map がある)、証拠の取得、後始末。後始末の後、証拠が指定した場所にまだ存在することを確認する - 証明を食ってしまう後始末は、この手順に落ちる。失敗したものは直す。そして失敗した反復のたびに、生成した後始末も実行する。壊れた試行がプロセスやポートを取り残さないようにするためだ。一度も実行されていない生成 skill は、成果物ではなく下書きだ。

## 5. 保守のループを提案する

アプリが変わっても map を正直に保つために、ユーザに `/maintain-verification-skill` を指し示す。頻度の提案は、聞かれたときだけにする。
