# Notes の検証マップ

このディレクトリは、Notes のユーザ向け挙動を検証するために保守される情報源である。アプリを操作する前にこのインデックスを読み、対応する機能ファイルをレシピとして使う。

## ベースラインの前提条件

- 使い捨てのデータディレクトリを使って、Notes を `http://127.0.0.1:4173` で起動する。
- `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` を設定し、同時実行が状態を共有しないようにする。
- `Quarterly plan` と `Grocery list` というタイトルのノートを seed する。
- `control-notes` と `notes` CLI を `PATH` に置く。
- `control-notes doctor` を実行し、期待どおりの URL、データディレクトリ、ビルドリビジョンであることを必須とする。
- この検証実行が起動したのではないインスタンスを操作してはならない。

## 操作の規約

- 前提条件が別途指示していない限り、すべてのレシピはベースライン状態から始める。
- CSS セレクタや DOM の位置より、ARIA のロールとアクセシブルな名前を優先する。
- すべてのコマンドを字義どおりに扱う。クォートされた名前やフラグを変えない。
- ブラウザ操作は `control-notes browser` を通じて実行する。
- ターミナル操作は `control-notes cli -- <command>` を通じて実行する。
- 変更を加えた後は seed データを復元する。クリーンアップで証拠の成果物を消してはならない。

## 証拠とスキップの報告

- 最終画面だけでなく、ユーザの操作とその結果の状態を取得する。
- UI の証拠には、ARIA スナップショットと、アプリの identity が見えるスクリーンショットを含める。
- CLI の証拠には、コマンド、stdout、stderr、終了コードを含める。
- 変更の証拠には、保存された値を read-only で見た 2 つ目のビューを含める。
- 成果物ごとに、使った機能 ID と入口を記録する。
- 到達できなかった経路は、試したコマンドと満たされなかった前提条件とともに報告する。
- スキップした入口を、別の経路で検証済みとして報告してはならない。

## 機能エントリの契約

各機能ファイルは H1 のタイトルと、ユーザから見える挙動を説明する 1 段落で始まる。その後、ちょうど 4 つの H2 セクションをこの順で使う。

1. `Sub-features` は短い ID を列挙し、各挙動を 1 行で書く。
2. `How to get to it (user POV)` はユーザの入口をすべて列挙する。
3. `Driving it with <harness>` は `Preconditions:` で始まり、ラベル付きの箇条書きで、各ユーザ操作を厳密なコマンドと観測可能な結果に対応付ける。
4. `Gotchas` は、検証実行を無駄にしたり無効にしたりしうる罠を列挙する。

実装の詳細はマップに入れない。ユーザ経路、安定したハンドル、必要な状態、コマンド、観測可能な証拠だけを挙げる。

## 機能

- [ノートを作成する](./create-note.ja.md) はブラウザと CLI での作成、キャンセル、永続化、クリーンアップを扱う。
- [ノートを検索する](./search.ja.md) はツールバー、キーボード、CLI での検索を、マッチあり・空・クリアの状態とともに扱う。
