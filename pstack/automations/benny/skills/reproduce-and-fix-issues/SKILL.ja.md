# Reproduce and fix issues

source スレッドで信頼できる triage マーカーを待つ。対象アプリの実際の UI を通じて、厳密な症状を再現する。既存の修正があるときはそれを検証する。再現が確認できた後にのみ、範囲を限った修正を試みる。

automation から供給される外部の Benny 設定を読み込む。設定、必要なアクション、control adapter、完成した feature map のいずれかが欠けていれば fail closed する。

## 厳格な安全ルール

- 作業に入る前に、source channel と root スレッドの座標を凍結する。
- source channel にルートメッセージを投稿してはならない。
- source スレッドへの投稿の前には毎回、source の親をプリフライトする。
- Slack に投稿するのは coordinator だけである。
- 委任された分析ワーカーは読み取り専用であり、findings かメディアに関するメモを返す。
- fix フェーズのコードワーカーが編集してよいのは、その環境が Slack の資格情報とすべての Slack 書き込みアクションを確実に除外していると証明できるときだけだ。それ以外では coordinator が編集する。
- すべての子プロンプトは、`SendSlackMessage`、`PostToSlack`、`chat.postMessage`、およびその他すべての Slack 書き込みを明示的に禁止しなければならない。
- 子に Slack トークン、投稿の指示、投稿用の source 座標、外部へ報告する許可を与えてはならない。
- 子が動くために Slack の書き込みアクセスを必要とするなら、それを起動してはならない。
- ユーティリティ bot は証拠源である。人が明示的にその bot に修正を委任していない限り、修正の所有者ではない。
- 症状を区別できる厳密な事象が、実際の UI 操作を通じて 2 回現れなければならない。
- 状態の検査は観測の裏付けにはなる。症状を注入したり強制したりしてはならない。
- 再現が確認できていないなら、修正を書くことはない。
- 既存の pull request や commit があれば、その実行は verify モードに切り替わる。その上に書き足してはならない。
- pull request のリンクは `github.com` のものを使う。
- キャプチャ、録画、ログ、トークンをソース管理に入れない。
- 委任した分析には pstack の `principle-guard-the-context-window` を使う。
- 再現、修正、検証を通じて pstack の `principle-sequence-verifiable-units`、`principle-fix-root-causes`、`principle-prove-it-works` を適用する。

## 1. source 座標を凍結する

作業リストを作る前、また委任する前に:

1. トリガーの channel が、設定した source channel と一致することを必須とする。
2. `trigger.thread_ts` があればそれを `SOURCE_THREAD_TS` に設定する。無ければ `trigger.ts` を使う。
3. `SOURCE_THREAD_TS` が空でないことを必須とする。
4. `SOURCE_CHANNEL_ID` と `SOURCE_THREAD_TS` を不変の値として保存する。
5. source スレッドを読み、その root がその厳密な座標を持つことを検証する。
6. source の permalink を取得する。

これらの値を、返信のタイムスタンプ、operations のタイムスタンプ、ステータスメッセージのタイムスタンプで置き換えてはならない。

source channel への投稿の前には毎回:

1. 不変の座標でスレッドを読む。
2. 親が存在し、削除されておらず、依然として source channel に属することを確認する。
3. `channel=SOURCE_CHANNEL_ID` と `thread_ts=SOURCE_THREAD_TS` を指定してのみ送信する。
4. スレッドを再度読み、新しいメッセージが返信になっていることを検証する。

いずれかのチェックが失敗したら、何も投稿しない。root やフォールバックの channel で再試行してはならない。

## 2. triage の契約を待つ

設定した verdict の予算のあいだ、source スレッドを監視する。待っている間は沈黙を保つ。

verdict を受け入れるのは次をすべて満たすときだけだ:

- 作者が `slack.triage_identity_user_id` と一致する。
- `SOURCE_THREAD_TS` の下の返信である。
- 設定されたマーカーをちょうど 1 つ含む。

公開マーカーの形式:

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

進むのは `bug` または `performance` のときだけだ。任意の tracker URL を取得する。`other`、verdict の欠如、信頼できない作者、矛盾するマーカー、タイムアウトのときは黙って止まる。

このマーカーが、非公開の bot identity や自由記述の verdict マッチングに取って代わる。

## 3. 所有権と修正成果物のゲートを適用する

作業を始める直前にスレッドを読み直す。

### 誰かが明確に修正している

人が明確に修正を引き受けている、具体的な実装プランを示している、あるいは別のエージェントに実装・パッチ・修正・pull request の作成を頼んでいるときは止まる。

次のものは修正の所有権として扱わない:

- bot が証拠を要約している。
- ツールがログやチケットを調べている。
- 誰かが bot に診断・説明・調査・再現を頼んでいる。
- bot が原因の仮説を投稿しているが、実装に同意していない。

bot の存在ではなく、依頼されたアクションで判断する。

### 修正成果物が既に存在する

open な pull request または merge 済みの commit が、この報告をもっともらしく修正しているなら、`references/verify-existing-fix.md` に切り替える。

成果物はスレッド、tracker の issue、リポジトリの履歴、pull request の検索のいずれから来てもよい。commit も pull request も伴わない主張は修正成果物ではない。

人がその作業を所有していて、まだ成果物を出していないなら止まる。競争してはならない。

## 4. 任意の operations スレッドを開く

`slack.operations_channel_id` が設定されているなら、coordinator はそこにルートのステータスメッセージを 1 件作ってよい。これが repro ワークフローで唯一許されるルート投稿である。

その座標を `OPERATIONS_CHANNEL_ID` と `OPERATIONS_THREAD_TS` として保存する。source の座標と決して混同しない。

設定された素の Unicode ステータス文字列を使う。ステータスのテキストは短く保つ:

- Reproducing
- Could not reproduce
- Blocked
- Reproduced
- Verifying existing fix
- Attempting bounded fix
- Draft pull request opened
- Fix did not land

設定された Cursor の Slack アクションを優先する。`BENNY_SLACK_BOT_TOKEN` を使うのは、このステータスメッセージ 1 件の編集のような、狭い欠落機能のためにユーザが設定したときだけだ。トークンをワーカーに晒してはならない。

operations channel が設定されていないなら、詳細なステータスは automation の実行出力に保つ。source channel のルートメッセージで代用してはならない。

## 5. control adapter を読み込んで確認する

`references/control-adapter.md` と `control.feature_map_path` にある完成した map を読み、次に `control.skill_name` が指す skill を呼び出す。

報告されたユーザ経路に一致する feature map のセクションを探す。アプリを操作する前にそれを読む。その機能をカバーするセクションが無いなら、経路やセレクタを捏造せず、その実行を blocked とする。

次の 7 つの機能すべてを必須とする:

1. 設定された対象アプリとテスト環境を起動する。
2. map された機能へ遷移し、文書化された状態を再現する。
3. クリック、入力、キー、スクロール、ドラッグ、リサイズ、遷移で実際の UI を操作する。
4. 状態を変更せずに検査する。
5. スクリーンショットを撮る。
6. 画面録画を開始・停止する。
7. プロセス、セッション、プロファイル、一時データを片付ける。

adapter が無い、または必須の機能のいずれかが欠けているなら、operations のステータスを blocked にして止まる。スクリーンショット、ユニットテスト、状態の変更、ソースの読解を UI の再現だと言い張ってはならない。

## 6. 報告を精査する

source スレッド全文と、あれば tracker の issue を読む。

収集するもの:

- 厳密なアクションの経路
- 期待される挙動
- 観測された挙動
- 両者が分岐する、区別可能な状態
- 発生頻度
- バージョン、環境、プラットフォーム
- 添付とエラーのシグネチャ
- 候補となるコード領域

スクリーンショットと動画を確認する。コードの履歴、テストの案、影響範囲のマッピング、メディアのレビューには、有用なら読み取り専用の並列ワーカーを使う。各ワーカーには狭い問いと、Slack 書き込み禁止を与える。

pstack の `how` skill を使って、そのアクションをリポジトリ内で辿る。リグレッションの履歴と防御的コードには `why` を使う。競合する原因仮説を立て、それらを切り分ける証拠を特定する。

## 7. 再現する

control adapter を通じて対象アプリを起動する。

操作の前に、正しいアプリ、ワークスペース、アカウント、データセット、機能の状態であることを確認する。安定したアプリのマーカーを使う。ウィンドウの順序や見覚えのあるタイトルだけに頼らない。

報告された経路を、実際の UI 操作で辿る。

再現したと呼ぶ前に:

1. 正しい最終状態を言語化する。
2. 壊れた最終状態を言語化する。
3. 両者が分岐する地点まで到達する。
4. 壊れた状態を観測する。
5. 2 回目の試行が独立になるだけの状態をリセットする。
6. 同じ経路を繰り返し、同じ壊れた状態を再び観測する。
7. 可能なら実際の状態値をクロスチェックする。

想定されたダイアログ、ローディング状態、セットアップの手順はバグではない。正しい挙動と壊れた挙動を区別する最終状態を捉える。

設定された repro の予算を使う。その範囲で症状が再現しないなら、`Could not reproduce` という明快な結果を報告する。環境が必要な機能を提供できないなら `Blocked` を報告し、何が欠けていたかを述べる。

## 8. 証拠を取得してレビューする

再現に成功した場合:

- 症状に至る経路全体を録画する。
- 壊れた最終状態のスクリーンショットを撮る。
- 厳密な手順と観測された状態を書いた短いメモを保存する。
- 成果物は設定された一時成果物ディレクトリに置く。

読み取り専用のメディアレビュワーに、ひとつの問いだけを答えさせる。その証拠は、区別可能な壊れた状態を目に見える形で示しているか。

答えが no または不確かなら、再現は確認されていない。もっとよい証拠を取るか、`Could not reproduce` を使う。

詳細な証拠は、設定されている場合の operations スレッドにのみ投稿する。source への更新は簡潔に保つ。

## 9. 再現の結果を報告する

まず operations のステータスを更新する。

`Could not reproduce` または `Blocked` の場合は、source スレッドに何も投稿しない。operations スレッドか実行出力が結果を運ぶ。

再現が確認できた場合は、source のプリフライトを実行し、依頼されていない source への返信を最大 1 件投稿する:

- issue が再現したと述べる。
- operations の証拠スレッドがあればリンクする。
- 短い findings を最大 3 件含める。
- tracker の issue があればリンクする。
- 既定では所有者を ping しない。

証拠を添付するのは、設定された Slack アクションがそれを同じ source スレッド内に留め、かつ組織の保持ポリシーが許すときだけだ。

設定された rejection ウィンドウのあいだ待つ。セットアップや解釈が誤っていたと人が示したなら、再現を 1 回修正する。有効な棄却が無いままウィンドウが閉じるまで、fix フェーズを始めてはならない。

## 10. 既存の修正を検証する

修正成果物が存在するときは `references/verify-existing-fix.md` に従う。

検証は、ベースラインで症状が出ること、パッチ適用済みのビルドで症状が出ないことを示さなければならない。どちらの経路も実際の UI で 2 回行う。

既存の修正を編集したり、競合するパッチを足したり、置き換えの pull request を開いたりしない。

## 11. 範囲を限った修正の資格を確認する

次のすべてが成り立つときにだけ修正を試みる:

- 結果が、素直に再現が確認された状態である。
- メディアレビューが壊れた最終状態を確認した。
- 既存の修正成果物が現れなかった。
- rejection ウィンドウのあいだ、誰も修正を引き受けなかった。
- ランタイムの証拠が根本原因を特定している。
- 想定される変更が、設定された fix の予算とリポジトリのスコープに収まる。
- control adapter がベースラインとパッチ適用済みの両方のビルドを走らせられる。

いずれかの条件が満たされないなら、再現の報告を保ったまま、pull request を出さずに止まる。

ゲートを通過したら、operations のステータスを `Attempting bounded fix` に更新する。

## 12. 根本原因を突き止めて実装する

Slack への投稿すべて、最終的な diff のレビュー、commit、pull request は coordinator が所有する。

読み取り専用のワーカーができること:

- コードと履歴を辿る
- テストを提案する
- 影響範囲をマップする
- diff をレビューする
- メディアをレビューする

ワーカーは編集せず、外部への書き込みを実行せず、ステータスを投稿せず、修正を所有しない。

このフェーズで厳密にスコープを絞ったコード編集を委任してよいのは、ツールの隔離によって Slack の資格情報とすべての Slack 書き込みアクションがそのワーカーから取り除かれているときだけだ。そのプロンプトにも、明示的な Slack 書き込み禁止を必ず載せる。coordinator が編集をレビューし、必要なテストを実行するか検証する。ツールの隔離が不確かなら、編集は coordinator に留める。

メカニズムをランタイムの証拠で確認する。編集の前に競合する仮説を消す。

正当化できる最小の変更で根本原因を修正する。

- 安価なローカルのテスト対象があるときは pstack の `tdd` skill を呼び出し、修正の前に落ちるテストを書く。
- 経路が高コスト、不明瞭、あるいは結合テスト寄りで TDD を省いた場合は、その理由を述べる。
- 無関係な掃除を入れない。
- 変更が設定された工数やリスクの予算を超えて膨らんだら止める。

## 13. 修正を証明する

元のベースラインの証拠は保持する。

パッチ適用済みのビルドで:

1. 同じ実際の UI 経路を実行する。
2. それを 2 回繰り返す。
3. 壊れた状態が消えていることを示す。
4. その場所に期待される状態が現れることを示す。
5. after の録画とスクリーンショットを取る。
6. ベースラインで使ったのと同じ実際の状態値をクロスチェックする。

コンパイル、ユニットテスト、コードレビュー、もっともらしい diff は after の証拠ではない。

絞り込んだテストを実行し、次に変更した挙動の周りの影響範囲をスモークする。その変更が影響しうる近傍の状態、入力、権限、プラットフォーム、失敗経路をカバーする。リグレッションが残るなら、pull request を出さずに止める。

## 14. draft pull request を開く

before-and-after の証明が取れた後にだけ:

- 最終的な diff に無関係な変更やシークレットが無いかレビューする。
- リポジトリの必須チェックを実行する。
- リポジトリのワークフローが許すなら、小さく順序立てた commit を作る。
- draft pull request を開く。このワークフローから merge も deploy もしてはならない。
- 設定した tracker の issue を、その tracker が対応する pull request の構文でリンクする。
- 設定された公開 URL の形式、通常は `https://github.com/{owner}/{repo}/pull/{number}` を使う。
- 再現の手順、根本原因、テスト結果、before と after の証拠、影響範囲のチェックを含める。
- pull request の本文と Slack への更新はすべて pstack の `unslop` skill に通す。

pull request の作成に失敗したら、成功したと主張してはならない。commit やブランチの状態を実行出力に残し、operations のステータスを `Fix did not land` にする。

成功したら、operations のステータスを `Draft pull request opened` にし、operations スレッドに pull request をリンクした簡潔な返信を 1 件投稿する。source channel の 2 つ目のルートや、依頼されていない source への返信を作ってはならない。

## 15. フォローアップと片付け

設定された operations スレッドを、1 回のフォローアップウィンドウのあいだ監視する。

- 既に集めた証拠から、直接の質問に答える。
- セットアップを無効化するような具体的な訂正が 1 件あれば、それを適用して再現を 1 回やり直す。
- 人間同士の調整や雑談には立ち入らない。
- 止めるよう言われたら止まる。

control adapter の片付け機能を必ず呼ぶ。成果物は設定された保持ポリシーが許す期間だけ保つ。
