# control-adapter の契約

Benny は、あらゆるアプリの起動方法や操作方法を知っているわけではない。ユーザは、対象アプリ向けにこの契約を実装した control skill またはアダプタを 1 つ設定しなければならない。

その skill 名を `control.skill_name` に設定する。

記入済みのユーザ向け feature map のパスを `control.feature_map_path` に設定する。[`feature-map.example.md`](./feature-map.example.ja.md) をコピーして `.cursor/automations/benny/` の外で記入する。コピー元のサンプルを直接編集しない。

skill、feature map、または必要なケイパビリティが欠落・曖昧・不完全な場合、再現と修正の作業は fail-closed でなければならない。

## 必須のケイパビリティ

### Bring up

要求されたアプリのリビジョンを、要求されたテスト環境で起動する。

入力:

- リポジトリとリビジョン
- ビルドまたは起動のモード
- ワークスペース、アカウント、fixture、機能状態の要件
- 成果物ディレクトリ
- 記入済みの feature map のパス

戻り値:

- セッション識別子
- アダプタが正しいアプリと環境をどう確認したか
- 安定したアプリのマーカー
- 後続の呼び出しに必要な、実行中のプロセスやターゲットの詳細
- 欠けているケイパビリティ

アダプタは、対象アプリを類似のウィンドウ、シェル、本番インスタンスと区別できなければならない。

### Drive UI

実際のユーザ操作を行う:

- クリック
- 入力
- キー押下
- スクロール
- ドラッグ
- リサイズ
- アプリのコントロールを通じたナビゲーション

ロール、ラベル、安定したセレクタを優先する。座標は、新しく撮ったスクリーンショットの後にのみ使う。

各アクションと、観測された状態変化を返す。

内部状態を直接設定する、隠しアプリメソッドを呼ぶ、ストレージに直接書き込む、DOM 変更を注入する、といった方法で症状を作り出してはならない。

### Drive mapped features and states

アプリを操作する前に、該当する feature map のセクションを読む。

アダプタは以下の手段を公開しなければならない:

- マップされたすべての機能へ、ユーザから見える経路でナビゲートする。
- その機能に対して列挙されたアダプタのアクション名を実行する。
- default、hover、focus-visible、active、disabled、loading、empty、error、selected、open、expanded、および機能固有の状態が該当する場合に、それらと対話する。
- 安全な fixture データ、権限、フラグ、サービスの応答、またはサポートされたテスト用コントロールを通じて状態を用意する。
- 2 回目の独立した再現試行のために機能をリセットする。
- feature map が指定するスクリーンショット、動画、read-only のクロスチェックを取得する。

ロール、アクセシブルな名前、ARIA の関係、安定したコンポーネントのマーカー、目的を表す名前の data 属性を使う。生成された CSS や StyleX のクラス、動的なハッシュ、子要素のインデックス、脆い DOM の位置を使ってはならない。

前提条件を用意することは、報告された症状を注入してよいという許可ではない。再現そのものは、依然として実際のユーザ操作から生じなければならない。

### Inspect state

UI が表示している内容を確認するために状態を読む。

例:

- アクセシビリティツリー
- DOM またはビュー階層
- プロセスの状態
- ローカルのログ
- ネットワークリクエストのステータス
- アプリが公開しているデバッグ状態

検査は read-only である。クエリが状態を変えるなら、それは `drive UI` に属し、実際のユーザ操作を表現していなければならない。

### Screenshot

現在のアプリ状態を、要求されたパスにキャプチャする。

戻り値:

- ファイルパス
- キャプチャ時刻
- アプリのマーカーまたはウィンドウタイトル
- 何が見えているはずかの短い説明

スクリーンショットは、正しいアプリがテスト対象であると証明できるだけのアプリの外枠を含まなければならない。

### Recording

再現経路の全体を挟むように、画面録画を開始・停止する。

戻り値:

- ファイルパス
- 開始時刻と停止時刻
- キャプチャしたウィンドウまたは領域
- 音声や機微なオーバーレイを除外したかどうか

録画は、セットアップやローディング画面だけでなく、決定的な最終状態を示さなければならない。

### Cleanup

アダプタが作成したプロセスとセッションを停止する。

使い捨ての以下を削除する:

- ブラウザまたはアプリのプロファイル
- 一時的なワークスペース
- アダプタが作成した場合のテストアカウントや fixture
- デバッグ用ポートとトンネル
- 保持期間を過ぎたキャプチャ

何を停止し、削除し、保持し、人間のために残したかを返す。

Cleanup はユーザの作業物を削除してはならない。

## アダプタの振る舞い

アダプタは以下を満たさなければならない:

- 再現を始める前にケイパビリティを報告する。
- feature map のどのセクションを操作でき、どれがブロックされているかを報告する。
- baseline ビルドと patched ビルドで同じ環境入力を使う。
- 起動の失敗は失敗として表面化する。
- リトライに上限を設ける。
- シークレットをログや成果物に残さない。
- キャプチャをリポジトリの外に置く。
- 2 回の再現試行の間で、まっさらな状態またはリセット済みの状態をサポートする。
- ユーザが安全なテスト用アクションを明示的に設定していない限り、本番への変更を避ける。

## 環境の読み替え

環境ブロックを宣言する前に、プラットフォーム固有の名詞を使わずに欠陥を言い直し、同じ挙動を利用可能な環境で安全にテストできないかを問う。

例:

- 特定のブラウザ名は、任意の外部ブラウザを意味しうる。
- 特定のキー名は、設定されたショートカットを意味しうる。
- 特定のリモートホスト名は、遅延した、あるいは切断されたリモートターゲットを意味しうる。

読み替えた試行は、同じ根底の挙動をテストしている場合にのみ使う。読み替えた証拠であるとラベルを付ける。欠けている環境そのものが欠陥の一部である場合、それを厳密な再現と呼んではならない。

ハードウェアのプロンプト、OS の権限ダイアログ、デバイス固有の API、利用できないアカウント状態は、本当のブロックでありうる。

## セットアップチェック

再現 automation を有効化する前に、無害なアダプタチェックを 1 回実行する:

1. アプリを起動する。
2. 安定したアプリのマーカーを確認する。
3. 記入済みの feature map セクションを 1 つ読み込む。
4. ユーザ経路を通じてその機能へナビゲートする。
5. マップされたアダプタのアクションを通じて、使い捨ての状態を 1 つ実行する。
6. 結果の状態を検査する。
7. スクリーンショットを取得する。
8. 短いクリップを録画する。
9. 後始末する。

9 つのステップがすべて成功し、発生元チャンネルへの Slack 投稿が一切関与しない場合にのみ、再現作業を有効化する。
