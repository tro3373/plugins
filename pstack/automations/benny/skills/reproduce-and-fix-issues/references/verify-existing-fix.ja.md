# 既存の修正を検証する

オープンな pull request またはマージ済みコミットが、報告された問題を修正している見込みがあるときにこのモードを使う。

修正の所有権は既存の成果物にある。それを検証せよ。編集してはならず、対抗するパッチを書いてはならず、別の pull request を出してはならない。

## 成果物を適格と判定する

具体的な成果物を 1 つ要求する:

- 症状に対処するコード変更を含むオープンな pull request
- マージ済みの pull request
- コードと意図が一致するマージ済みコミット

pull request もコミットも伴わない、スレッド上の主張、トラッカーのステータス、ブランチ名、原因の仮説は不十分である。

複数の成果物があるときは、ソーススレッドまたはトラッカーからリンクされているものを選ぶ。それがないなら、影響を受けるコードに最も近いものを選び、その理由を述べる。

## 作業ツリーを守る

リポジトリが対応しているなら、隔離された worktree か別のクリーンなチェックアウトを使う。ユーザの変更を上書きしてはならない。

記録する:

- ベースラインのリビジョン
- パッチ適用後のリビジョン
- pull request またはコミットの URL
- 両方の実行で共有されるビルドと環境の入力

pull request のリンクは通常の `github.com` のものを使う。

## ベースラインを測る

オープンな pull request では、その base ブランチをベースラインとして使う。

マージ済みの修正では、修正の直前のリビジョンがビルドでき、かつ旧挙動を表しているなら、それを使う。

設定されたコントロールアダプタを通じて:

1. ベースラインのアプリを立ち上げる。
2. 正しいアプリと環境であることを確認する。
3. 報告された経路を実際の UI 操作で通す。
4. 判別可能な症状を観察する。
5. リセットして繰り返す。
6. ベースラインの録画、スクリーンショット、状態チェックを取得する。

ベースラインで症状が 2 回現れないなら、ベースラインは存在しない。修正が効いていると主張してはならない。

## パッチ適用後のビルドを測る

pull request または修正コミットを、同じ環境と同じデータでビルドして実行する。

1. 同じ UI 経路を通す。
2. それを 2 回繰り返す。
3. 壊れた状態が消えていることを確認する。
4. 期待される状態が現れることを確認する。
5. 事後の録画、スクリーンショット、同じ状態チェックを取得する。

コンパイルやテストで止まってはならない。事後の結果は、動いているパッチ適用済みアプリから得たものでなければならない。

## 結末

### Confirmed

ベースラインで 2 回再現し、パッチ適用後のビルドで 2 回解消している。

- オペレーションのステータスを verified にする。
- 成果物をリンクする。
- ソースの preflight の後、ソーススレッドに簡潔な返信を 1 つ投稿する。
- 事前と事後の結果を含める。
- pull request は出さない。

### Insufficient fix

ベースラインでもパッチ適用後のビルドでも症状が現れる。

- オペレーションのステータスを reproduced but not fixed にする。
- 成果物をリンクし、それでは症状が解消しなかったと述べる。
- この実行でまだ使っていないなら、通常の「再現を確認した」ソース更新を投稿する。
- 対抗する pull request は出さない。

### Inconclusive

ベースラインが再現しない、パッチ適用後のアプリが実行できない、または証拠が判別可能な状態を示していない。

- 成功を主張してはならない。
- どちらの半分が測定できなかったかを述べる。
- 結果はオペレーションスレッドまたは実行の出力に留める。
- 直接の質問に答える必要がある場合を除き、ソーススレッドには何も投稿しない。

## 後始末

両方のビルドを停止し、一時プロファイルとキャプチャを保持ポリシーに従って削除し、ユーザの作業を捨てることなくリポジトリを元の状態に戻す。
