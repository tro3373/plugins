# issue レポートのトリアージ

Slack のレポートを 1 件分類し、その発生元スレッドに有用な判定を 1 つ投稿する。明確かつ新規のバグの場合のみ tracker に issue を作成する。ここで再現や修正は行わない。

automation から供給される外部 Benny 設定を読み込む。設定が欠落している、壊れている、不完全な場合は、投稿も tracker への書き込みもせずに停止する。

## 厳格な安全ルール

- 発生元チャンネルとルートスレッドの座標は不変である。
- 発生元チャンネルにルートメッセージを投稿してはならない。
- 別チャンネルへの投稿、返信のブロードキャスト、DM 送信、代替スレッドの開始をしてはならない。
- tracker への書き込み前と、判定投稿の直前に、発生元の親メッセージを preflight する。
- 親が欠落・削除済み・アクセス不能・不確かな場合は、書き込みを一切せずに停止する。
- 実質的な判定を 1 つだけ投稿する。進捗を実況しない。
- Slack に投稿するのはコーディネータだけである。
- 委譲されたワーカーは findings のみを返す。ワーカーは read-only でなければならず、Slack の資格情報や書き込みアクションを渡してはならない。
- すべての子プロンプトは `SendSlackMessage`、`PostToSlack`、`chat.postMessage`、およびその他あらゆる Slack 書き込みを禁止しなければならない。
- ワーカーの隔離でその制限を強制できない場合は、コーディネータ側で作業する。
- 発生元スレッドにリンクを張り戻せない issue を作成してはならない。
- 推測や重複のチケットを作るより、チケットを作らないほうがよい。
- 発生元座標には pstack の `principle-separate-before-serializing-shared-state` を適用する。
- 最終的な判定には pstack の `principle-minimize-reader-load` と `unslop` skill を適用する。

## 1. 発生元座標を凍結する

作業リストを作る前、または委譲する前に:

1. トリガーから `source_channel_id` を読む。
2. それが設定された発生元チャンネルと一致することを必須とする。
3. `trigger.thread_ts` があればそれを `SOURCE_THREAD_TS` に設定する。無ければ `trigger.ts` を使う。
4. `SOURCE_THREAD_TS` が空でないことを必須とする。
5. `SOURCE_CHANNEL_ID` と `SOURCE_THREAD_TS` を不変値として保持する。
6. スレッドを読み、そのルートがまさにその座標を持つことを検証する。
7. 安定した発生元 permalink を取得する。

以降の発生元の読み取りと投稿は、すべてその保持した値を使わなければならない。返信のタイムスタンプや運用スレッドのタイムスタンプで置き換えてはならない。

## 2. レポート全体を読む

判断する前に、ルートと現在の返信を読む。

以下を捉える:

- 報告者の言い回し
- 製品バージョン、アプリのビルド、環境、プラットフォーム (記載があれば)
- 期待される挙動
- 観測された挙動
- 頻度とトリガー
- エラーテキストまたはスタックのシグネチャ
- 既存の issue、コミット、pull request のリンク
- 誰かが既に修正中であるという明示的な記述

関連するすべての添付を確認する。

- スクリーンショットは有用な解像度のまま読む。
- 動画は、正常な挙動と壊れた挙動を分ける状態遷移に注目してレビューする。
- ログ、トレース、クラッシュテキストは具体的なシグネチャを求めて読む。
- メディアに専門的なレビューが必要なら、read-only のメディアワーカーを使い、絞った質問をする。ワーカーは findings のみを返す。
- 添付が読めない場合は、その旨を判定に書く。何が写っているかを捏造してはならない。

報告者に追加情報を求める前に、スレッドに既にある証拠を使う。

## 3. ルーティング前に原因を追う

オーナーや宛先を選ぶ前に、範囲を区切ったソースと履歴の調査を行う。pstack の `how` skill を使い、報告されたアクションから観測された結果までの経路を追う。レポートがリグレッションに見える場合や防御的コードに触れる場合は `why` を使う。

1. 報告されたアクションから観測された結果までの、ありうるコードパスを特定する。
2. 見えている症状がそのコードパスに属するのか、その下の依存に属するのかを確認する。
3. レポートがリグレッションに見える場合は最近の変更を確認する。
4. マージ済みコミットやオープンな pull request が既に同じ症状に対処していないか確認する。
5. 確認済みの事実と仮説を分ける。

この調査で完全な根本原因まで到達する必要はない。見えている症状を誤ったオーナーにルーティングしない程度に強ければよい。

リポジトリが読めない場合は、コードオーナーを推測してはならない。保守的な分類のまま進め、原因追跡ができなかったと述べる。

## 4. 分類する

カテゴリを 1 つ選ぶ。

### Bug

意図された挙動に違反している。例としては、誤った出力、壊れた状態、エラー、クラッシュ、ハング、無言の no-op、リグレッションなど。

### Performance

計測可能な遅さ、過剰なメモリ、バッテリー消費、ジャンク、その他のリソース問題を報告している。バグとして扱うが、計測値とプロファイルを保持する。

### Feature request

現在の挙動は意図的に見えるが、報告者が別の挙動やアフォーダンスを望んでいる。

### Question or feedback

何かの動作の仕方を尋ねている、具体的な欠陥なしに好みを述べている、または一般的なフィードバックである。

### Reroute

原因追跡の結果、別の設定済み宛先がその issue のオーナーであると判明した。

バグかフィーチャーかの線引きが不明瞭な場合は、起票しない。唯一の判定の中で、絞った質問を 1 つだけして `other` マーカーを使ってよい。

## 5. 設定されたルーティングを適用する

`routing.map_path` からオプションのルーティングマップを読む。

- 確認済みの製品領域、コードパス、エラーシグネチャでマッチする。
- 原因追跡が別を指しているとき、見えている症状だけでは根拠として不十分である。
- マッチするルートが無ければ、オーナーが不明であると述べる。推測しない。
- クロスポストしない。発生元スレッドで、報告者にどこへ持って行くべきかを伝える。

オーナーへの ping は既定でオフである。ping が許されるのは、以下がすべて成り立つ場合のみ:

1. ルーティングマップがそのオーナーを明示的に指名している。
2. 設定がその ping の種類を許可している。
3. その項目が、オーナーの意見を要する feature request であるか、直近の履歴が強い証拠とともにリグレッションの作成者を特定している。
4. そのオーナーが広範なオンコールグループでない。

これ以外のケースでは ping しない。

## 6. issue tracker アダプタを使う

tracker はアダプタであり、特定のベンダーを必須とするものではない。Linear アダプタは有効な一例である。GitHub Issues アダプタや他の tracker が同じ契約を実装してもよい。

設定されたアダプタは以下を提供しなければならない:

- テキスト、状態、ラベル、ソース URL、日付範囲による issue 検索
- 1 件の issue とそのリンクの読み取り
- タイトル、本文、ステータス、ラベル、ソース URL を伴う issue の作成
- 無関係なフィールドを置き換えずに既存 issue を更新する
- ソースリンクと再発ノートの追加
- Slack への引き渡しに失敗した場合に、この実行で作成した issue をキャンセル・クローズ・削除する

必要な操作が使えない場合は、その書き込みについて fail-closed とする。

設定された team、project、status、label は実行時に解決する。設定が明示的に要求しない限り、ID を捏造したり、ラベルを作成したり、オーナーをアサインしたり、優先度を設定したりしてはならない。

## 7. 重複排除する

この発生元 permalink が既に tracker の issue や過去のトリアージ返信に紐付いていないかを、必ず確認する。紐付いていれば、重複した投稿も作成もしない。

バグとパフォーマンスのレポートについては、以下を使って tracker を検索する:

- 厳密なエラーまたはクラッシュのシグネチャ
- 製品領域
- トリガー
- 症状
- バージョンまたは日付のウィンドウ
- リグレッションの疑いがあるコミット
- 発生元 permalink

結果を 1 つ選ぶ:

- 確度の高い重複: シグネチャが同一、または領域・トリガー・症状が同一、または原因の共有が確認済み。
- 関連の可能性あり: 原因の共有はありうるが証明されていない。
- 類似が弱い: 似ているのは表層だけ。
- 一致なし。

確度の高い重複の場合は、既存 issue に発生元 permalink と短い再発ノートを 1 つ追加して更新する。設定がそう指示しない限り、reopen・ラベル変更・アサイン変更はしない。

可能性ありの一致の場合は、不確かなものとして判定にリンクし、何も作成しない。

長くクローズされている issue はリグレッションの手掛かりであり、自動的に現行の重複と見なされるわけではない。

## 8. 作成するかどうかを判断する

以下がすべて真の場合にのみ作成する:

1. 分類が bug または performance である。
2. 挙動が明確に壊れている。
3. その issue がまだ現行であるか、修正済みと分かっていない。
4. 重複排除で、確度の高い一致も妥当な現行の一致も見つからなかった。
5. 発生元の親と permalink が preflight を通過した。
6. tracker の対象フィールドが解決できた。
7. 判定の投稿が失敗した場合にアダプタが補償できる。

feature request、question、feedback 項目、reroute、重複の可能性あり、確度の高い重複、修正済み issue では、決して作成してはならない。

新規 issue は自己完結していなければならない:

- 領域と症状を示す平易なタイトル
- 報告者の引用
- 期待される挙動と観測された挙動
- バージョンと環境、または `unknown`
- トリガーと頻度
- 発生元スレッドの permalink
- 短い原因追跡の findings。仮説は仮説として明示する
- サポートされていればスクリーンショットまたは代表的な動画フレームをインラインで
- 残りの成果物へのリンク
- 設定された intake ステータスとラベル

推測した根本原因をタイトルに入れてはならない。

## 9. 判定を 1 つ投稿する

発生元の親に対する preflight を新たに実行する。その上で `channel=SOURCE_CHANNEL_ID` と `thread_ts=SOURCE_THREAD_TS` を指定して、返信をちょうど 1 つ投稿する。

`thread_ts` が空のまま発生元チャンネルへの投稿アクションを呼んではならない。

返信は短く保つ:

- 結論から書く。
- 既存または新規の tracker issue があればリンクする。
- 必要なら reroute または欠落している事実を 1 つ挙げる。
- 許可されたオーナー ping は最大 1 つまで含める。
- ちょうど 1 行のマーカー行で終える。

マーカーの契約:

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

設定されたマーカー文字列だけを使う。再現 automation は、この発生元スレッドで設定されたトリアージ identity から来たマーカーだけを信頼する。

投稿後、同じ発生元スレッドを読み、判定が `SOURCE_THREAD_TS` の下に現れていることを検証する。現れていない場合も、ルートで再試行してはならない。

この実行で tracker issue を作成し、判定が着地しなかった場合は、アダプタの補償アクションを使う。その issue がキャンセル・クローズ・削除されたことを検証する。補償を検証できない場合は、その失敗を automation の実行出力にのみ報告する。

## 10. フォローアップのウィンドウを 1 回だけ見張る

設定されたフォローアップ期間だけ発生元スレッドを見張り、その後停止する。

- トリアージ identity への直接の質問にのみ答える。
- 安全なときは、具体的な訂正を tracker issue に反映する。
- 同一実行で 2 つ目のマーカーを出してはならない。
- 人間同士の調整や雑談には立ち入らない。
- automation に停止を求められたら早期に停止する。

ウィンドウを 2 回以上延長してはならない。新しいレポートは新しい実行として始めるべきである。
