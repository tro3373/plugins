# Benny をセットアップする

Benny は pstack の中に休眠状態のオートメーションパックとして同梱されている。プラグインのマニフェストが公開しているのは pstack の通常の skill ルートだけであり、このファイルと 2 つの運用ファイルはスラッシュ skill ではない。

人間は、パックの `FOR_AGENTS.md` に Cursor を向けることでセットアップに入る。ブートストラップのフローはパック全体を対象リポジトリへコピーし、その後このファイルを `.cursor/automations/benny/skills/setup-benny/SKILL.md` から直接読む。

Benny は外部設定と 2 つのライブ Cursor オートメーションを必要とする。

ユーザが明示的に求めるまで、オートメーションを作成・更新してはならない。シークレットの値をプラグインファイル、プロンプト、コミットされる設定に決して入れてはならない。

## 1. パックをコピーし、共有 pstack skill を有効にする

Benny の設定を尋ねる前、かつ組み込みの `/automate` skill を呼ぶ前に、これを行う。

どのリポジトリでオートメーションを実行するかを尋ねる。ソースパックは `FOR_AGENTS.md` を含むディレクトリである。コピー先は `<target-repository>/.cursor/automations/benny/` である。

ソースパック全体をコピー先へマージする:

1. コピー先が無ければ作成する。
2. 全てのソースファイルを同じ相対パスへコピーする。
3. コピー先にしかないファイルは保持する。インストールやリフレッシュの際に無関係なファイルを決して削除してはならない。
4. ユーザ所有の設定、feature map、routing map はコピー先の外に置く。決して上書きしてはならない。
5. 既存のソース管理下のファイルに差異があるときは、diff を精査し、ローカルの編集を捨てずにマージする。所有権が曖昧なら、置き換える前に止めて尋ねる。
6. コピー先に `FOR_AGENTS.md`、このセットアップファイル、2 つの運用ファイル、それらの references、テンプレートが揃っていることを確認する。

このファイルが既にコピー先から読まれているなら、コピーは完了したものとして扱い、続ける前に同じ確認を実行する。

対象リポジトリの `.cursor/settings.json` に pstack を追加する。ファイルまたは `.cursor` ディレクトリが存在しないなら作成する。

このエントリを既存の JSON または JSONC にマージする:

```json
{
	"plugins": {
		"pstack": { "enabled": true }
	}
}
```

無関係なトップレベル設定と、他のプラグインエントリは全て保持する。`plugins.pstack` が既にあるなら、`enabled` の値だけを変える。ファイルが JSONC ならコメントと妥当な JSONC 構文を保持する。編集後にファイルを検証する。

対象プロジェクトをリロードするか、そこをルートとする新しいエージェントを起動する。次の共有 pstack skill がプロジェクトスコープから解決されることを確認する:

- `how`
- `why`
- `tdd`
- `unslop`
- `principle-separate-before-serializing-shared-state`
- `principle-minimize-reader-load`
- `principle-guard-the-context-window`
- `principle-sequence-verifiable-units`
- `principle-fix-root-causes`
- `principle-prove-it-works`

現在のセッションやユーザスコープのプラグインから読み込まれた skill を数えてはならない。対象リポジトリの新しいエージェントが、プロジェクト設定を通じて pstack を受け取っていることを確認できなければならない。

プロジェクトスコープのプラグインインストールが利用できない場合、または共有依存のいずれかが解決しない場合は、止めて失敗の内容を説明する。

Benny のファイルは `.cursor/automations/benny/` から直接読まれる。そのディレクトリをプラグインマニフェストに追加してはならず、その `SKILL.md` がスラッシュ skill の一覧に現れることを期待してもならない。

どちらかのオートメーションを有効にする前に、`.cursor/settings.json`、`.cursor/automations/benny/`、および参照されるシークレットを含まない設定をコミットする必要があることをユーザに伝える。ユーザが求めない限りコミットしてはならない。

このチェックが通れば、ライブのオートメーションプロンプトは、コミット済みの運用ファイルを安定したリポジトリ相対パスで読んでよい。プラグインのキャッシュパスを埋め込んだり、ファイルの内容をコピーしたりしてはならない。

## 2. 設定を適合させる

コピーされた次の例を開く:

- `../../templates/configuration.example.yaml`
- `../reproduce-and-fix-issues/references/feature-map.example.md`

`.cursor/automations/benny/` の外に、ユーザ所有のコピーを作る。これらは設定ファイルであり、パックファイルではない。配置場所の例:

- プロジェクト設定、例えば `.cursor/benny/configuration.yaml`
- プロジェクトの feature map、例えば `.cursor/benny/feature-map.md`
- プロジェクトの routing map、例えば `.cursor/benny/routing.md`
- ユーザ設定、例えば `~/.config/benny/configuration.yaml`
- ユーザの feature map、例えば `~/.config/benny/feature-map.md`

オートメーションが再現しうる全てのユーザ向け機能について、feature map のセクションを 1 つずつ埋める。ユーザ視点を保つ。実装の詳細や現在のコードパスをマップに固定してはならない。

コピーされた例を編集してはならない。パックのリフレッシュは、コンフリクトのレビューを経てソース管理下のファイルを更新することがあるが、ユーザ所有のコピーには決して触れてはならない。

新しいオートメーションのチェックアウトがそれらを読む必要があるなら、対象リポジトリにコミットされたシークレットを含まないファイルを優先する。そうでなければ、必要な値をライブプロンプトの中に言い換えて書く。リポジトリのファイルを参照するのは、オートメーションが動くリポジトリにそのファイルがコミットされていることを組み込みの `/automate` skill が確認した後に限る。

コミット済みのパックと設定ファイルには、安定したリポジトリ相対パスを使う。ライブのオートメーションから、プラグインのソースディレクトリやプラグインのキャッシュパスを決して参照してはならない。

## 3. 必要な選択肢を埋める

次を尋ねるか確認する:

- ソースの Slack チャンネル ID
- 任意のオペレーション用またはステータス用チャンネル ID
- リポジトリ URL と既定ブランチ
- triage のアイデンティティまたは Slack ユーザ ID
- issue トラッカーの種別、チーム、プロジェクト、ラベル、受付ステータス
- トラッカーのアダプタ skill または MCP アクション
- 任意の routing map のパス
- 必須のコントロール skill 名
- 必須のユーザ向け feature map のパス
- ステータス絵文字の文字列
- pull request の URL 形式
- ポーリングと effort の予算
- triage、repro、コード作業、メディアレビューに使うモデルの slug

ユーザの Cursor のモデルピッカーまたはサポート対象モデル一覧で利用可能と表示されているモデル slug のみを使う。slug を推測してはならず、非公開の既定値を引き継いでもならない。

ソースチャンネル、triage のアイデンティティ、リポジトリ、トラッカーアダプタ、コントロール skill、feature map は明示的でなければならない。必須の値が曖昧なままなら、セットアップを失敗させる。

保存する前に、最終的なオートメーションの名前、説明、プロンプトのシムに pstack の `unslop` skill を使う。

## 4. 連携の機能を確認する

triage オートメーションが必要とするもの:

- 設定されたソース Slack チャンネルとそのスレッドへの読み取りアクセス
- そのチャンネルでのスレッド返信アクセス
- 報告にメディアが含まれる場合の、添付メタデータとファイルダウンロードのアクセス
- 設定された issue トラッカーアダプタを通じた検索・読み取り・作成・更新のアクセス

repro オートメーションが必要とするもの:

- ソーススレッドへの読み取りアクセス
- ソースチャンネルでのスレッド返信アクセス
- 設定されたオペレーションチャンネルでの、任意の投稿・編集アクセス
- リポジトリの読み取りと履歴のアクセス
- draft pull request を開ける pull request アクション
- 設定されたコントロールアダプタ skill

読み取りと投稿には、設定済みの Cursor Slack アクションを優先する。任意の `BENNY_SLACK_BOT_TOKEN` は、オペレーションのステータスメッセージを 1 つ編集する、添付をダウンロードする、といった狭い隙間を埋めるために使ってよい。値は YAML ではなく、シークレットマネージャか環境に保存する。

ドキュメント化されていない連携エンドポイントを使ってはならない。

## 5. routing map を用意する

ユーザが再ルーティングやオーナーへのメンションを望むなら:

1. `../triage-issue-reports/references/routing.example.md` を `.cursor/automations/benny/` の外にコピーする。
2. 全てのプレースホルダを、公開値または組織内の値に置き換える。
3. オーナーへのメンションは既定でオフにしておく。
4. メンションを許すのは、設定された機能オーナー、または確認済みのリグレッション作成者と見られる人物に対してのみとする。

routing map が設定されていないなら、triage は報告を分類してよいが、宛先やオーナーを推測してはならない。

## 6. コントロールアダプタを検証する

`../reproduce-and-fix-issues/references/control-adapter.md` と、ユーザが記入した feature map を読む。

指定された skill が次をできることを確認する:

- 対象アプリを立ち上げる
- マップされた全機能を実際の UI で操作する
- 宣言されたアダプタのアクションを通じて、マップされた状態を発生させる
- 結果を強制することなく状態を検査する
- スクリーンショットを取得する
- 録画を開始・停止する
- 自身のプロセスと一時データを後始末する

いずれかの能力が欠けているなら、repro オートメーションは無効のままにする。実施していない再現を主張するよりも、閉じる方向で失敗しなければならない。

## 7. ライブのオートメーションを準備する

これが初回作成なのか、既存オートメーションの設定なのかを尋ねる。

どちらの経路でも、コピーされたパックの `../../FOR_AGENTS.md` を主要なユーザ意図のソースとして読む。それを使って、2 つのトリガ、ツール、指示、結果、共通ルールを理解する。

### 初回作成

オートメーションは 1 つずつ作成する。

各オートメーションについて:

1. 対応するコピー済みプロンプトテンプレートを、二次的な内部資料として読む。
2. `FOR_AGENTS.md`、完成した Benny の設定、テンプレートの意図を、完全な自然言語のリクエストに変える。
3. ライブプロンプトに対し、`.cursor/automations/benny/` 配下の正確なコミット済み運用ファイルを読んで従うよう指示する。
4. プラグインのソースやキャッシュのパスではなく、安定したリポジトリ相対パスを使う。運用ファイルの内容をライブプロンプトにコピーしてはならない。
5. 組み込みの `automate` skill を読んで従う。
6. Slack チャンネル、リポジトリ、接続済みの連携の発見は `automate` に任せる。
7. コピーされたパックと参照される設定ファイルが、オートメーションが動くのと同じリポジトリにコミットされていることの確認は `automate` に任せる。
8. ドラフトの表を示し、承認を得て、準備状況を尋ね、Automations エディタを開くのは `automate` に任せる。
9. このオートメーションのエディタへの引き渡しを終えてから、次に取り掛かる。

`automate` には、設定から埋めた次の完全な triage 意図を渡す:

- 名前は `benny-triage`。
- 毎回の実行で `.cursor/automations/benny/skills/triage-issue-reports/SKILL.md` を読んで従う。
- 設定されたソース Slack チャンネルの新しいトップレベル報告ごとに発火する。
- トリガとなったスレッドを読み、そのスレッド内にのみ返信する。
- 設定された issue トラッカー連携を使う。
- 分類し、証拠を精査し、原因を辿り、重複を排除し、明確な新規バグのみを作成する。
- スレッド内のみの判定を 1 つ、設定された `[benny:bug]`、`[benny:performance]`、`[benny:other]` のマーカーと、任意のトラッカー URL で締める。
- ソースチャンネルのルートメッセージを決して投稿しない。

triage のエディタ引き渡しが完了した後、`automate` に次の完全な repro と修正の意図を渡す:

- 名前は `benny-reproduce`。
- 毎回の実行で `.cursor/automations/benny/skills/reproduce-and-fix-issues/SKILL.md` を読んで従う。
- 設定されたソース Slack チャンネルの、同じ新しいトップレベル報告で発火する。
- 設定されたリポジトリと既定ブランチを使う。
- ソーススレッドを読み、そのスレッド内にのみ返信する。
- pull request の作成と、設定されたトラッカー、コントロールアダプタ、feature map の要件を含める。同じリポジトリに適格なコミット済みファイルがあることを `automate` が確認しない限り、マップされたユーザ経路と状態は言い換えて書く。
- 行動する前に、信頼できる triage マーカーを待つ。
- マップされた実際の UI を通じて、まったく同じ症状を 2 回再現し、証拠を取得する。
- 既存の修正を、その上に自分の実装を被せることなく検証する。
- 再現が確認された後にのみ、範囲を限った任意の修正を試み、証明とチェックが通ったら draft pull request を開く。
- ソースチャンネルのルートメッセージを決して投稿しない。

`automate` の Slack、リポジトリ、連携、完全性、認証、ドラフトレビュー、承認、準備状況、エディタ引き渡しの作業を重複して行ってはならない。

### 既存のオートメーション

組み込みの `automate` skill は作成専用である。既存のオートメーションを検索・調査・更新するのに使ってはならない。

設定、ルーティング、コントロールアダプタ、feature map の検証を終える。その上で、ユーザに次の簡潔なエディタ用チェックリストを渡す。

既存の triage オートメーションについて、次を更新する:

- 名前と説明
- `.cursor/automations/benny/skills/triage-issue-reports/SKILL.md` を読むという直接の指示
- 新しいトップレベル Slack 報告のトリガとソースチャンネル
- Slack スレッドの読み取りと返信の権限
- issue トラッカー連携
- 言い換えた triage の指示、スレッド内のみのルール、Benny の判定マーカー

既存の repro オートメーションについて、次を更新する:

- 名前と説明
- `.cursor/automations/benny/skills/reproduce-and-fix-issues/SKILL.md` を読むという直接の指示
- 対応する Slack トリガとソースチャンネル
- リポジトリと既定ブランチ
- Slack スレッドの読み取りと返信の権限
- pull request アクション
- トラッカー、コントロールアダプタ、feature map の要件
- 言い換えたマーカー待ち、証拠、検証、範囲を限った修正の指示

既存の各オートメーションは、その Automations エディタで直接更新するようユーザに依頼する。置き換えや複製を作ってはならない。

### 作成の境界

オートメーションのバックエンドサービスやバックエンドのオートメーションツールを直接呼び出してはならない。ドラフトのフィールドを含むブラウザ URL を使ってはならない。Cursor のプロトコルディープリンクを構築・オープンしてはならない。新規オートメーションの唯一の完了経路は、組み込みの `automate` skill によるレビュー済みの Automations エディタ引き渡しである。

エディタ保存後にスレッド安全性のテストが通るまで、どちらのオートメーションも有効にしてはならない。

## 8. スレッド安全性をテストする

テスト用チャンネル、または無害なテスト報告を使う。

テストの前に、対象リポジトリの `.cursor/settings.json`、`.cursor/automations/benny/`、および参照される全てのシークレットを含まない設定ファイルが、オートメーションのチェックアウトが使うブランチにコミットされていることを確認する。両方のライブプロンプトが、それぞれの正確なコミット済み運用ファイルを指していることを確認する。いずれかの確認が失敗したら止める。まだオートメーションを有効にできないとユーザに伝える。

確認する:

1. triage がルートの `thread_ts` を保存し、判定をちょうど 1 つ返信として投稿する。
2. その判定に、設定されたマーカーが 1 つ含まれる。
3. repro が、設定された triage アイデンティティからのマーカーのみを受け付ける。
4. repro が、同じ不変のソース座標を保つ。
5. ソースチャンネルのルートメッセージが現れない。
6. 委譲されたワーカーが、いかなる Slack 書き込みアクションも使えない。
7. 座標の欠落、親の削除、preflight の失敗のいずれでも、投稿もトラッカーの issue も発生しない。

7 つのチェックが全て通ってから、通常のトラフィックを有効にする。
